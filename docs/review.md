# Review

Review is the last phase, and it closes the loop the whole system was built around: it holds the delivered work up against what was agreed and confirms they match. The reviewer is framed as a senior architect who has never seen this code before — fresh eyes, questioning everything, there to find problems rather than fix them. That independence is the point. The people and agents who build something are the worst placed to notice what they assumed; a reviewer with no stake in the implementation and no memory of writing it catches what they cannot.

Review refuses to start unless both the plan and the implementation are complete — and it will not start quietly beside another session already writing or checking code. A checkout has one working tree, and review is not a read-only phase: its per-task verifiers only read, but its change-set verifiers measure by the project's own rules, the corrections it makes edit the tree, and the verifier that checks those corrections runs your suite over them. So [implementation](implementation.md) and review take turns across the whole checkout, and a second one meets a red stop naming which topic the other session holds and how long ago it was active — a stop you can walk through, on the stated condition that you know that session has finished. If a review already exists, you can continue it — the system tracks which tasks each review covered, so it re-reviews only what has not been checked yet — or restart and review everything again. A restart is a genuine discard: any remediation the abandoned review had queued is retired — marked skipped in the plan and disclosed in the next report — so abandoned corrections never execute behind your back, and a discarded task is always something the report *says* was discarded, never a silent gap.

## What a cycle checks

Review reads the plan and the specification. It does not re-read the discussion, because the discussion's decisions were already absorbed into the spec upstream; the spec is the contract, so the spec is what the built work is measured against. Working from those, it detects in two layers, and the two are deliberately different in what they hold the work against and in what they are allowed to do.

The first layer is per task. Verifier agents are dispatched in parallel, one per task, and each checks its task independently by reading — it runs nothing. It checks the implementation: is the task actually built, does it match its acceptance criteria and the spec, has anything drifted — with the code as the source of truth, so a deliberate, sound divergence from the written word is a question rather than a finding, and only a loss is reported. It checks the tests: does a real test exist, does it cover the criteria and the edge cases, would it fail if the feature broke — and, just as importantly, is it *over*-tested, padded with redundant assertions or excessive mocking. And it checks code quality against the project's conventions and the usual structural concerns. A verifier reports only what is wrong. Each finding names the failure it prevents — what goes wrong if it is left — and records two things about itself: whether it sits inside the delivered change-set, which is what the work actually built or altered rather than what the spec's text happens to mention, and how far its fix reaches — contained, when the exact change is known and the compiler, the suite or a guard would catch it going wrong, or spreading, when the correct shape is not obvious or the checks would never see it go wrong. Something merely tidier is not reported at all. And a criterion reading cannot settle — one that holds only under something run or observed — is neither passed over nor guessed: the verifier quotes it, says what would have to be run to settle it, and hands it on to the second layer.

The second layer is the executing pass, run after every task has been read — once per review cycle, over the change-set as it then stands. A few change-set verifiers — one per section of the specification, adjacent sections merged when there are many, plus one over the test surface — each hold the *whole* delivered change-set against their section's intent rather than any task's criteria. The gaps between tasks are theirs: a requirement no task carried, a behaviour two tasks built halves of, an edge the spec names that nothing delivered. They measure where the project's own conventions give a way to — its declared linters, its build, a single package's tests by the project's own command and only to confirm a defect already suspected, a disposable dependency only where the project says how to stand one up — and read where they do not, because a way of running the project that the workflows invented would not be the project's way. They never run the whole suite — that runs once, later, over the corrected tree — and they leave the tree as they found it: it is checked clean after the pass, and anything left behind stops the review rather than being reverted blind. They take the criteria the first layer could not settle and measure them, a criterion that fails becoming a finding like any other; what they cannot measure either is recorded with the reason. And each returns a coverage map — what it checked and found sound, where it lives, and how it was checked — because an empty findings list is evidenced by its map or it is not evidenced at all.

## How findings are handled

Every finding from both layers is then checked against the code before anything is written or applied. Each verifier saw one task or one section; none of them knows that six findings target one sentence, that a fix would breach an invariant asserted three packages away, or that a section's finding and a task's finding name the same defect. A prep pipeline of read-only agents establishes all of that. Of every finding it asks: is it true — the file it cites is opened, never taken on trust, since it was written against a tree that has since moved; would the change it proposes meet the project's code standard; and where its remedy is comment text, is that because the prose is wrong or because it was the easy edit — a code defect wearing a comment fix is re-aimed at the code, and the reach of that code change is read afresh. One agent builds an inventory of the project's own guards first — the tests asserting what must remain true — and asks whether applying each finding could breach one, or is safe only if done a particular way. Another sees the whole set at once and finds the collisions: duplicates, findings competing for one site, findings bound across files by a guard, findings asking for opposite outcomes.

A synthesis merges those assessments into one action list. Collisions collapse into single actions — a bound pair spans every file it binds and is never split — and each survivor is routed by one question asked in order. Not actually wrong: discarded, with its reason recorded; a large discard list is a healthy review, not a failed one. Inside the change-set with a contained fix: corrected in this session. Appliers apply those actions in batches, one batch at a time, each owning its files outright and compiling as it goes; a verifier then reads the whole uncommitted diff as one body of work — the view no applier had — repairs damage, smooths the seams of piecemeal editing, runs the suite, and reverts anything it cannot repair; and what survives lands as one commit naming exactly the files it touched. A blocking issue — an acceptance criterion unmet in substance, or behaviour broken — whose remedy is contained is among them: corrected, and named in the report as blocking and corrected. All of this happens before the review is presented, because leaving such work costs more than doing it: it is never re-found on a later cycle, and any remediation that follows builds on corrected code rather than on files still carrying false claims. Inside the change-set with a fix that spreads: planned, which fails the review — and because the verdict hangs on it, the claim that a fix spreads is verified against the code first, the callers counted, before it is allowed to fail anything. Outside the change-set: held for your call at a pass, never filed automatically, because filing costs a whole pass through the pipeline and whether that is worth spending is yours to decide.

The verdict is derived from that routing, never chosen: pass or fail, and fail exactly when something must go back to planning. A passing review can still carry corrected work and held findings; neither blocks, because the first is already finished and the second was never part of this specification.

## The report and the verdict

The report is written from the outcome. Its specification-compliance section is the change-set verifiers' coverage maps, carried as they were written and never summarised into a sentence — a paraphrase is not evidence. Its plan-completion section steps back to the whole plan — were the phase criteria met, was anything built that was never planned, was anything planned never built — and names any criterion neither reading nor measurement could settle, quoted, so a criterion nobody measured is disclosed rather than ticked. Corrected work is recorded as the commit shows it, never as a status claimed it, with anything reverted still owed. What must be planned carries why the review failed — what is wrong, the failure it causes, and how far the fix reaches. And every discard carries its reason, so a reader sees the judgment rather than inferring it from silence.

What you see is smaller than the report: the verdict, the counts — corrected, held outside this work's scope, discarded, not measured — and only what you must act on, each item led by its impact rather than its mechanism, with a plain account of what was reviewed and where it stands; you can ask about any finding, and the answer draws on the report, the per-task findings, the change-set verifiers' files, the spec and the plan. At a pass you complete the phase — review is the last phase, so that is the pipeline finished for this topic — or first take up the held findings: they have accumulated across cycles, so they are re-checked against the code as it now stands, offered with what taking each up would cost, and only the ones you choose are filed to your [inbox](capture-and-inbox.md). At a fail, the planned findings become remediation tasks and implementation reopens.

## Why it runs in cycles, and why they are capped

Review is not a verdict handed down once. Whatever could be corrected in the session already has been, so a cycle is owed only for the work that must be planned. At a fail those findings — already deduplicated, corrected and constrained by the prep — are synthesised into remediation proposals, and a proposal whose evidence indicts the specification rather than the code is settled against the record first, so the tasks are authored against a correct spec. You approve the proposals one by one, each authored into a full task only once you have, and those tasks are written back into the plan. Review then re-opens implementation and hands off to a fresh session to build exactly those tasks, which then flows back into review again. Build, review, remediate, build again: this is the loop, and it repeats until the work and the agreements line up. Each pass reviews incrementally, only the newly changed work, so cycles get cheaper rather than re-litigating the whole thing every time.

The self-correcting loops inside this machinery are deliberately capped. The automated checks that run during specification and planning escalate to you after a few unproductive rounds and stop entirely at a hard safety limit; implementation's fix loop forces a decision after three attempts on a single task, and its analysis loop asks you to confirm every cycle past the third on a topic, however many sessions it took to get there. At every one of these limits the same thing happens: the system shows you a convergence read — is this converging, holding steady, or diverging with each fix spawning new problems — and hands you the decision. The cap is not a signal to give up; it is an escape hatch for you. Its reason is straightforward: an unattended loop that keeps correcting itself can thrash forever, or worse, diverge, with every fix creating the next problem. Rather than let that happen quietly, the system surfaces it and asks. A loop that cannot end on its own is one you would not want running while you are away, so the design guarantees it always comes back to a human before it goes too far.

The result is a delivery that has been measured against the record that produced it, with any gaps either closed or consciously accepted by you. That is what makes "done" mean something here: not that the agents ran out of things to do, but that the built thing was checked against what you decided to build and found to match.
