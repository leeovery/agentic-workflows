# How it stays reliable

A system you hand months of work to has to be trustworthy in a specific way: it must not quietly drift. The status it shows you today should mean the same thing tomorrow; a decision captured last week should still be there next month; a session that crashes mid-task should not leave you guessing what actually happened. This reliability comes from a few guarantees you can feel, even though the machinery producing them stays out of sight. You do not manage any of it — you just do not experience the drift it prevents.

**There is one authority on the state of your work.** The assistant reasons, proposes, and talks with you, but it never decides on its own what the true state of your work is. Anything that can be worked out from what is already recorded is worked out once, the same way every time, and everything reads from that single source. So you will not get one answer today and a subtly different one tomorrow because the assistant recalled the situation loosely. Status is derived from your files, not remembered; a phase is complete because the record says so, not because someone said "done." State changes are consistent and repeatable rather than improvised — which is why phases cannot be skipped, and why a half-finished session resumes exactly where it stopped. Resumption is exact about decisions, too: a question you answered before a crash is not asked again, and work an interrupted session left half-done is either picked up precisely or retired visibly — never silently rerun, never silently dropped.

**Your work is written down as it happens.** The system treats finished thinking as something to be saved into version control continuously — at natural breaks, before context is refreshed, as each document completes — rather than left floating in a conversation that could be lost. Because the work lands in git along the way, your history is real and recoverable: you can see how a decision was reached, and nothing important lives only in a chat window. Kill a session whenever you like; the next one picks up from disk. The system's own memory is committed with the same discipline whenever it changes. And each commit is scoped to the action that produced it — a commit for one topic's progress stages that topic's files and nothing else, so work happening in parallel is never swept into a record it does not belong to.

**The files stay current with the design.** As the system itself improves, the shape of older projects' records could fall out of step with how things work now. That gets reconciled quietly at start-up: existing work is brought forward to match the current design, safely and repeatably, so you are never operating on a stale or half-migrated project. This is invisible when nothing needs changing, and when something does, you are shown a plain-language summary of what moved before anything continues. Where one of these updates has to transform content that was originally written with judgment, code alone is not trusted to have matched it: the update leaves verification notes behind, and those checks are made — with judgment — before you are asked to confirm the result.

**Finished work is never read over stale ground.** Reopen something another phase was already built on — re-decide a discussion a specification extracted, revise a spec a plan was written from, change an implementation a review already approved — and the system marks the downstream phase "input moved" at that moment. The mark is visible everywhere it matters: status rows and menus carry the cue, nothing that would build on the stale input is recommended, and the pipeline routes back to the marked phase instead of forward past it. An epic will not offer to complete while any mark is live, and a specification whose source discussion was re-decided after extraction refuses sign-off until the change is genuinely reconciled — not re-extracted wholesale, but diffed against what was already written and amended through the normal approval gate. The mark clears the next time you enter the affected phase, where you are shown what moved; each phase's reconciliation then decides whether the change ripples one phase further. Staleness travels hop by hop, in the open — never as a silent cascade, and never ignored at the finish line.

**Two sessions do not trample each other.** Long work invites working in parallel, and the system expects it. Every running session leaves a per-topic heartbeat, so the epic view can mark a topic as open in another session — it strikes those entries through, never recommends them, and asks before letting you open a second session on the same topic. Background analyses hold off while a peer session is live on the material they would read. A crashed session's heartbeat is recognised as dead rather than blocking you forever, and an orderly exit cleans its own markers up.

**Delivery is checked against what you agreed.** The final phase's whole job is to hold the built work up against the record that produced it — the discussion that shaped it, the specification that defined it, the plan that scheduled it — and confirm they match. "Done" is not a feeling anyone reports; it is a check against durable agreements you made earlier and approved.

**Every path is rehearsed before it ships.** The system's own test bed replays every pipeline end-to-end against the deterministic core — each work type's full arc plus the awkward edges: reopening finished work, merging overlapping specifications, cancelling and reviving topics, converting one kind of work into another — checking the entire recorded state after every single step. A change to the system that would corrupt state, or record something one display reads differently from another, fails that rehearsal before it ever reaches a release. This is aimed squarely at the worst class of bug: the one that writes fine, raises nothing, and only shows up three phases later as a menu that looks wrong.

Put together, these are the guarantees the system rests on: one source of truth for state, a history you can trust, files that never silently rot, staleness that announces itself instead of hiding, sessions that coexist without collision, every path rehearsed before it ships, and delivery measured against what you actually decided. Decisions are captured, the capture is authoritative, and the outcome is validated back against the capture. That closed loop is what lets you leave the loop running and trust what you come back to. If you want the mechanism these guarantees rest on rather than the guarantees themselves, [the engine](engine.md) describes it.
