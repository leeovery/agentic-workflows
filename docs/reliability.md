# How it stays reliable

A system you hand months of work to has to be trustworthy in a particular way: it must not quietly drift. What it shows you today should mean the same tomorrow; a decision captured last week should still be there next month; a session that crashes mid-task should not leave you guessing what happened. Ledger's reliability comes from a few guarantees you can feel, even though the machinery behind them stays out of sight. [The engine](engine.md) describes that machinery.

**There is one authority on the state of your work.** Claude reasons, proposes and talks with you, but it never decides on its own what the true state of your work is. Anything that can be worked out from what is recorded is worked out once, by the engine, the same way every time, and every screen reads from that one source. A phase is finished because the record says so, not because someone said "done", which is why phases can't be skipped and why a session resumes exactly where it stopped. The record is guarded at the door too: hooks Ledger installs in the project's Claude Code settings refuse Claude editing a state file directly and point it back at the engine, with or without Ledger's Claude Code mod.

**Every decision is on the record, and the record only grows.** Every question, finding and decision is an entry on the [ledger](trust.md#the-ledger), and nothing on it is ever edited: a change of mind is a new entry replacing the old one. The engine checks on every read that the ledger begins, byte for byte, with what was last committed, and stops if a line was changed outside it. So the history of how a decision was reached is always there to read, and "what have you decided without me?" always has a complete answer.

**Your work is written down as it happens.** Every action commits what it wrote, on Ledger's own [state branch](state-and-git.md), and pushes it wherever the project has a remote. Nothing important lives only in a chat window: kill a session whenever you like, and the next one picks up from disk. Each conversation keeps a log beside the record — its journey, the options weighed and why minds changed — under a dated heading per session that names the conversation that wrote it and the path of its transcript. The transcript lasts only as long as Claude Code keeps it; Ledger never sets or recommends how long that is, and the log stands on its own without it.

**A compaction, a crash or a new session carries on.** A conversation compacted mid-phase doesn't start over: the phase re-reads its instructions and the record it runs from — prompted at once where Ledger's Claude Code mod runs — and continues where it was, with no recap. A message you had just sent is taken up where you sent it; otherwise the menu that was waiting on you comes back. A question you answered before a crash is not asked again, and work an interrupted session left half-done is either picked up precisely or retired visibly, never silently rerun or dropped.

**Nothing builds on a decision that changed under it.** When a decision is replaced, every entry that relied on it is marked affected, but the replacement's own cause, and stays marked until it is confirmed still holding or replaced itself. The topic shows among what waits on you, "a decision it relies on changed", so nothing affected is trusted by mistake. A concluded spec is never corrected: a change after it is new work, replacing the entry on the ledger and flagging what relied on it where it is made. The change travels in the open, one link at a time, never as a silent cascade.

**Two sessions don't trample each other.** Long work invites working in parallel, and Ledger expects it. A session working a topic leaves a mark on it, so an epic's menu shows the topic in session, strikes it through and asks before you open a second session there; a crashed session's mark is recognised as dead rather than blocking you, and an orderly exit clears its own. A state commit takes what its own action wrote, together with any conversation log written since, and a code commit only the paths its task names, so one session's commit never sweeps up another's half-made change. Code is the exception, since a checkout has one working tree: a build and the review phase take turns in it, and entering one while another session holds the code names that session and asks before going on. Inside a build, tasks run side by side, each in a worktree of its own, and each quick-fix is built in a worktree of its own.

**Proof comes from running the product.** A builder proves each task by driving the running product the way a user would, and a script, never Claude, writes the verdict; a scenario nothing could drive is reported not proven. [Verification](verification.md) has how.

**Delivery is checked against what you agreed.** The review phase's whole job is to hold the built change up against the spec, area by area, and every finding lands somewhere: fixed, or filed. Finish is yours, and it shows anything skipped on the way there with its reason. "Done" is not a feeling anyone reports; it is a check against decisions you made and approved.

**The files stay current with the design.** As Ledger improves, older projects' records could fall out of step with how it works now. That is reconciled at start-up by migrations: each a numbered step, applied at most once, that stops rather than half-applies if anything is wrong. When something needs changing you are shown what moved before anything continues, and where a migration has to carry content that was written with judgment, it stops for the session to do that work, and checks it before you are asked to confirm the result. The move from before Ledger onto the state branch is one of them; [state and git](state-and-git.md#moving-a-project-across) describes it.

**Every path is rehearsed before it ships.** Ledger's own test bed replays every kind of work end to end against the engine — each work type's full arc, and the awkward edges: cancelling and reviving work and topics, turning one kind of work into another — checking the whole recorded state after every step. A change that would corrupt state, or record something one screen reads differently from another, fails there before it reaches you.

Put together, these are the guarantees Ledger rests on: one source of truth for state, a history you can trust, a record that only grows, a changed decision that flags what relied on it, sessions that coexist, work proven by running it, and delivery measured against what you decided. That closed loop is what lets you leave the build running and trust what you come back to.
