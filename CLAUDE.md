# CLAUDE.md

Guidance for Claude Code working in this repo.

## Project Overview

Agentic Engineering Workflows for Claude Code. Installed via `npx agntc add leeovery/agentic-workflows`.

**This project authors the workflow system — it does not use it.** Never invoke workflow skills (`/workflow-start`, `/workflow-continue-*`, etc.) for work on this project. Edit skill files, references, and scripts directly. This CLAUDE.md is development documentation that does not ship with the product — installed projects get their own. Skills and agents must be self-contained — never rely on this file for runtime behaviour.

## Git Workflow

Always create a feature branch **before** the first commit. Never commit to main and move commits after. The only exception is when explicitly told to commit to main.

## Changelog

`CHANGELOG.md` is generated by Mint, the release tool that mints commits and releases. **Never edit it by hand** — no `[Unreleased]` section, no entries in a PR. The release writes it.

## Reviewing Work

`/review-work` is the standing review pass — run it when asked to review the work, check for regressions, or verify convention adherence. It dispatches one `workflow-reviewer` agent per dimension (`.claude/skills/review-work/references/dimensions.md`), verifies the findings, and lands the fixes. Where those fixes go depends on review state: commits onto a PR whose review is live, a new top-of-stack PR once a layer is signed off, folded into the owning PR while nothing has been reviewed yet.

## Ideas

Improvement ideas live in `ideas/`, indexed by `ideas/INDEX.md`.

The index holds **pending items only** — one table. **When you complete an idea, remove its row and delete its file in the same PR as the work**; git history is the record of what shipped. Shipping the fix and leaving the row in place is how the index stops being trustworthy; an entry that reads open when the work landed sends the next reader to re-do it. Status nuance on a still-pending idea (partial ship, audit notes) belongs in its index row.

## Design Docs

`design/` holds each programme's design record. An in-flight design is rewritten in place as rulings change — pure design, no amendment history. **A concluded design doc is frozen: never edit it from a later change.** A change that alters shipped behaviour describes itself in its own PR, CLAUDE.md, and docs — never by annotating or rewriting the earlier record.

## Workflow Phases

The phases group into three stages (the **three D's**), used as the top-level grouping in the epic dashboard (`workflow-continue-epic/references/epic-display-and-menu.md`): **Discovery** (Discovery, Research, Experiment, Discussion, Investigation) — explore and decide; **Definition** (Scoping, Specification, Planning) — specify and plan; **Delivery** (Implementation, Review) — build and verify. The dashboard renders each stage as a `── STAGE ──` divider with the phases beneath it.

1. **Discovery** (`workflow-discovery`): the universal **first phase** — every work type begins here. Confirm the work type, shape the outline, persist at the work-type commit, route into the pipeline. Two invocation modes dispatched at Step 0: **new** (from `workflow-start`, no work unit yet — decide the type via the universal detection core, then epic → initial topic sketch, feature/cross-cutting → research-vs-discussion routing, bugfix/quick-fix → brief intent capture; a **product-altitude** read — no single unit of work on the table — routes out to `/workflow-roadmap genesis` before any work unit exists) and **existing-epic** (from `workflow-continue-epic` — skip the macro decision, re-shape the map). The **work-type commit is the durability boundary**: the confirm-trigger creates the manifest, writes the session log, lands imports, lands the promoted inbox item(s) as the work unit's **seed(s)** — uniformly for every type; nothing persists before it. The name is derived and never confirmed with the user — a single seed's filename slug, else the `description`, a name the user offered unprompted winning either — and a collision comes back as `workunit create`'s refusal, met by deriving another. For epics the same conversation continues into topic curation — name topics, classify each as research or discussion, build the discovery map, and at the harvest synthesise per-topic **briefs** (soft decisions, rejected paths, open questions) that seed each topic's research/discussion read-in-full — a brief written or regenerated over in-flight downstream work sets `reconcile_needed`, surfaced non-destructively (never overwriting); the gap analysis's approval gate writes the same file for a candidate it approves, from the gap rather than a conversation. A populated-map session also edits existing items (remove, rename, re-route, edit summary/description) via `map-operations.md`. Session log is created **lazily** for existing-epic edits, written by the confirm-trigger for new work. Resume detection (`resume-detection.md`) handles an interrupted prior epic session. The self-healing gap analysis (discovery-gap-analysis, the sole boot-time analysis) is run by `workflow-continue-epic` Step 6 and `workflow-bridge` section B via shared `topic-discovery-dispatch.md` — **not** from inside discovery. `workflow-continue-epic` ordering: Legacy Bridge (`/workflow-legacy-research-split` for pre-discovery epics with migration-seeded broad research files) → Summary Backfill → Self-Healing → Display. Direct-entry items land here with `source: direct-start`.
2. **Research** (`workflow-research-process`): EXPLORE — feasibility, market, viability, early ideas. Scoped per-topic, one file per topic at `.workflows/{work_unit}/research/{topic}.md`. Files the user shares land as imports whenever they arrive — discovery's opener, or mid-session through the shared `landing-shared-files.md` (`engine workunit import`, origin `research/{topic}`), read for the conversation and linked from the research file by relative path. Research carries **aids**, never an audit: no background review agent, no trigger checklist, no closing review — the phase's agent store holds `deep-dive` rows alone. The **deep dive** is the learning instrument: a background agent answering a brief (kinds survey / read / feasibility / landscape / verify — never measuring; a number a decision would rest on comes back under Opened as the measurement it would take, the laboratory's cue) whose report folds into the research file as a dated, sourced section, marks its thread `learned`, seeds threads from what it opened, and reaches the user as its answers in full at product altitude (a question brief) or a digest — no announce menu, no lanes, no dismissal. The **thread register** (`phases.research.items.{topic}.threads`, `engine research-threads add|set|reframe|remove`, `render research-threads`) is a lens, not a plan: what the topic set out to learn, origins `seed`/`brief`/`user`/`conversation`/a dive id/a rerouting topic, states `open`/`digging`/`learned`/`parked` with nothing gating on any of them; seeded and rendered at initialisation, rendered at natural breaks where a thread changed state, at the fold, at the resume, and above the conclude gate (`render research-conclude-gate` prepends it), never every exchange. The session loop commits after each write and evaluates nothing at the commit. Document review reconciles session against research file to catch undocumented substance (mandatory before conclusion); the conclusion writes open, being-dug, and parked threads into the file's Open Threads, which the discussion reads in full — open is a fine way to conclude.
3. **Experiment** (`workflow-experiment-process`): MEASURE — the umbrella laboratory research and discussion use; never a topic's first phase, never entered except through the spawn. A conversation whose number is about to bear a decision **offers** the laboratory (shared `experiment-spawn.md`; declining keeps an inline measurement, labelled exploratory); on yes the session writes the problem statement — **no design content** — to a cache scratch and `experiment create --from {phase} --problem <scratch>` allocates `E{n}` (per-topic series) and installs it as `experiment/{topic}/{id}-{slug}/problem.md` in the same transaction (no conceived record ever exists without its problem file), and the spawning item locks: `awaiting_experiments` gains the id, `topic complete` refuses engine-side until every wait releases (`wait-gate` is the refusal's graceful face; the post-spawn `experiment-spawn-gate` offers now-or-later). A `yes` at either gate is the **pause**: the session, its work already committed, invokes `/workflow-bridge {wu} {phase} none paused` — the same door a conclusion takes — and the bridge routes as after a conclusion: the epic continuation renders `phase-paused` (what the phase's conversations await, derived from their waits) in place of the completed banner and shows the menu, whose outstanding-research or live-experiment row is the way in; the linear continuations skip the revisit offer and enter plan mode at what `computeNextPhase` names. The **menu is the router**: the epic menu carries one row per topic whose series holds a live record, ranked above other recommendations (an interrupted discovery session's resume still leads), appearing at the first spawn and retiring when no live record remains; every route is the uniform entry contract, and the record resolves inside the phase — one live record auto-selects, several render the register with a picker. After a record ends, `experiment-next-gate` offers the next live experiment in the same session or the menu; either way the laboratory starts in fresh context — isolation is a scientific control that guards the spawning conversation's hopes, not sibling records. Record lifecycle `conceived → designed → approved → running → concluded | abandoned`: `advance` walks the mechanical steps, `approve` alone records the briefing's user-confirmed freeze, `conclude` takes the one-line verdict (the pre-registered decision rule's mechanical outcome), `abandon` keeps the row and its reason. Amendments are dated and re-confirmed before results are visible, frozen for good after; report corrections append-only. A split nests sub-experiments (`E{n}.{m}`, `--parent`) inside the running parent — the wait stays on the parent and releases once. A terminal top-level record releases the wait and flags the holder (`reconcile_needed: "experiment"`); the conversation's re-entry — or, for a conversation already in session, its loop's next check and its close — surfaces the register and reads the reports before the waiting point settles (`reconcile-advisory.md`'s experiment branch; `topic complete` refuses the holder while the flag is unread) — experiments measure, conversations decide, and an abandonment reverts the point to open. The phase item is derived bookkeeping over the records (`completed` when all terminal — `topic start/complete/reopen` refuse it; a new spawn reopens the series); the schema's `DERIVED_PHASES` property carries that fact, and every generic surface keys on the property, never on the phase name.
4. **Discussion** (`workflow-discussion-process`): Organic conversation guided by a live Discussion Map (`pending` → `exploring` → `converging` → `decided`/`deferred`). Background review agent for topical gaps; document review reconciles session against discussion file to catch undocumented substance (both mandatory before conclusion). The background review also hunts the user-visible edges of the mechanisms and screens the document has already decided — an input empty or malformed, a dependency unavailable, a boundary, a failure of the mechanism itself — the same edges the specification's gap pass hunts, filed `decide` where the record determines the answer and `ask` otherwise; how the tree achieves a decided behaviour stays the builder's. Off-topic concerns reroute into the target topic's triage queue (`.workflows/{wu}/{phase}/.triage/{topic}/`, one engine-numbered file per concern, delivered by the self-committing `topic triage`), landing with `source: reroute:{origin}` on an existing or newly-created map item (epics only); the target's session raises each queued concern as an opener through the shared `composing-a-raise.md` — the entry is the brief, its depth entering as responses, the fold recording the outcome. Outstanding research on the topic — in-progress or parked, a `triaged` stub on a topic whose discussion was never born included — holds the discussion shut at **entry**, every work type: derived from the research item's status, never stored, refused engine-side by `topic start` at the discussion's birth and by `topic reopen` (a discussion already in session resumes), and rendered by `render entry-gate` at the discussion entry skill before any status read (the menu's research row is the way in; the discussion carries no menu row of its own unless a live session holds it, when its continue row stands struck through beneath the research row — the epic tree names the research it awaits); the conclusion refusal — `topic complete` naming the wait, `wait-gate` alongside the experiment waits — stays as the backstop for research parked under a discussion already in session — by the session's own requeue, or by a peer's landing. Discovery-gap analysis (epics only, formerly discussion-gap-analysis) reads completed research AND completed discussions holistically to surface cross-artifact themes, research themes no discussion addressed, emergent topics, integration gaps — cached and manifest-tracked under `phases.discovery.gap_analysis_cache`.
5. **Investigation** (`workflow-investigation-process`): Bugfix-specific — symptom gathering + code analysis → root cause.
6. **Scoping** (`workflow-scoping-process`): Quick-fix-specific — context, spec, plan in one pass.
7. **Specification** (`workflow-specification-process`): Validate and refine into standalone spec. A spec declares two input types: **sources** (discussions extracted wholesale, gated by `incorporated`) and **consult references** (a sibling discussion read narrowly for an owed correction — cite the hand-off slice, don't extract; gated by `addressed`). Consult references are declared at grouping time (consolidation analysis + a KB advisory query surfaces candidates), carried into the handoff, tracked in the manifest under `specification.{topic}.consult_references.{name}.status`, and block completion until addressed. Source incoherence is met in-flow (`resolve-source-incoherence.md`, loaded from `spec-construction.md` and from `process-review-findings.md` when a review finding indicts a source): spec makes decisions clear, never makes them, and classification is Claude's — four moves by effort, derivation exhausted first (context, logic, sibling artifacts, measurement), a stop the exception that names what was searched. A claim that fails direct measurement against the tree lands its correction in the owning document (value-only or with a record-supported repair of the leaning conclusion, silently with a one-line notify; a mismatch stops only when it unseats a product conclusion no record-supported repair re-lands); anything else the record settles (supersession, derivable repairs) is derived **silently** — no raise, no edit to any source document; an unsourced decision a defensible derivation pins — the record yielding the answer (constraints, sibling artifacts, measurement), or first principles over the decisions it records whittling the fork to one answer the session stands behind, what leaned and the alternatives named — lands in the owning doc with a one-line notify, no stop; a settleable point always stops (overrides `auto`) — the conflict menu (numbered sides + Comment) where sides are documented, a plain conversational question where derivation ran out (an underivable point is a product-intent gap by construction: the spec never invents product intent, it makes only the call first principles over the record make obvious) — and the decision made together mirrors back into the owning doc (a discussion's dated timeline entry, reindexed, `sources stale --except` flagging other extractions); a genuine gap stops at an acknowledgement gate (a confirm — an objection drops into the settleable exchange — that on an epic also settles which of three homes takes it), then takes one of them: the owning document's triage queue (all work types — epic via `triage-landing.md`, linear via a direct `topic triage`); a new topic created on the map through `triage-landing.md` and added to this specification's `sources` as `pending` (epic), so the spec waits for it and extracts it when it concludes; or a roadmap park where the gap is beyond this specification's scope (epic — `roadmap add … --origin park:{wu}`, the review caller recording the finding `Declined` and construction the exclusion, neither pausing). The first two pause the spec in-progress and route the session to the work type's continue skill with the routed work named — an incorporated row reconciles at re-entry (`session-setup.md`), a pending row re-extracts the updated document. The gap exit liveness-checks the spec item first (a parallel session can collapse it). Spec entry hard-blocks on an unsettled record at every layer: the epic menu refuses the analyze route while discussions are open and a blocked spec's start/continue (`spec_blocked` in epic DATA), open discussions block the structure-building scenarios (`blocked-discussions-open`), a source still open — reopened, or opened by the gap exit and parked — blocks its spec (menu `blocked_spec` row + the epic entry-gate backstop). The grouping analysis records advisory `**Tension**` lines construction raises when the relevant chunk arrives. `topic complete` enforces the source gate engine-side (no completion over `pending`/`stale` rows). Spec review runs three strictly sequential agent passes per cycle — claims verification (re-runs the spec's recorded measurements against the tree and reads the code a cited product guarantee leans on, the unit's imports among its inputs), input review (fidelity against sources, including the reverse check: spec content no source decides, where an earlier cycle's tracking file is never a source), gap analysis (standalone, graded `Critical`/`Important`, the 90–95% coverage target stated in its brief, and from cycle 2 reading every earlier cycle's gap tracking file as settled directions — a finding refining a landed rule is out unless it contradicts it) — and a finding that indicts a source (`Source defect`, `Unsourced decision`) routes through the incoherence flow (Resolution `Routed`), never applied to the spec and never riding `auto`. Every finding any pass writes clears the floor (`finding-floor.md`'s bar, spec-flavoured: what goes wrong for the product's user if the implementer guesses, or it is not written) — duplication is a finding only where the copies encode a rule whose divergence would be silent and change what gets built, and a sub-floor point lands under `## Observations`, never walked and never counted — but a user-facing string, value, or behaviour whose answer the record already holds is a `settled` finding whatever its size, and a Contradiction is a finding; neither is ever an Observation. The Move vocabulary is `settled | choice | route`. `settled` is the record's answer or Claude's call: a source states the answer, the record uniquely determines it, first principles over the decisions the record made whittle the fork to one answer the session stands behind, or, among the answers that clear the floor, several serve the user equally and it picks the most appropriate — a call the record does not itself determine naming what leaned and the alternatives that also fit, the provenance rule, and a fork with one live side (a side no informed user would choose) settled whatever the derivation is made of. The walk disposes every finding against that bar before anything renders — a `settled` call the session cannot stand behind becomes a `choice`, the builder's is declined outright (a mechanism, a boundary, a byte any competent implementer settles the same way), a source-silent point a measurement or sibling artifact pins routes, and only a `choice` clearing every prong (product-level, irreducible, a side visibly costs the user, the tie-break is product intent) survives — then works the moves in turn. The **settled batch** (`render finding-batch` lane `settled`, screens of at most five with an `a/auto` row; under `auto` a display of what landed and no stop anywhere) lands each call: the record's own derivation applies to the spec and records `Approved`, a call the source document never made lands there first through the incoherence flow's landing step and records `Routed`. Each **choice** then walks alone and stops at every gate mode (the surface carries the auto-override line), its pick landing in the owning document before the specification re-aligns to it, recorded `Routed`; each **route** takes the incoherence flow. Under `auto` the loop concludes itself — no gate — on the convergence diagnostic's first `churning` verdict from cycle 2 or at the cycle-5 cap, the diagnostic rendered either way and its growth flag naming review-authored growth as the signal; what the specification leaves open is the implementer's (#8). Load-bearing empirical claims are recorded with their measuring command (`` `cmd` `` → result) in specs, discussions, and research alike, and both document reviews re-run them at conclusion.
8. **Planning** (`workflow-planning-process`): Define HOW — phases, tasks, acceptance criteria. The plan carries what the specification decided, product and how alike, and states no mechanism the specification did not: the how of the code is the implementer's, left open rather than settled, while a fork in how the work is cut — phase ownership, task grouping, order, dependencies — is the planner's and settles on what leans, at construction (`planning-principles.md`) and at the review walk's dispose alike; a gap in what the product does is classified and landed in the record, never answered in the plan. Acceptance criteria are scenarios — a starting state, an action, an observable outcome traceable to a specification section, rule form only where a scenario would be contrived — the task template carries no Tests or Edge Cases fields, and **Do** is optional and record-sourced (`task-design.md`). The review checks fidelity to the record and the plan's own structure, never what an implementer would have to guess. The three tiers are `resolve-spec-gap.md`, loaded once per `## Spec Defects` entry the phase designer, task designer, and task author report — and from the review walk's dispose over a finding that indicts the specification — before the structure, task-list, author, or finding gate renders: what the record settles or a defensible derivation pins lands as a silent corrigendum on the specification, one line said; a product fork stops for a brief exchange (overriding `auto`) whose answer lands in the owning discussion and brings the specification into line by corrigendum, the plan continuing; and a gap the exchange shows needs real discussion work — or whose discussion another session holds — goes to that discussion's triage queue and pauses the plan through the bridge. A plan is held while its specification is unsettled — not concluded, its own input moved, or a source row not yet extracted or moved beneath the extraction, derived from the specification item alone and never stored — at its entry, its birth and reopen, its conclusion (`render wait-gate`), its epic menu row, and the linear next-phase derivation. The traceability review flags any mechanism the specification does not decide alongside untraceable product content, and the fix is removal, never justification. Every review finding clears the shared `finding-floor.md` in its planning flavour — what the implementer builds wrong or fails to build, for whom, and how it would be noticed — sub-floor points landing under `## Observations` (one line each, never walked, never counted, never re-raised) and the severities reading `Critical`/`Important` alone; from cycle 2 both reviewers read every earlier cycle's tracking files of both streams, listed at dispatch, as settled directions a finding may not reverse — which bounds what they may find, never what they read; and the walk's decline is the builder's — a mechanism the specification leaves open, or a boundary, byte, ordering, or format detail any competent implementer settles the same way, or a preference no side of which costs the user — recorded `Declined` with its reason and never rendered. The plan review loop takes the specification loop's exits — under `auto` it concludes on the convergence diagnostic's first `churning` verdict from cycle 2 or at the cycle-5 cap, never a gate — and measures growth against `review_baseline_words`, stamped on the planning item when the review opens as the word count of `planning.md` plus every `phase-{N}-tasks.md`.
9. **Implementation** (`workflow-implementation-process`): Execute plan via TDD (or verification workflow for quick-fix). The how of the code is the executor's — every mechanism the task leaves open is settled with the code in front of it, a **Do** step the record sourced followed as written, and the tests named and written from the acceptance criteria — so its stop is **intent**: a product question the task, the specification sections it cites, and the code do not answer (`blocked`; an executor that could not finish is `failed`). On `blocked` the orchestrator classifies through `resolve-spec-gap.md`'s three tiers one hop down before anything renders — the reference takes an `implementation` lane and answers `landed | answered | stopped | unsettled`: record-settled or derivation-pinned lands the silent corrigendum and returns `landed`, the answer riding onto the task in flight as an addition marked with its origin — the orchestrator's where the record settled it, the user's where they settled it at the gate (`ad-hoc-plan-changes.md` §C) — and the executor re-dispatched with no stop, `auto` and `bounded` alike; a product fork is an **engineering stop presented to an engineer** — the task-result header (`display-task-result.md`, result `blocked`), then the block in the task loop's report register (`report-register.md` → Executor Block: **Blocked on**, **What the executor found** with real names and `file:line`, **Options** carrying each side's technical shape, product consequence and cost side by side, **Recommendation**), then the gate rendering those Options as numbered sides recommended-first with **Comment** beside them (`render executor-block-gate … --result blocked --file <sides.json>`, the engine heading the menu with the auto-override line off `task_gate_mode` so the prose never announces it) — no skip, no stop: a number picks, and a comment settles it, routes it, or is answered and the gate re-rendered. The pick lands in the owning discussion and the specification re-aligns by corrigendum; a gap the exchange shows needs real discussion work goes to that discussion's triage queue, and the session names the topic it is queued on and takes a terminal stop — never the conclude gate, no new wait, the staleness hop and the menu routing it back. A quick-fix's specification is its own record: tier two lands the user's answer there as a corrigendum directly, and tier three is unreachable — the exchange that shows the work has outgrown its type says so and re-renders the gate. A specification live in its own phase or held by a peer returns `unsettled` where nothing was asked — the same block moment puts the sides to the user — or `answered` where the user's answer is in hand and rides the task while the record is out. **During the build a task is finished or it is being fixed**: a `failed` executor — tests it cannot make pass, or an environment that will not do what the record assumes — presents its failure in the register (`report-register.md` → Executor Failure: **What failed**, **What the executor tried**, **Why**, **Next attempt**, or **What is needed** where the environment is the cause) and the gate offers `r/retry` with **Comment** to steer it, never a skip or a stop; a specification decision that proves untenable is a `blocked`, not a failure — the question is what the product does instead. Executor and reviewer report cross-scope consolidation opportunities under BANK, deposited (`implementation.{topic}.bank`) only while a phase's own tasks run — `task start` answers `do_banking`, and the loop loads the deposit reference on `true` alone; each phase closes through a consolidation boundary — a finder sweeps the phase's combined surface, confirms or drops each banked entry, and reports spec defects; the judge settles the defects (record-settled → the silent same-unit corrigendum route in `correcting-historical-artifacts.md`) and folds the survivors into **proposals** (problem + direction settled with its derivation, class-tagged incl. `behaviour`; an irreducible product fork as a Decision — stakes argued, sides stored as product end states, recommended side first — which is raised in product terms between the slim header and the sides menu (`raising-a-decision.md`, technical retelling one option away) and always stops, auto included) walked at proposal altitude; the approved shortlist is expanded by the task-author agent and transcribed by the task writer into the still-open phase (`staging.p{N}`, `consolidation_gate_mode`, `consolidated_phases`) before `--phase-complete` records. The analysis and review synthesis loops share the same shape — synthesizers stage proposals and report spec defects; author before writer at task creation. The **settled directions** are derived, never stored: every earlier walk's `approved` rows in the implementation and review items' `staging` name proposals in that pass's staging file whose title and Solution an earlier pass settled, and the boundary judge and the synthesizer read them before judging — a proposal that reverses one is dropped unless the finding shows it wrong by measurement, the specification, or a project rule, never raised to the user; the analysis agents, executor, and reviewer never see them. Every finding any party writes or judges clears the consequence floor (`finding-floor.md`: a finding names the failure it prevents — what goes wrong, for whom, how it is noticed — or it is not written; test files in scope only for failure modes); a finding whose whole remedy is comment text is a comment correction the orchestrator applies in place and commits at both judgment points, never a task; one-edit fixes fold into a single `corrections` task per pass; a consolidation task that routes call sites through a helper converts the measured complete set. The boundary folds what the finder confirms and empties the bank on every path — nothing carries across a phase and nothing seeds the analysis loop; quick-fix plans never take the boundary.
10. **Review** (`workflow-review-process`): Two detection layers, one routing. Per-task verifiers read — never execute — and report only what is wrong: each finding names its failure, its scope (in/out of the delivered change-set) and its blast radius (contained/spreading); a criterion reading cannot settle is quoted under `UNSETTLED` with what would have to run, never judged either way, and the orchestrator collects them for the pass. After the batches the executing pass runs, once per review cycle: `workflow-review-change-set-verifier` agents, one per numbered specification section plus one over the test surface (adjacent sections merged from the lowest numbers up to cap the total at five; a document with no numbered sections is one section, slug `specification`, and a quick-fix's scoping document is that section alone), hold the whole change-set against the specification's intent — the gaps between tasks are theirs — under project-supplied execution rules (the declared linter names, each run the project's own way, the build the conventions name, a single package's tests by the project's own command to confirm a suspected defect, a disposable dependency only where the conventions say how; never the suite, never a command the conventions do not describe), measure the unsettled criteria (`MEASURED` holds/fails — a fail is a finding — or `NOT MEASURED` with the reason), clear the shared `finding-floor.md`, write one `change-set-c{N}-{slug}.md` per section per cycle carrying a coverage map of what was checked and found sound, and leave the tree as they found it — the orchestrator checks `git status` after the pass and stops over dirt outside `.workflows/`, never reverting blind — then reconciles measured/not-measured across this cycle's section files into the cache's `not-measured.txt`. Prep runs both streams through one pipeline — assessor (validity, standards, remedy: a comment remedy standing in for a code defect is re-aimed at the code and its radius re-read), guards (inventory first, `depends` verdicts), relationships (the whole set at once), one synthesis — that collapses collisions and routes: nothing wrong → discarded with reasons; in-scope and contained → `do-now`, applied in-session (batched appliers, a whole-diff fix-verifier running the suite, one confined commit) — a blocking issue with a contained remedy among them, carrying `blocking` and reported as corrected; in-scope and spreading → `replan`, which **fails the review**; out-of-scope → banked durably on the manifest (`out_of_scope`), decided before the review closes on every path that closes one — filed or dropped, never auto-filed and never silently discarded. The verdict is derived from the `replan` set alone — pass or fail, binary. A finding whose entire remedy is comment text never blocks. The report's Specification Compliance is the coverage maps verbatim, Plan Completion names the not-measured criteria with their task suffixes, and the presentation counts `not_measured`. Aggregation reads `BLOCKING ISSUES`, never `STATUS`; coverage (`reviewed_tasks`) is pushed per batch; crash-resume after verification re-enters with nothing to dispatch (`reviewed_tasks` + report existence pick the branch; the aggregation re-reads the reports, the cycle's section files discriminate what the pass re-dispatches), never re-verifying.

## Skill Architecture

Skills organised in tiers:

**Entry skill** (`workflow-start`): the sole user-invocable entry. Shows all work; routes new work into discovery and existing work into the per-type `workflow-continue-*` skills. Also hosts the inbox pickup — a **working set** (multi-select promotion, single-type-gated) with an `.archived` lifecycle (archive · restore · delete). Hosts the full Step 0, run once: `engine boot` (migrations + knowledge check + bulk index + compact in one call), then the walkthrough offer, the session-label prompt, the gate-surface prompt, the knowledge gate and the baseline judgment — the teaching first, the setup gates after, each explaining itself where it lands.

**Discovery** (`workflow-discovery`): model-only (`user-invocable: false`). ### Phase Entry Skill Routing

Phase entry skills (`workflow-*-entry`) receive positional arguments: `$0` = work_type, `$1` = work_unit, `$2` = topic (optional) — no exceptions. Topic resolution: `topic = $2 || (wt !== 'epic' ? $1 : null)`.

**With topic** (feature/bugfix always; epic when caller provides it):
- Check manifest phase status → new entry (bootstrap questions) / resume / reopen
- No discovery needed — topic is already determined

**Without topic** (epic only — scoped path):
- Run discovery scoped to work_unit → analysis/selection flow → determine topic
- Only used by discussion and specification (research also, but simpler — just asks seed questions)
- Planning, implementation, review always receive a topic

## Key Conventions

**Work types and work units**: *Work type* = one of five pipeline shapes: epic, feature, bugfix, quick-fix, cross-cutting. *Work unit* = named instance of a work type (e.g., "auth-flow" is a feature work unit, "payments-overhaul" an epic work unit). Each work unit gets its own directory under `.workflows/` and its own `manifest.json`.

- **Epic**: Multi-topic, multi-session, phase-centric (Discovery → Research (opt.) → Experiment (opt.) → Discussion → Specification → Planning → Implementation → Review)
- **Feature**: Single-topic, single-session, linear (Discovery → Research (opt.) → Experiment (opt.) → Discussion → Specification → Planning → Implementation → Review)
- **Bugfix**: Single-topic, investigation-centric (Discovery → Investigation → Specification → Planning → Implementation → Review)
- **Quick-fix**: Single-topic, scoping-centric (Discovery → Scoping → Implementation → Review)
- **Cross-cutting**: Single-topic, project-level (Discovery → Research (opt.) → Experiment (opt.) → Discussion → Specification — terminal)

**Topics**: *Topic* = the item within a phase. For feature/bugfix/quick-fix, topic name equals work unit name. For epic, topics are distinct from the work unit name. All work types use per-topic manifest items (unified structure).

Work-unit-first directory structure with uniform `{topic}` in all paths (`{topic}` = `{work_unit}` for feature/bugfix/quick-fix).

- Project manifest: `.workflows/manifest.json` (work unit registry + project defaults)
- Manifest: `.workflows/{work_unit}/manifest.json`
- Discovery sessions: `.workflows/{work_unit}/discovery/sessions/session-NNN.md`
- Discovery briefs: `.workflows/{work_unit}/discovery/briefs/{topic}.md` (per-topic views synthesised at the epic harvest — soft decisions, rejected paths, open questions — and written by the discovery-gap analysis's approval gate for every candidate it approves, shaped from the gap instead: the gap, the artifacts it was read out of, why it matters, open questions; regenerable, never records; pointed to by the discovery item's `brief_path`, read in full by the topic's research/experiment/discussion and tracked via `brief_incorporated`; a brief written or regenerated over in-flight downstream work sets `reconcile_needed`; a first-written brief for an existing topic gets its pointer backfilled at the harvest)
- Research: `.workflows/{work_unit}/research/`
- Experiment: `.workflows/{work_unit}/experiment/{topic}/{id}-{slug}/` (per-record directory — `problem.md`, `design.md` frozen at the confirm, `report.md` with append-only corrections, `data/`; sub-experiments nest inside the parent's directory; the series itself lives on the manifest at `phases.experiment.items.{topic}.experiments`)
- Discussion: `.workflows/{work_unit}/discussion/{topic}.md` (flat file)
- Investigation: `.workflows/{work_unit}/investigation/{topic}.md` (flat file)
- Specification: `.workflows/{work_unit}/specification/{topic}/specification.md`
- Planning: `.workflows/{work_unit}/planning/{topic}/planning.md` (+ `phase-{N}-tasks.md` + task files in output format)
- Implementation: `.workflows/{work_unit}/implementation/{topic}/`
- Review: `.workflows/{work_unit}/review/{topic}/report.md`
- State: `.workflows/{work_unit}/.state/` (per-work-unit analysis files)
- Global state: `.workflows/.state/` (migrations, environment-setup.md)
- Cache: `.workflows/.cache/{work_unit}/{phase}/{topic}/` (scratch files for any phase; gitignored via `.workflows/.gitignore`, purged when the work unit closes — complete/cancel/absorb — and backfilled for already-closed units by migration 050). The cache root also holds two project-level stores that belong to no work unit: the session-label store, `.workflows/.cache/.session-labels/`, and the gate mod's sent record, `.workflows/.cache/.gates/`
- Imports: `.workflows/{work_unit}/imports/` (user-shared reference material — one home, whatever the phase and whatever the file type. Landed at discovery's opener by `workunit create --import` and mid-session by `engine workunit import {wu} <path>… --from <origin>`, one self-committing call behind the shared `landing-shared-files.md`; tracked via the `imports[]` manifest field, each entry `{path, imported_at, origin}` with `origin` **required** — `discovery` or `{phase}/{topic}` with the phase one of `research`, `discussion`, `investigation` (`roadmap` is the product layer's own origin, carried by `roadmap.imports[]` and refused by `workunit import`). A markdown-ish source (`.md`, `.markdown`, `.txt`, `.text`, or no extension) lands as `{stem}.md` and is KB-indexed; any other source keeps its extension, lowercased, and is tracked on the manifest but never indexed. A document links its import by relative path — `../imports/{name}` from a phase file, `../../imports/{name}` from a specification or a discovery session log — with the link text saying what the file shows and the prose around it the searchable record; absorb rewrites, in the documents it moved, the links its own dedupe rename broke (`renamed_imports`), promote *copies* into the cross-cutting unit every import a moved document links and every import a moved discussion attached, and topic cancel/reactivate never touch imports — the material is the work unit's)
- Seeds: `.workflows/{work_unit}/seeds/` (the work unit's **origin** — the promoted inbox item, or several items of one type, *moved* here at the work-type commit; tracked via the `seeds[]` manifest field, one entry per item, each with a `source: inbox:{idea|bug|quickfix}` tag; KB-indexed under the `seeds` phase. Distinct from imports: the trigger the work was spawned from, not reference material it pulled in)
- Baseline: `.workflows/.baseline/{area}.md` (project-level brownfield assessment docs — no work unit; session material under `.workflows/.baseline/.state/`)
- Roadmap: `.workflows/.roadmap/` (project-level product layer — no work unit; `sessions/session-NNN.md` product session logs, `imports/` the project-level imports home; the map itself lives on the project manifest's `roadmap` node; `roadmap` is a reserved work-unit name; `engine commit --roadmap` is the session cadence commit)
- Inbox: `.workflows/.inbox/{ideas,bugs,quickfixes}/` (pre-pipeline capture. The inbox pickup is a **working set** — select one or more items *of a single type* to promote, moving them into the work unit's `seeds/`; or archive any selection, regardless of type, to `.archived/{type}/`. The `.archived/` store is live: archived items can be restored to the inbox or hard-deleted (`git rm`) from the archived sub-view. It holds *declined* items, never promoted ones)

**Work unit lifecycle**: Each work unit has a `status` field in its manifest tracking lifecycle state:
- `in-progress` — actively being worked on (default on creation)
- `completed` — pipeline finished (set automatically on pipeline completion, or manually via manage menu)
- `cancelled` — abandoned (set manually via manage menu, or from inside the session working the unit — a linear work type's topic is its work unit, so the same `cancelling-the-topic.md` reference runs `workunit cancel`, renders the receipt, and stops there)

Discovery filters by status — active work by default, with options to view completed/cancelled or manage lifecycle. Work units can be reactivated.

**Feature-to-epic pivot**: Convert features to epics via manage menu (`p`/`pivot`). After pivot, continue immediately as an epic or return to the previous view.

**Feature absorption**: Merge a feature into an in-progress epic via manage menu (`a`/`absorb`). Moves the feature's discussion and research into the epic as a new topic named after the feature — a clash re-derived, never asked — then deletes the feature. Guarded: requires a discussion, no spec-or-beyond, at least one in-progress epic. Git history serves as provenance.

**Epic topic cancellation**: Cancel/reactivate topics via the workflow-continue-epic menu (`a`/`cancel`, `e`/`reactivate`) — one unit per stage, never a phase item, and nothing rolls through a stage boundary. `topic cancel {wu} discovery {topic}` takes the map row with everything under its name: every non-terminal research/discussion item (a `triaged` stub included) stashes `previous_status` and reads `cancelled`; every evidence wait releases first, so the holder carries `reconcile_needed: "experiment"` inertly until a reactivate; every open experiment record ends `abandoned` with `reason: "topic cancelled"` and the series settles; every `proposed` grouping sourcing the discussion is discarded; and the map row takes `cancelled: true` — the marker a never-started topic is cancelled by, read first by `computeTopicLifecycle` (the every-attempted-item-cancelled reading stays as the legacy fallback) — with `order` stashed to `previous_order`. `topic cancel {wu} specification {spec}` takes the specification and its same-named plan and frees the source discussions to be regrouped or cancelled. What a cancel takes is one derivation (`cancelPlan`: items, open records, proposed discards) the transactions execute and `render cancel-gate` renders; a cancel that would take nothing refuses (no live item and no map row; a status-less specification). Locks: a topic whose discussion a **started** specification (`in-progress`/`completed` — `specIsStarted`; a `proposed` grouping never locks, a status-less item is inert) sources is refused (cancel the specification first), and a specification with an implementation or review item of its name is refused — Delivery never cancels, code is fixed forward, and the work-unit cancel abandons the epic. The cancel menu lists every unit, a locked row keyless with its reason and a held one with its in-session age (a cue, never a lock; the laboratory and the plan count toward their unit's hold) — `a/cancel` shows whenever a unit exists, `e/reactivate` whenever one is cancelled, and a sub-view whose every row is locked opens on a statement over `b/back` alone; `render cancel-gate {wu}.{stage}.{name}` is the one confirm and names exactly what the cancel takes (experiments counted top-level, a split named with its parent); `render topic-receipt … --verb cancel|reactivate` addresses the unit. `topic reactivate {wu} {stage} {name}` restores the unit — the marker cleared, every cancelled item restored (a stash returns as the status; an item cancelled with none returns to never-attempted, `status: null` in `restored`), the order returned only while no live row holds the number, each restored `completed` artifact re-indexed. A specification's reactivate is refused while a source topic is cancelled (reactivate the topic first) or another started specification has since taken a source (regroup at the specification entry) — `specReactivateLocks`, the one derivation the refusal and the reactivate menu's locked rows share — and discards every `proposed` grouping over a returning source (`discarded` on the response). The lifecycle fallback for a map-less topic reads cancelled when every attempted item is terminal and one is cancelled. Cancelled items remain visible in state display but excluded from phase aggregation (`phaseStatus`), gating flags, next-phase-ready logic, and discussion/spec entry discovery; `topic triage` refuses a cancelled or dead-ended map row (the backstop for a peer closing the target between the landing's read and its write); a cancelled specification anchors nothing at the grouping analysis and its key stays reserved — the spec-entry gateway's DATA lists it under `cancelled_specifications:` with its sources, and the field surface refuses a `status` write onto any cancelled item and any `delete` of the item or its fields. Migration 058 restores legacy cancelled planning, implementation, and review items to their stash or to never-attempted — Delivery never cancels. Remove stays discovery's operation for never-started mistakes and duplicates. A session sitting inside a topic cancels it from within, without leaving for the menu — `workflow-shared/references/cancelling-the-topic.md`, hooked as a standing `## Cancelling the Topic` section on every phase processing skill's backbone but the laboratory's (a record has `abandon`): the stage resolves from the session's own phase (research/discussion → `discovery`, specification/planning → `specification`), the gate confirms, `topic cancel` runs, the receipt renders, and `/workflow-bridge {wu} {phase} none cancelled` lands the user on the epic menu with no phase banner; an implementation or review session refuses per R3 and names the work-unit cancel. Epic-only — other work types use work-unit-level cancellation since topic = work unit.

**Epic topic postpone**: Cancel says "not doing this"; postpone says "doing this later". `topic postpone {wu} {topic} --horizon "{h}"` takes cancel's Discovery unit — the map row with every research and discussion item under its name and the experiment series — and sends it to the product roadmap: every non-terminal item stashes `previous_status` and reads `postponed`, the map row takes `postponed: true` with `order` stashed to `previous_order`, the series is left exactly as it stands, and nothing on disk moves. The topic's knowledge-base chunks leave with it — its conclusions are on hold and retrieval inside the epic must not surface them — and return when it does. In the same transaction the roadmap item is **born** under the topic's name (`summary` the map row's, `origin: postpone:{wu}`, the node and the horizon created just-in-time) or, when the topic was pulled from the roadmap, its own item **re-waits** (the join deleted, the chosen horizon taken, its name and origin untouched); either way the item records `postponed_from: {work_unit, topic}` and gains the topic's brief, research, and discussion files as `sources`. One derivation (`postponePlan`) feeds the gate, the menu row, and the verb, and carries every lock: an already postponed or cancelled row, a dead-ended one (the roadmap holds what is still to do, so "later" over an answered question is a contradiction — reopen it first), a started specification sourcing the discussion (a topic past specification is past "not yet" — no cascade, and a `proposed` grouping never locks but is discarded), a non-terminal experiment record (a laboratory cannot run under a topic that has left, and abandoning it is the destructive act this exit avoids), and a roadmap item of the name that is not this topic's. Presence is a cue, never a lock. `postponed` is a terminal status, so aggregation, gating, next-phase readiness, sequencing, epic completion, and the gap analysis's input all pass a postponed unit by exactly as they pass a cancelled one; the field surface refuses a `status` write onto one and any `delete` of it or its fields; `topic triage` **accepts** a postponed row — a concern for a topic that waits is mail that waits with it. Four doors, one reference (`workflow-shared/references/postponing-the-topic.md`, whose horizon step is the shared `choosing-a-horizon.md`): the epic menu's `p/postpone` row over the postpone sub-view; the standing `## Postponing the Topic` section on the eight process skills, where the session's own topic commits first, closes its agents, and ends through `/workflow-bridge {wu} {phase} none postponed` (no banner — the receipt was the session's) while a sibling's returns to the interrupted turn; discovery's map operations, which log it under **Edits**; and the gap-analysis gate's `p/postpone` arm, which lands the candidate with its brief and postpones it in one turn. The return is the pull, never reactivate: `roadmap pull-forward` back into the epic that postponed the topic restores the unit (marker cleared, stashes returned, each restored `completed` artifact re-indexed, the join re-recorded, `--routing` naming nothing) — the epic menu's `f/forward` row over the pull-forward sub-view is that door, listing each postponed topic whose item still waits (one another epic has since taken is rowless) and closing on `render topic-receipt … --verb restore`; the product roadmap's own pull is the other. A pull landing anywhere else carries `prior: {work_unit, topic}` onto the receiving epic's map row — read in full by `workflow-shared/references/read-prior-record.md` at that topic's research or discussion initialisation (the brief, the research and discussion files, and both triage queues of the prior topic), entering as soft decisions, rejected paths, and open questions the phase relitigates; the concerns left in that topic's old queue are open questions in that record, not mail to deliver — one whose ask still applies seeds this phase as the brief's questions do (a `pending` subtopic on the Discussion Map, an open thread on the register at origin `brief`), one that no longer applies takes a line in the phase's opening context — and the prior epic's files are its record: never moved, edited, or drained, nothing copied, nothing raised, and its queue never absorbed. `roadmap remove` over a `postponed_from` item cancels the epic's row in the same transaction — "actually never" has one door — and `topic cancel`/`reactivate` refuse a postponed row naming the pull. Epic-only, as cancel is. Design: `design/topic-postpone.md`.

**Epic soft gates**: Forward navigation between epic phases warns via `render epic-soft-gate` (empty on pass). The specification row counts the discussions still in progress; the planning and implementation rows read the build order and name the topics sitting ahead of the selection that are still unplanned/unbuilt. Informational, not blocking — system recovers via re-analysis if user proceeds early. Three entries are the deliberate exceptions, each hard-blocking on an unsettled upstream record: specification entry over a source discussion still open — in flight, or opened by the gap exit and not yet started (see Workflow Phases #7) — a spec cannot be reliably built from a record still open; discussion entry over outstanding research on the topic (see Workflow Phases #4) — research feeds discussion, so it lands first; and planning entry over an unsettled specification (see Workflow Phases #8) — a plan is built from a settled record.

**Staleness hops**: When a phase item's upstream input moves — at `topic reopen`, a triage landing, a spec-side `sources stale` (a discussion document amended in place during specification, no lifecycle transition), or a top-level `experiment conclude` (evidence arriving after a decision must surface before the record is trusted), never the later re-completion — the engine flags the downstream neighbour one hop away (`transitions.cjs flagDownstream`): the next pipeline phase's same-named `completed` item gets `reconcile_needed = <upstream phase>` (terminal states skipped, an existing flag never clobbered; the derived experiment slot is walked past unconditionally — a flag must land where an entry flow can clear it, and the series item has none; the hop out of research also flags an `in-progress` discussion — held at entry until the research lands, its conclusion held meanwhile by the derived research wait if a session already sits in it); a discussion's or investigation's downstream is every spec item naming it in `sources` (reverse join), whose `incorporated` rows also flip to `stale` until the spec's own reconciliation re-incorporates them (`stale` blocks spec sign-off alongside `pending`). Entry skills surface and clear the flag via `workflow-shared/references/reconcile-advisory.md` (value-keyed branches; the `research` branch reads the research item's status to tell landed from closed — the entry gate holds the discussion shut while the research is outstanding, so the branch meets a `completed` research, whose file it reads in full, or a closed lineage — and clears the flag either way; research a peer parked again between the door and the read holds it); a research or discussion session already inside meets a landed upstream through the same reference — its loop's check (after the triage check) and its close (before the wait gate) read the item's flag, and act on `research` only once the research item is `completed` (outstanding research is the wait gate's business) and on `experiment` always, the read put to the user before the conversation moves on — and `topic complete` refuses a research or discussion item carrying an unread `research`/`experiment` flag (the brief flag `true` and every other phase's flag stay entry-time advisories); for the linear work types `computeNextPhase` routes back to the earliest phase whose input moved (`input moved — reconcile`) — a flagged item, or a completed specification whose source rows are not `incorporated`, which the flag never reaches because the staling needs no reopen — so the bridge never reads `done` past a record still in motion; epic surfaces cue flagged items per-item (`· input moved`).

**Build order (epics)**: one soft execution sequence over an epic's live specification topics — `order` on `phases.specification.items.{topic}`, joined by name into planning and implementation. Born at the grouping analysis (riding the reconcile's `manifest apply`; the unify branch assigns too), refreshed by `workflow-continue-epic` Step 8 / the bridge's section D whenever `build_order_needs_sequencing` reports true (a live topic without an order, a non-contiguous or duplicated numbering, or `build_order_stale` — set by an epic spec's completion, cleared by sequencing), and re-derived manually via the epic menu's `o/order`. Advisory everywhere: it sorts the dashboard trees, the spec-entry menu, and the epic menu's entries (phase outranks order in the recommendation), and feeds the planning/implementation soft gates — it never blocks. `engine build-order sequence` writes it (whole live set, contiguous 1..N, terminal statuses refused; live set = every spec item not cancelled/superseded/promoted, completed items keep their number). A spec cancel stashes the item's order as `previous_order`; reactivate restores it only while no live topic holds the number. A dep-blocked plan carries no implementation menu row — the ⚑ list, the tree cue, and `u/unblock` carry the state. Design: `design/build-order.md`.

**Discovery map (epics)**: Discovery builds a manifest-backed map at `phases.discovery.items.{topic}` that drives auto-routing for research and discussion. Each item carries a `source` provenance field recording how the topic landed on the map — one of `discovery`, `gap-analysis`, `direct-start`, `migration-seeded`, `legacy-split:{parent}`, `reroute:{origin}` (off-topic concern rerouted in from another topic, or a gap a specification's exit opened as a topic of its own), `roadmap` (a product-roadmap item pulled into the epic), or the historical `research-analysis:{parent}` / `research-split:{parent}` on existing maps (still rendered, still walked for the discussion-time parent read). Multi-source items are comma-accumulated (e.g. `discovery,gap-analysis`). A `legacy_split_state: in-progress` sentinel field is set by `workflow-legacy-research-split` while an apply runs — the success path deletes the sentinel-bearing source item, so a surviving sentinel marks a crashed apply (surfaced by detect as `stranded_sentinels`); items with this field set are excluded by `detect-trigger`. Map items have no `status` field — lifecycle (`fresh`, `researching`, `ready for discussion`, `discussing`, `decided`, `handled` (rendered as dead end — completed research with nothing to carry forward under its own name; set by the conclude gate's dead-end row or a map op, reversible), `cancelled` (the row's own `cancelled: true` marker, set by the epic menu's cancel; a legacy manifest cancelled per phase reads it through every attempted item being cancelled), `postponed` (the row's own `postponed: true` marker, set by any of the postpone's four doors; the cancel outranks it where both sit)) is computed at render time by joining the discovery item against per-phase items. Removal during an discovery session hard-deletes the item and adds its name to a *dismissed list* so the analysis won't auto-re-add it (a "show dismissed" recovery option is available in any discovery session). Hard-delete is only allowed for items with no per-phase work; once research or discussion items exist, the map item is preserved as historical anchor. Auto-routing operates at the map-item level — research vs discussion is determined by the item's `routing` field (initial intent) overlaid with whichever per-phase items actually exist. The map gates the **birth** of a topic's research or discussion item: `topic start` refuses a phase the map's next action does not name (an in-progress item resumes; a discussion's birth is held for its outstanding research; a parked research stub starts from its menu row), the epic menu carries **one row per topic** — outstanding research (in-progress or parked) is that row for a fresh or discussing topic, whose discussion is held at entry until it lands (a discussion a live session still holds keeps a second row beneath it, struck through — a blocked item is rowless unless a session holds it), and a decided topic, which carries no row of its own, gets a research row when research is reopened or parked beneath it — and the `d`/`r` free-text doors refuse any name already on the map via `render direct-entry-gate`, outstanding research naming itself at either door — the menu row is the way in. A research/discussion item may carry `status: triaged` — a rerouted concern parked on an unstarted topic via `engine topic triage`; it renders as fresh with a `triage waiting` cue, is excluded from phase aggregation, and exits only via `topic start` (migration 052 repairs legacy phantom in-progress stubs). The cue reads the queue, not the status: a landing that reopened a concluded topic leaves the item `in-progress` with files in its queue, and the epic tree row and its continue/start rows carry `triage waiting` until the drain empties it. The single-topic types carry the same cue on their start-menu row, continue dashboard, and pick list (`triage_phases` on the unit entry).

**State ownership**: workflow state is engine-owned — durable state in the work-unit manifest, ephemeral session machinery in per-topic `.workflows/.cache/{wu}/{phase}/{topic}/state.json` (colocated with the content it describes; deleting a topic's cache dir is a complete cleanse). Frontmatter is never written or read as state; the sole exception is local-markdown's task files (the format's backend). Migration 051 translates pre-programme frontmatter state forward.

**Commit door**: every engine-made commit routes through `domain/commit.cjs` and is **confined** — it names the paths its action wrote and commits exactly those (`-- <paths>`; boot's untracking of the knowledge directory commits HEAD without them, built in a scratch index) under a process-wide commit lock, so a peer session's dirty or staged files are never swept up under someone else's message. Workflow artifacts commit by layout-derived scopes: `--topic {phase}/{topic}` (one topic's artifacts + the work-unit manifest, `--sweep` when the commit is over a topic this session is not working), `--discovery` (session logs + briefs + manifest), `--plan {topic}` (the planning topic's directory, both manifests, and the plan's declared `storage_paths`). Code has no layout, so `commit --paths <file>… -m msg --for {wu} {implementation|review}/{topic}` takes Claude-declared paths — validated (in-project, literal, never `.workflows/`), confined, and answered with `left_dirty` so a forgotten path comes back. Deliberately still work-unit-wide: the spec-entry grouping/reconcile commits, the shared analysis commits, and the work-unit lifecycle transactions (create, cancel, pivot, absorb).

**Presence**: per-topic session heartbeat, cache-resident (`.workflows/.cache/{wu}/{phase}/{topic}/presence`, gitignored) — awareness, never mutual exclusion. Every phase a session sits in carries one — research, experiment, discussion, investigation, scoping, specification, planning, implementation, review — except discovery, which `discovery-session open` already serialises to one session per epic. **Beats are mechanical and the prose never mentions them**: the engine stamps the heartbeat as a side effect of the verbs a session already runs on its own topic (`commit --topic` on a live item, `topic queue`, `topic start`/`absorb`, the agent-store verbs, the experiment verbs — `create --from` beats the spawning conversation, `create --parent`/`advance`/`approve` the laboratory's own topic — `workunit import --from {phase}/{topic}` (refused outright for a missing item, silent on a terminal one; a bare `discovery` origin beats nothing), `commit --paths … --for`, and the code gate's empty render — claiming the slot is the same act as reading it); `topic complete` *clears*, as do a top-level `experiment conclude`/`abandon` (the record's close is the laboratory's release) and any `commit --topic` on a terminal item, so the close is the release; `topic cancel` clears the calling session's own row on each item it took and a peer's never — the cancel is reachable from inside the conversation it closes; `--sweep` suppresses both on a commit made over a topic this session is not working; and no field write beats at all — a three-segment `manifest set` is frequently one phase's session writing another's item. `scan` answers one verdict per row — `held` (owning pid + start time verified alive, however long idle; a record with no identity is never held) — plus `held_sources`, the research and discussion rows alone; a row's `age_seconds` is shown as "last active {age} ago" wherever a hold is named and never judged; work-unit-less it walks the whole project. Consumers: the epic view strikes through held topics, skips them as recommendations, confirm-gates entering one, and keeps a blocked item's struck row only while a session holds it; the **code gate** at the implementation and review entry skills reads the project-wide scan (one code session per checkout — the tree and the index do not partition); analysis dispatch and the spec-entry grouping analysis defer while a source session is held; the conclude sweep leaves a held row's dirt alone; the spec-side resolution flow checks the target discussion before editing its document in place. The exit sweep is `presence cleanup`, run from a settings-level SessionEnd hook the engine installs in the project's committed `.claude/settings.json` at every boot, unconditionally (a SessionEnd hook declared in skill frontmatter never fires): it drops every row the ending session owns, by session id, on the exits that keep the process alive (`/clear`, `/logout`) — rows that would otherwise read `held` until the process exits; a dead process's row reads unheld through the pid check regardless, and a later conversation in the same process owns its predecessor's row through the pid arm. Design: `design/concurrent-phases.md`.

**Session labels**: opt-in tmux rename showing where a session is working (`{original} · {wu} · {phase} · {topic}`, topic collapsed when it equals the wu). Every place labels itself on arrival — leaving a place is never an event: `engine session label {wu} {phase} {topic}` is called by every process skill at Step 0 and by discovery at its run step; the navigation skills (`workflow-continue-*`) and the bridge call `engine session label {wu}` — the work unit alone — on arrival; the roadmap and the baseline label their own identity (`session label roadmap` / `session label baseline`, project-level places with no work unit); and workflow-start puts the original back through boot's `repair` pass, which restores this session's own label as well as a stranded one. `engine session cleanup` restores the original name from the settings-level SessionEnd hook the engine installs in the project's committed `.claude/settings.json` — the same hook that runs `presence cleanup`; a SessionEnd hook declared in skill frontmatter never fires, so no skill declares one (conventions lint check 18 forbids it). A resumed session gets its label back: every landed label records the session's **position** — `{name, phase, topic, at}` at `.workflows/.cache/.session-labels/positions/{session_id}.json`, keyed by Claude session id — which outlives the session (`cleanup` leaves it), and `engine session resume` re-applies it from the settings-level SessionStart hook (`matcher: "resume"`, fired on `claude --resume`; a SessionStart hook's stdout is injected into the resumed conversation as context, so the verb answers on stderr). A position leaves three ways: `repair` drops the calling session's own when it restores its own label (the start menu is no position; a dead owner's stays for its resume), `resume` drops one whose work unit or phase is gone, and `repair` prunes any older than 30 days — Claude Code's own session retention — whatever the opt-in. Presence and session labels are separate domains sharing only the SessionEnd hook: presence verbs never touch labels. Opt-in is the project manifest's `defaults.tmux_labels` boolean — absent means never asked; no system config, no migration, every project re-asks on its next `/workflow-start` (the prose-test harness stamps `tmux_labels: false` into every world, so a walk never labels the developer's terminal). `engine session label-config <true|false>` records it, syncs the hooks (`session cleanup` and `session resume` present iff `true`, `presence cleanup` always), and commits the project manifest confined — the settings file alongside it only when the sync changed it (answering `no` on a project whose boot already installed `presence cleanup` commits the manifest alone). Boot reports the state as `tmux_labels`, workflow-start's Step 0.3 asks once when the value is unset inside tmux, and every boot re-syncs the hooks — `presence cleanup` unconditionally, `session cleanup` and `session resume` per the opt-in; `session_hooks_installed` when the file changed — alongside the `repair` pass (`label_repaired`) — the start menu's own restore, and the stranded-label backstop for the first session after opt-in (Claude Code snapshots hooks at startup, so a settings hook takes effect from the next session), for crashes, and for a tmux server dying. Always a no-op outside tmux, on any tmux error, or with the feature off; a manual rename is adopted, never clobbered. Original names stash in the checkout's cache at `.workflows/.cache/.session-labels/` (keyed by tmux socket + session id), so no other checkout's engine ever reads a record; a label another checkout applied reads here as the user's own name.

**Gate surface**: opt-in per project for the `workflow-gates` mod (`skills/workflow-gates/`, its own `.claude-plugin/plugin.json`, loaded as `workflow-gates@skills-dir`), which reads the `=== GATE ===` payload off the Bash result a gate came back on and draws the menu's rows as buttons above the prompt, the prose unchanged: a click on a row picks it (its answer goes into the prompt box), and a second click on that row, or Enter, sends it — framed by Claude Code as the plugin's message. While any surface but the terminal is attached (Remote Control) the menu stays text, and a surface that attaches after a gate was drawn does not get that gate; an Esc once the answered turn has called a tool, and `/clear`, leave the band empty. State is the project manifest's `defaults.gate_surface` boolean — absent means never asked; per project by nature, so no system config holds it and no migration carries it. The mod reads it at session start and announces itself (`WORKFLOWS_GATE_SURFACE=1`, which the engine's `GATE` sections key on) only on `true`, so setting it to `false` turns the buttons off from the next session start. `engine gate-surface config <true|false>` records it and commits the project manifest confined; `true` also sets `env.CLAUDE_CODE_ENABLE_FUNCTION_HOOKS` to `"1"` in the project's committed `.claude/settings.json` (every other key untouched; the settings-file read/write is the shared `domain/settings.cjs` the session hooks use too), committed alongside when it changed. A recorded `false` never touches the flag: it turns function hooks on for every plugin in the project, so it is never the engine's to remove. The read, the status and the record are the project opt-in mechanics (`domain/project-opt-in.cjs`) the session labels share. Boot reports the state as `gate_surface` (`on`/`off`/`prompt`), read inside the project lock its settings sync holds; workflow-start's Step 0.4 asks once when the value is unset; and every boot under a recorded `true` puts the flag back if it went. Claude Code reads settings at startup, so a clean yes ends that session with a restart instruction and the next session has the buttons. The engine emits every menu regardless, so a mod that is off, absent or broken degrades to the text menu. The prose-test harness stamps `gate_surface: false` into every world beside `tmux_labels: false`, so a walk never meets the question.

## Migrations

Migrations keep workflow files in sync with current system design (run via `engine boot` in Step 0 of `workflow-start`).

**How it works:**
- `skills/workflow-migrate/scripts/migrate.cjs` (Node) runs every script in `skills/workflow-migrate/scripts/migrations/` — both the frozen `*.sh` fleet and modern `*.cjs` migrations — in one strict numeric-prefix ordering
- Each migration is idempotent — safe to run multiple times
- Progress tracked in `.workflows/.state/migrations`: numeric-only IDs, one per line, extension-independent. An ID is recorded only after its migration completes; any failure aborts the whole run without recording (boot treats a non-zero exit as fatal — migrations must never half-run silently). Whenever no document changed the ledger is the only dirt a run can leave, so boot commits it itself (`chore: record workflow migrations`) — the line this run recorded, or one an earlier boot stranded; when documents did change, the ledger rides the skill's reviewed migration commit

**Two migration formats:**
- **`*.sh` — the frozen fleet (001–046).** Shipped and already run by real installs; treat as immutable. Edit only to harden a failure path, **never** to change semantics — fix forward with a new numbered `.cjs` migration instead. The orchestrator sources each in a spawned bash with `report_update`/`report_skip` helpers, `PROJECT_DIR` pinned to `.`, cwd = project root, under `set -eo pipefail` (`return 0` semantics preserved).
- **`*.cjs` — all new migrations.** A `.cjs` migration is a module exporting `id`, `description`, and a `run` function, executed in-process:
  ```js
  module.exports = {
    id: '050',
    description: 'short summary',
    info: 'optional — what the migration does, project-agnostic',
    run({ projectDir, reportUpdate, reportSkip }) { /* ...; may return { verify: '…' } */ },
  };
  ```
  Read/write files under `path.join(projectDir, '.workflows')` (`projectDir` is always `.`). Signal outcome only through `reportUpdate()` / `reportSkip()` (display counters — call `reportUpdate()` once per changed unit); never write to stdout. A thrown error aborts the run; if a migration should instead degrade to a skip on unexpected input, catch internally and `reportSkip()`.

  **Verification addenda** (optional): when a migration transforms judgment-written content its code can only exact-match, export `info` (what the migration does, any project) and have `run()` return `{ verify: '…' }` — natural-language instructions for what to check in this project, returned on skip paths too (a skip can be a false negative: content the parser didn't recognise). Addenda from migrations executed this boot ride the boot response (`migrations.verify`); workflow-start Step 0.1 performs the checks with judgment before the migration confirm gate and folds fixes into the migration commit. Addenda fire once — never again for a recorded migration.

**Adding a new migration:**
1. Create `skills/workflow-migrate/scripts/migrations/NNN-description.cjs` (next number after the highest existing)
2. It runs automatically in numeric order; once its ID is in the log it never runs again

Migration `038-add-inception-phase.sh` seeds the phase for existing in-progress epics (`040-rename-inception-to-discovery.sh` then renames it to `discovery`) so legacy work units pick up the discovery map without manual intervention.

**Critical: Migrations must not use `engine manifest`**

Migrations are point-in-time snapshots. The engine's field surface validates against the current schema, which changes over time — a migration using it today may break silently later. Always read/write `manifest.json` directly (`node`/`fs` in `.cjs`; `node`/`jq` in the frozen `.sh` fleet).

**Bash 3.2 compatibility** (frozen `.sh` fleet only): the shipped bash migrations must run under stock macOS `/bin/bash` 3.2 — avoid `mapfile`/`readarray`, `declare -A`, `local -n` (all bash 4+). New `.cjs` migrations run under Node and are exempt.

**Testing migrations:**

Every migration has a matching test suite.

*New `.cjs` migrations* — a node:test suite at `tests/scripts/test-migration-NNN.cjs`, registered in `package.json`'s `test` script (runs under `npm test`). `require` the migration module and drive `run({ projectDir, reportUpdate, reportSkip })` directly against a temp `projectDir`. Follow the sibling suites (`test-migration-047/048/049.cjs`): `describe`/`it`, `node:assert`, per-test `setup`/`teardown` with a `mkdtemp` dir, counting `reportUpdate`/`reportSkip` stubs. Cover at minimum happy path, skip/no-op, idempotency (run twice), content preservation, and every defensive guard. The Node orchestrator itself is covered by `tests/scripts/test-migration-orchestrator.cjs` (mixed `.sh`/`.cjs` ordering, legacy tracking-log compatibility, failure-aborts-without-recording, the `.sh` path under stock `/bin/bash` 3.2, `PROJECT_DIR` pinning).

*Frozen `.sh` fleet* — the existing `tests/scripts/test-migration-NNN.sh` suites (run under `npm run test:migrations`) stay as-is. Their harness: `set -euo pipefail`, `PASS`/`FAIL` counters, `report_update`/`report_skip` stubs, an `assert_eq` function, `setup`/`teardown` with a temp dir. Conventions:
- **Invocation**: `source "$MIGRATION"` (the fleet uses `return 0`).
- **Isolation**: each test function calls `setup` at the start and `teardown` at the end. No shared state.
- **Assertions**: only `assert_eq` (`label`, `expected`, `actual`). File exists → `assert_eq "desc" "true" "$([ -f "$path" ] && echo true || echo false)"`; content match → `... "$(echo "$content" | grep -q 'pattern' && echo true || echo false)"`; fixed-string → `grep -qF`.
- **grep with leading dashes**: always use `--` before patterns starting with `-`.
- **Test naming**: functions prefixed `test_`, comments `# --- Test N: Description ---`.
- **Summary**: `echo "Results: $PASS passed, $FAIL failed"` then `[ "$FAIL" -eq 0 ] || exit 1`.
- **Coverage**: happy path, skip/no-op, idempotency (run twice), and content preservation where applicable.

## Manifest Field Surface

`engine manifest` (`node .claude/skills/workflow-engine/scripts/engine.cjs manifest <command> …`, implemented in `skills/workflow-engine/scripts/domain/fields.cjs`) is the single source of truth for all workflow state. Dot-path syntax: `command <work-unit>[.<phase>[.<topic>]] [field] [value]`. Segment count determines access level (1 = work unit, 2 = phase, 3 = topic). Reserved prefix `project` routes to project manifest — e.g., `get project.defaults.plan_format`. Reads (`get`, `exists`, `list`, `key-of`, `resolve`) print bare stdout; mutations (`set`, `push`, `pull`, `delete`, `apply`) answer with the engine's one-line JSON response; `set` takes one positional pair or a uniform `<field>=<value>` batch (never mixed) in one locked write, and `apply <work-unit> --file <ops.json>` batches set/delete ops across dotpaths in one atomic write. The engine `SKILL.md` is the authoritative API reference. Contract suite: `tests/scripts/test-engine-manifest.sh`.

**Project defaults cascade**: `project.defaults` → topic level. Project defaults are suggestions (user confirms or overrides). Topic level records the actual value in use. No phase-level storage for settings like `plan_format`, `project_skills`, or `linters`.

**Shell quoting**: Always single-quote values that zsh would interpret — `'[]'`, `'[...]'`, `'{}'`, `'~'`. Bare `[]` is a glob pattern (causes `no matches found` errors) and bare `~` expands to the home directory.

- `npm run typecheck:mod` / `npm run test:mod` — the gate mod's types against Claude Code's mod API declarations, and its suite under `claude plugin test`; owed for any change under `skills/workflow-gates*/`. The declarations are gitignored: `npm run mod:types` fetches them before the first `typecheck:mod`.

Add or update a test alongside any change to engine scripts, adapters, migrations, the gate mod, or `src/knowledge/`.

**The engine's in-process entry**: `engine.run(argv, {cwd, env, stdin})` (exported by `skills/workflow-engine/scripts/engine.cjs`, covered by `tests/scripts/test-engine-run.cjs`) is the door a node harness takes to drive the engine by argv — same argv, same `stdout`/`stderr`, same exit code as the CLI, without a process per call. The invocation is the caller's: the cwd is a parameter (never a `chdir` — refused inside a worker thread), the env keys are held for the call and restored exactly, the stdin is a string, and the display-width memo resolves per call. Spawning stays for the shell tiers (`test:cli`, `test:migrations`) and for the real CLI, whose door is `main`.

**The shared harness**: `tests/scripts/engine-harness.cjs` is where a node suite gets its engine runner and its git fixture — the in-process entry wrapped in one shape per answer the engine gives (`call` for the raw three parts, `ok`/`okSections` for a success, `refuses` for a refusal, `output` for the whole stdout), each taking the project directory, then argv, then the call's own environment overlay and stdin; plus `git`, `setupGitFixture`, `cleanupFixture`, and `stubbedEngine()` — the engine copied once per process into a temp skills tree beside a stub knowledge CLI, for the suites that assert on what the engine asked the store to do (`knowledgeCalls`). Its own contract is `tests/scripts/test-engine-harness.cjs`. A suite keeps a spawn only where the subject is the process: the real CLI's pipe and exit behaviour, a child that must run concurrently (a lock race), a script that is not the engine.

**Hermetic environment**: `tests/scripts/hermetic-env.cjs` pins the suite's world at require time — an empty `WORKFLOWS_CONFIG_DIR`, no `OPENAI_API_KEY`, no `WORKFLOWS_GATE_SURFACE`, git's global and system config at `/dev/null`, `WORKFLOWS_DISPLAY_WIDTH=65` — and every process a test spawns inherits it. **Every `tests/scripts/test-*.cjs` requires it first**; `recipeEnv()` in the prose harness composes its exported entries; the shell tiers export the same variables in their npm scripts. The invariant it holds: a test never reads the developer's config or credentials, never reaches an embedding provider — a knowledge store is built only where the test chose keyword-only or the stub provider in the project's config — and never renders a gate payload it did not announce itself (a session with the gate surface loaded announces it to every command it runs, and every golden pins the unannounced bytes). `tests/scripts/test-hermetic-env.cjs` guards the pins, lints the adoption, and indexes a document under the pinned environment to assert no store is built — nothing there configures one. A suite that fakes `$HOME` to reach a system config takes the override back off the environment it passes down (`test-engine-boot.cjs`, `test-knowledge-setup-forms.cjs`, `test-knowledge-cli.sh`).

**Display-width pinning**: the engine detects the terminal width at render time (`kernel/terminal.cjs`), and `CLAUDE_PID` reaches every test env — so the hermetic module pins `WORKFLOWS_DISPLAY_WIDTH=65` for every entry into the node suites, `npm test` and a direct `node --test <file>` alike, and `npm run test:cli` exports it for the shell suites. A golden regenerated from any of them encodes 65, never whatever pane happened to be open.

## Pipeline Simulation

`tests/scripts/test-pipeline-simulation.cjs` (under `npm test`) drives the engine CLI end-to-end, through its in-process entry, following the call sequences the skill prose prescribes — every work type's mainline plus the supported edges (reopen, supersession, cancel/reactivate, pivot, absorption, promotion, restarts) — auditing the whole state after every mutation: schema-valid manifests, no shadow roots, every derivation computes, every navigation gateway discovers and formats, render surfaces hold. It is the detector for silent state corruption — writes that succeed and only break a menu phases later.

**Any change to the workflows must update the simulation** — a new engine verb, a changed prose call sequence, a new phase ordering, a new manifest field: extend an existing scenario, add a new permutation, or re-pin changed expectations. A red simulation is the design speaking — decide deliberately whether the flow or the scenario is wrong, never paper over it. New permutations are cheap: a scenario is an ordered list of engine calls with assertions.

## Prose Tests

`tests/prose/` — end-to-end tests for the prose logic (design: `design/prose-tests.md`). A case is a directory under `tests/prose/cases/{case-id}/`: `case.json` (values code branches on: the required `entry`, deterministic `invariants`, scripted `answers` and/or a `conduct` description of the user, stub arming, `world: "claims"` for model-authored end states judged against stated claims), `fixture.md` + `fixture-state.cjs` (the starting world), `act.md` (the coarse instruction a walker agent follows through the real skills), `assert.md` (the expected path, seen only by the asserting agent), optional `assertion-state.cjs` (the world the walk should produce; absent = unchanged), and the two generated snapshots. What a snapshot cannot hold directly, a recipe declares in a **sidecar** the snapshot carries and `materialise` turns into real world state, never landing in the world itself: `.world-history.json` (layered commits), `.world-presence.json` (heartbeats a *peer* session holds — presence files are excluded from every snapshot as timing noise, so a fixture needing a peer's hold declares it here and it is stamped last so its last-active age reads freshest in the world; a row that omits `pid` is beaten as pid 1, which is what makes the peer read held and owned by nobody, and a declared `pid` is beaten as that process — a dead one on purpose reads unheld), `.world-dirt.json` (snapshot paths held out of the world's commits — a bare string for untracked, `{path, committed}` for modified over a committed version — written back after the last commit). Nothing is parsed and prose never shares a file with code. **A case starts where a session starts and stops where its claims can be answered**: `entry` must name `workflow-start`, a `workflow-*-entry` skill, `workflow-discovery`, or `workflow-roadmap` — never a navigation or processing skill, never a reference — because a walk begun mid-session lacks the context the prose was written for. A handoff is a fine ending (recorded actions are as deterministic as a world delta); what a case must never do is stop where only display claims remain, since text put on screen is evidenced by no hook. Claims that code can settle belong in `invariants` (`engine_before_write` — declared only where the walk writes, `calls_include`, `calls_exclude`, `calls_in_order` — whose entries may be `write:<path>` tokens standing for the path's *first* recorded write, ordering artifact creation against the calls around it), which run before the asserter and whose verdicts it cannot overturn. Shared pipeline stages live in `tests/prose/mainlines/`. Walks cost tokens — run on command via the `/prose-test` dev skill, never as part of a routine gate. The deterministic perimeter runs under `npm test`: corpus validation plus snapshot goldens — every snapshot must rebuild byte-identical from its recipe under the frozen clock, the rebuilds fanned out over a thread pool a core short of the machine and skipped per world by a **gitignored local cache** (`tests/prose/.cache/`) the verify maintains itself: a byte-identical rebuild records the recipe hash it ran under, a drift records nothing, and a hash the cache does not hold — or one an engine change has moved on from — costs a rebuild, never a skip. So a fresh clone's first run rebuilds the corpus in parallel, the run after it costs nothing, and no PR carries the bookkeeping. When an engine change moves a world, regenerate with `node tests/prose/run.cjs snap {case-id}` and land the snapshot diff in the same PR; never hand-edit a snapshot. Every review finding lands twice: the fix, and the case that would have caught it. At the end of a PR that touches skill prose, run `node tests/prose/run.cjs select --diff main` and suggest running the intersecting cases.

## Knowledge Base Subsystem

Retrieval-augmented store of completed workflow artifacts (research, discussion, investigation, specification — never experiment/planning/implementation/review), plus epic discovery **session logs** (indexed under a `discovery` phase — the running exploration record), seed material for early-phase context: user-shared `imports` (the markdown ones — any other file type is tracked on the manifest and never embedded) and the inbox-promoted `seeds` (the work unit's origin), the project **baseline** docs (`.workflows/.baseline/*.md`, reserved pseudo work-unit `baseline`), and the product **roadmap**'s session logs and imports (`.workflows/.roadmap/`, reserved identity `roadmap`, phase `roadmap`/`imports`). Every entry-point skill gates on knowledge base initialisation before any phase runs.

**Source vs bundle**: Source lives in `src/knowledge/` (multi-file Node.js — `index.js`, `store.js`, `chunker.js`, `embeddings.js`, `config.js`, `setup.js`, `setup-forms.js`, `providers/openai.js`, `providers/openai-engine.js`, `providers/openai-compatible.js`). Committed CLI at `skills/workflow-knowledge/scripts/knowledge.cjs` is a single-file esbuild bundle. AGNTC installs from git tags with no build step, so the bundle must be present and current at tag time.

**Building**: `npm run build` runs `node build/knowledge.build.js`, which esbuild-bundles `src/knowledge/index.js` into `skills/workflow-knowledge/scripts/knowledge.cjs`. Always rebuild after editing `src/knowledge/` and commit the bundle alongside the source change.

**Allowed tools**: Skills that invoke the CLI must declare `Bash(node .claude/skills/workflow-knowledge/scripts/knowledge.cjs)` in their frontmatter. SKILL.md is the authoritative API reference — read it before adding a new call site.

**Mandatory boot gate**: `engine boot` (Step 0 of `workflow-start`) runs `knowledge check` and, when ready, the bulk `knowledge index` — it indexes new and changed artifacts (compared by the content hash every chunk records), drops the chunks of identities positively known to be gone, and skips what compact prunes — then `knowledge compact` (progress-based decay); a failing bulk index or compact is its own boot warning, which `workflow-start` surfaces without stopping. A checkout that is set up (its local `config.json`) but has no store gets one built by that bulk index — `knowledge check` answers `buildable` — when this machine's config says how: a provider whose key resolves, or keyword-only chosen outright (a system config naming no provider, or a project config unsetting it — `setup --keyword-only` always pins `provider: null`); a missing or invalid system config, or a provider whose key cannot be resolved, never builds a keyword-only store in its place, and no write path — the single-file index included — creates a store the config does not say how to build. Every other `not-ready` response carries a `system_config` report (valid/absent/invalid + active provider/model, never secrets) and routes into `workflow-start`'s knowledge gate (`references/knowledge-gate.md`), which initialises the store conversationally via the non-interactive `knowledge setup` forms (`--from-system`, `--keyword-only`, `--provider ...`) and commits nothing — boot itself never sets a checkout up. API keys never transit chat or argv: they resolve from `$OPENAI_API_KEY` or `credentials.json`, written by the `--key-only` terminal detour or the interactive wizard (which remains human-only). The whole `.workflows/.knowledge/` directory is local to each checkout — setup is once per copy of the project, never committed: migration 060 ignores it, no engine commit stages it, and boot stops git tracking anything under it — one confined commit built from a scratch index, the files left on disk, refused while a merge, cherry-pick, revert or rebase is in progress — and keeps its three files (store, metadata, config) listed in the project-root `.worktreeinclude`, so a worktree Claude Code creates starts with a copy.

**Phase-completion indexing**: Processing skills invoke `knowledge index <path>` at phase completion to add the new artifact. Spec promotion and work-unit cancellation invoke `knowledge remove --work-unit ... [--phase ...] [--topic ...]` to clean up. Transient failures retry with backoff; a failure that outlasts them exits non-zero and lands in the transaction's `warnings`, and the bulk `knowledge index` at boot re-indexes what failed to index and drops what failed to remove. Corrections to a concluded specification follow `workflow-shared/references/correcting-historical-artifacts.md` — specification only, the golden record; other phase artifacts decay and are never corrected — in-place edit + corrigenda entry, then a single-file `knowledge index <path>` (replaces that file's chunks; the owning manifest is never touched). Two entries: another unit's completed spec is gated (`render correction-gate`); the working unit's own spec, defect found by a downstream phase (the planning phase designer, task designer, and task author, the executor's block, the consolidation finder, analysis, review synthesis), is corrected **silently** when the record settles the side or a defensible derivation (an honest technical call included) pins an open one — the corrigendum records the reasoning; code-wrong verdicts and product-intent gaps route back to the phase that found them — a staged proposal in Delivery, plan content or a decision landed in the owning discussion from planning or from the executor's block (the specification itself on a quick-fix) — never spec edits. (A spec still in its own phase differs: the spec resolution flow — construction or review — edits the owning source document and reindexes it single-file.)

**Stub mode**: When no embedding provider is configured, CLI runs in keyword-only mode (BM25). Treat as supported degraded mode, not broken state. `query` output prepends `[keyword-only mode — ...]` note.

**Tests**: `tests/scripts/test-knowledge-*.{cjs,sh}` cover the subsystem — store, chunker, embeddings, config, OpenAI provider, integration, retry, build, CLI surface. Node suites run under `npm test`, shell suites under `npm run test:cli`. The one test that reaches the real API, `tests/scripts/knowledge-openai-smoke.cjs`, sits outside the gate by name and by list and runs by hand with a key in the environment. Add a test alongside any `src/knowledge/` change.

**Project layout**: `.workflows/.knowledge/` (checkout-local and gitignored: `store.msp`, `metadata.json`, and the knowledge `config.json` setup writes), `~/.config/workflows/config.json` (system config — setup writes provider identity only; the tuning keys `similarity_threshold`, `decay_prune_below`, `decay_base_stability`, `decay_weights` are never written, only honoured as overrides in either config file, project over system, `null` unsetting a key; defaults live in `src/knowledge/config.js` `DEFAULTS`), `~/.config/workflows/credentials.json` (mode 0600, optional API key store).
