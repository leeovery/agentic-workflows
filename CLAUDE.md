# CLAUDE.md

Guidance for Claude Code working in this repo.

## Project Overview

Agentic Engineering Workflows for Claude Code. Installed via `npx agntc add leeovery/agentic-workflows`.

**This project authors the workflow system — it does not use it.** Never invoke workflow skills (`/workflow-start`, `/workflow-continue-*`, etc.) for work on this project. Edit skill files, references, and scripts directly. This CLAUDE.md is development documentation that does not ship with the product — installed projects get their own. Skills and agents must be self-contained — never rely on this file for runtime behaviour.

## Git Workflow

Always create a feature branch **before** the first commit. Never commit to main and move commits after. The only exception is when explicitly told to commit to main.

## Reviewing Work

`/review-work` is the standing review pass — run it when asked to review the work, check for regressions, or verify convention adherence. It dispatches one `workflow-reviewer` agent per dimension (`.claude/skills/review-work/references/dimensions.md`), verifies the findings, and lands the fixes. Where those fixes go depends on review state: commits onto a PR whose review is live, a new top-of-stack PR once a layer is signed off, folded into the owning PR while nothing has been reviewed yet.

## Ideas

Improvement ideas live in `ideas/`, indexed by `ideas/INDEX.md`.

The index holds **pending items only** — one table. **When you complete an idea, remove its row and delete its file in the same PR as the work**; git history is the record of what shipped. Shipping the fix and leaving the row in place is how the index stops being trustworthy; an entry that reads open when the work landed sends the next reader to re-do it. Status nuance on a still-pending idea (partial ship, audit notes) belongs in its index row.

## Workflow Phases

The phases group into three stages (the **three D's**), used as the top-level grouping in the epic dashboard (`workflow-continue-epic/references/epic-display-and-menu.md`): **Discovery** (Discovery, Research, Experiment, Discussion, Investigation) — explore and decide; **Definition** (Scoping, Specification, Planning) — specify and plan; **Delivery** (Implementation, Review) — build and verify. The dashboard renders each stage as a `── STAGE ──` divider with the phases beneath it.

1. **Discovery** (`workflow-discovery`): the universal **first phase** — every work type begins here. Confirm the work type, shape the outline, persist at the work-type commit, route into the pipeline. Two invocation modes dispatched at Step 0: **new** (from `workflow-start`, no work unit yet — decide the type via the universal detection core, then epic → initial topic sketch, feature/cross-cutting → research-vs-discussion routing, bugfix/quick-fix → brief intent capture; a **product-altitude** read — no single unit of work on the table — routes out to `/workflow-roadmap genesis` before any work unit exists) and **existing-epic** (from `workflow-continue-epic` — skip the macro decision, re-shape the map). The **work-type commit is the durability boundary**: the confirm-trigger creates the manifest, writes the session log, lands imports, lands the promoted inbox item(s) as the work unit's **seed(s)** — uniformly for every type; nothing persists before it. For epics the same conversation continues into topic curation — name topics, classify each as research or discussion, build the discovery map, and at the harvest synthesise per-topic **briefs** (soft decisions, rejected paths, open questions) that seed each topic's research/discussion read-in-full — a brief written or regenerated over in-flight downstream work sets `reconcile_needed`, surfaced non-destructively (never overwriting). A populated-map session also edits existing items (remove, rename, re-route, edit summary/description) via `map-operations.md`. Session log is created **lazily** for existing-epic edits, written by the confirm-trigger for new work. Resume detection (`resume-detection.md`) handles an interrupted prior epic session. The self-healing gap analysis (discovery-gap-analysis, the sole boot-time analysis) is run by `workflow-continue-epic` Step 6 and `workflow-bridge` section B via shared `topic-discovery-dispatch.md` — **not** from inside discovery. `workflow-continue-epic` ordering: Legacy Bridge (`/workflow-legacy-research-split` for pre-discovery epics with migration-seeded broad research files) → Summary Backfill → Self-Healing → Display. Direct-entry items land here with `source: direct-start`.
2. **Research** (`workflow-research-process`): EXPLORE — feasibility, market, viability, early ideas. Scoped per-topic, one file per topic at `.workflows/{work_unit}/research/{topic}.md`. Existing files can be attached as imports during discovery's opener (universal across work types) — imports land in `imports/` and surface via the knowledge base. Background review agent for topical gaps; document review reconciles session against research file to catch undocumented substance (both mandatory before conclusion); deep-dive agents for independent thread investigation.
3. **Experiment** (`workflow-experiment-process`): MEASURE — the umbrella laboratory research and discussion use; never a topic's first phase, never entered except through the spawn. A conversation whose number is about to bear a decision **offers** the laboratory (shared `experiment-spawn.md`; declining keeps an inline measurement, labelled exploratory); on yes the session writes the problem statement — **no design content** — to a cache scratch and `experiment create --from {phase} --problem <scratch>` allocates `E{n}` (per-topic series) and installs it as `experiment/{topic}/{id}-{slug}/problem.md` in the same transaction (no conceived record ever exists without its problem file), and the spawning item locks: `awaiting_experiments` gains the id, `topic complete` refuses engine-side until every wait releases (`experiment-wait-gate` is the refusal's graceful face; the post-spawn `experiment-spawn-gate` offers now-or-later). The **menu is the router**: the epic menu carries one row per topic whose series holds a live record, ranked above other recommendations (an interrupted discovery session's resume still leads), appearing at the first spawn and retiring when no live record remains; every route is the uniform entry contract, and the record resolves inside the phase — one live record auto-selects, several render the register with a picker. After a record ends, `experiment-next-gate` offers the next live experiment in the same session or the menu; either way the laboratory starts in fresh context — isolation is a scientific control that guards the spawning conversation's hopes, not sibling records. Record lifecycle `conceived → designed → approved → running → concluded | abandoned`: `advance` walks the mechanical steps, `approve` alone records the briefing's user-confirmed freeze, `conclude` takes the one-line verdict (the pre-registered decision rule's mechanical outcome), `abandon` keeps the row and its reason. Amendments are dated and re-confirmed before results are visible, frozen for good after; report corrections append-only. A split nests sub-experiments (`E{n}.{m}`, `--parent`) inside the running parent — the wait stays on the parent and releases once. A terminal top-level record releases the wait and flags the holder (`reconcile_needed: "experiment"`); the conversation's re-entry surfaces the register and reads the reports before the waiting point settles (`reconcile-advisory.md`'s experiment branch) — experiments measure, conversations decide, and an abandonment reverts the point to open. The phase item is derived bookkeeping over the records (`completed` when all terminal — `topic start/complete/reopen` refuse it; a new spawn reopens the series); the schema's `DERIVED_PHASES` property carries that fact, and every generic surface keys on the property, never on the phase name.
4. **Discussion** (`workflow-discussion-process`): Organic conversation guided by a live Discussion Map (`pending` → `exploring` → `converging` → `decided`/`deferred`). Background review agent for topical gaps; document review reconciles session against discussion file to catch undocumented substance (both mandatory before conclusion). Off-topic concerns reroute into the target topic's triage queue (`.workflows/{wu}/{phase}/.triage/{topic}/`, one engine-numbered file per concern, delivered by the self-committing `topic triage`), landing with `source: reroute:{origin}` on an existing or newly-created map item (epics only). Discovery-gap analysis (epics only, formerly discussion-gap-analysis) reads completed research AND completed discussions holistically to surface cross-artifact themes, research themes no discussion addressed, emergent topics, integration gaps — cached and manifest-tracked under `phases.discovery.gap_analysis_cache`.
5. **Investigation** (`workflow-investigation-process`): Bugfix-specific — symptom gathering + code analysis → root cause.
6. **Scoping** (`workflow-scoping-process`): Quick-fix-specific — context, spec, plan in one pass.
7. **Specification** (`workflow-specification-process`): Validate and refine into standalone spec. A spec declares two input types: **sources** (discussions extracted wholesale, gated by `incorporated`) and **consult references** (a sibling discussion read narrowly for an owed correction — cite the hand-off slice, don't extract; gated by `addressed`). Consult references are declared at grouping time (consolidation analysis + a KB advisory query surfaces candidates), carried into the handoff, tracked in the manifest under `specification.{topic}.consult_references.{name}.status`, and block completion until addressed. Source incoherence is met in-flow (`resolve-source-incoherence.md`, loaded from `spec-construction.md` and from `process-review-findings.md` when a review finding indicts a source): spec makes decisions clear, never makes them, and classification is Claude's — four moves by effort, derivation exhausted first (context, logic, sibling artifacts, measurement), a stop the exception that names what was searched. A claim that fails direct measurement against the tree lands its correction in the owning document (value-only or with a record-supported repair of the leaning conclusion, silently with a one-line notify; a mismatch stops only when it unseats a product conclusion no record-supported repair re-lands); anything else the record settles (supersession, derivable repairs) is derived **silently** — no raise, no edit to any source document; an unsourced decision a defensible derivation pins (precedent, constraints, sibling artifacts, measurement) lands in the owning doc with a one-line notify, no stop; a settleable point always stops (overrides `auto`) — the conflict menu (numbered sides + Comment) where sides are documented, a plain conversational question where derivation ran out (an underivable point is a product-intent gap by construction: spec has no judgment tier) — and the decision made together mirrors back into the owning doc (a discussion's dated timeline entry, reindexed, `sources stale --except` flagging other extractions); a genuine gap stops at an acknowledgement gate (confirm, not choose — an objection drops into the settleable exchange), then lands in the owning document's triage queue (all work types — epic via `triage-landing.md`, linear via a direct `topic triage`), the spec pauses in-progress, and the session routes to the work type's continue skill with the reopened item named — an incorporated row reconciles at re-entry (`session-setup.md`), a pending row re-extracts the updated document. The gap exit liveness-checks the spec item first (a parallel session can collapse it). Spec entry hard-blocks on an unsettled record at every layer: the epic menu refuses the analyze route while discussions are open and a blocked spec's start/continue (`spec_blocked` in epic DATA), open discussions block the structure-building scenarios (`blocked-discussions-open`), a reopened source blocks its spec (menu `blocked_spec` row + the epic entry-gate backstop). The grouping analysis records advisory `**Tension**` lines construction raises when the relevant chunk arrives. `topic complete` enforces the source gate engine-side (no completion over `pending`/`stale` rows). Spec review runs three strictly sequential agent passes per cycle — claims verification (re-runs the spec's recorded measurements against the tree), input review (fidelity against sources, including the reverse check: spec content no source decides), gap analysis (standalone) — and a finding that indicts a source (`Source defect`, `Unsourced decision`) routes through the incoherence flow (Resolution `Routed`), never applied to the spec and never riding `auto`; load-bearing empirical claims are recorded with their measuring command (`` `cmd` `` → result) in specs, discussions, and research alike, and both document reviews re-run them at conclusion.
8. **Planning** (`workflow-planning-process`): Define HOW — phases, tasks, acceptance criteria.
9. **Implementation** (`workflow-implementation-process`): Execute plan via TDD (or verification workflow for quick-fix). Executor and reviewer bank cross-scope consolidation opportunities per report (`implementation.{topic}.bank`); each plan-authored phase closes through a consolidation boundary — a finder sweeps the phase's combined surface, verdicts the bank, and reports spec defects; the judge settles the defects (record-settled → the silent same-unit corrigendum route in `correcting-historical-artifacts.md`) and folds the survivors into **proposals** (problem + direction settled with its derivation, class-tagged incl. `behaviour`; an irreducible product fork as a Decision — stakes argued, sides stored as product end states, recommended side first — which is raised in product terms between the slim header and the sides menu (`raising-a-decision.md`, technical retelling one option away) and always stops, auto included) walked at proposal altitude; the approved shortlist is expanded by the task-author agent and transcribed by the task writer into the still-open phase (`staging.p{N}`, `consolidation_gate_mode`, `consolidated_phases`) before `--phase-complete` records. The analysis and review synthesis loops share the same shape — synthesizers stage proposals and report spec defects; author before writer at task creation. Bank residue seeds the analysis loop's synthesizer; quick-fix and machinery-created remediation phases never take the boundary.
10. **Review** (`workflow-review-process`): Per-task verifiers report only what is wrong — each finding names its failure, its scope (in/out of the delivered change-set) and its blast radius (contained/spreading) — then a prep pipeline (assessor + guards + relationships agents, one synthesis) verifies every finding against the code, collapses collisions, and routes: nothing wrong → discarded with reasons; in-scope and contained → applied in-session (batched appliers, a whole-diff verifier, one commit); in-scope and spreading → `replan`, which **fails the review** (the verdict is derived, never chosen — pass or fail, binary); out-of-scope → banked durably on the manifest (`out_of_scope`), offered at a pass, never auto-filed. A finding whose entire remedy is comment text never blocks. Crash-resume after verification lands on prep, never re-verifying (`reviewed_tasks` + report existence discriminate).

## Skill Architecture

Skills organised in tiers:

**Entry skill** (`workflow-start`): the sole user-invocable entry. Shows all work; routes new work into discovery and existing work into the per-type `workflow-continue-*` skills. Also hosts the inbox pickup — a **working set** (multi-select promotion, single-type-gated) with an `.archived` lifecycle (archive · restore · delete). Hosts the full Step 0 (`engine boot` — migrations + knowledge check + compact in one call — then the knowledge gate), run once.

**Discovery** (`workflow-discovery`): model-only (`user-invocable: false`). The universal first phase (see Workflow Phases #1) — new work is shaped and its type settled here before the pipeline branches into the type-specific phases. Two modes — new (decide the work type, persist at the commit, route out) and existing-epic (re-shape the map, delegated from `workflow-continue-epic`).

**Navigation skills** (`workflow-continue-{epic,feature,bugfix,quickfix,cross-cutting}`): model-only (`user-invocable: false`). Per-type resume/dashboard — show state and route to the right phase. `workflow-continue-epic` also delegates map refinement to discovery and triggers the analytical bridge enrichment. Step 0 renders the phase title only (migrations + the knowledge gate are guaranteed by `workflow-start`).

**Phase entry skills** (`workflow-*-entry`): internal (`user-invocable: false`). Invoked by discovery, `workflow-continue-*`, and the bridge with work_type and work_unit always provided. Handle phase-specific validation, bootstrap questions, processing skill invocation. Durable phase inputs — the seed, an epic topic's brief, the discovery carrier (session log + manifest `description`), completed research — are read by the processing skills at initialisation, never relayed through the handoff.

**Processing skills** (`workflow-*-process`): model-invocable. Assume pipeline context — work_type set, prior phases complete, artifacts in expected locations.

**Capture skills** (`workflow-log-idea`, `workflow-log-bug`, `workflow-log-quickfix`): model-invocable, lightweight, outside the pipeline. Capture ideas, bugs, or quick-fixes as markdown files in the inbox (`.workflows/.inbox/`). No manifest, no migrations, no step/reference structure — just natural-language instructions with capture-only constraints.

**Roadmap skill** (`workflow-roadmap`): model-only, project-level, outside the pipeline — the product layer above the work unit (design: `design/product-roadmap.md`). Sessions at `.workflows/.roadmap/sessions/` (KB-indexed under reserved identity `roadmap`, graded like discovery logs); the map on the project manifest's `roadmap` node — user-named ordered **horizons** + capability-grain **items** (`{horizon, summary, origin, sources[, pulled_to]}`), lifecycle computed by joining `pulled_to` against the work unit (waiting = no join; never stored). Two entry modes — `genesis` (discovery's shaping gate reads product-altitude: no single unit of work on the table; the conversation continues here) and `open` (the status-keyed `r/roadmap` start row) — plus `pull` (a recognition offer's direct route). The **pull is the commitment point**: a working-set select births the unit fenced to the pulled items (epic → discovery continues under `pull_continuation` on a backfilled session-001; feature → bridge), with the remainder named. Authority splits at the pull: waiting items edit freely; a pulled item refuses re-bucket/remove (topic/work-unit cancel reverts the join to waiting), cross-boundary signal travels as `reconcile_needed: "roadmap"` flags and triage reroutes, never edits. The map is born JIT at the first park (`roadmap add --origin park:{origin}`, available in epic discovery's session loop and in the shared off-topic flow the research and discussion epic sessions both load — "the bucket is the ticket": stated placement parks, unplaced thoughts go to the inbox); the epic harvest sorts two ways (topics / park set / pull-forward set, with the `waiting_on_roadmap` anti-twin flag); a recognition pass at shaping matches forming work against waiting items and live inbox captures. Briefs are never written at product level — one distillation, at the epic's topic shaping, from the whole session chain.

**Baseline skill** (`workflow-baseline`): model-only, project-level, outside the pipeline — the brownfield assessment. Reached only from `workflow-start` (the one-time Step 0.4 judgment when boot reports `baseline: none` — read from boot's `baseline_signal`, the repository's own account of what came before the workflows — the commits before `.workflows/` first landed and the tree they arrived into, judged as evidence, never thresholded: a project that grew up on the workflows records `native` and is never asked again, a codebase that predates them gets the assessment offer; either verdict lands through `engine baseline record native|skipped`, one confined write and commit; the status-keyed `a/baseline` menu rows — resume on in-progress, view/expand on completed, and on the empty state a declined one starts from there too; manage carries it always). Scope-areas confirm → one `workflow-baseline-researcher` agent per area (dossiers of observed structure + question candidates, never fabricated rationale) → per-area agendas → a conversational interview in rounds (engine-rendered ask blocks with lettered candidate answers; the user replies in prose; answers recorded to the agenda ledger every round) → per-area docs at `.workflows/.baseline/{area}.md` weaving **observed / stated (from the interview) / open** layers, indexed as they land (KB phase `baseline`, confidence low, reserved pseudo work-unit `baseline`, advisory never record and never decaying — `knowledge-usage.md` carries the doctrine line). Durable state on the project manifest (`baseline.status`: `native`/`in-progress`/`completed`/`skipped`; per-area statuses under `baseline.areas`: `pending`/`researched`/`completed`); dossiers + agendas are committed content under `.workflows/.baseline/.state/` (never indexed). Pausable/resumable; expand reuses the same scoping flow — a new area, or a deepen that appends to an existing area's agenda and extends its doc, never replacing either. Every display and gate is the `baseline-*` render-surface family (`projections/baseline.cjs`; state derivation single-homed in `domain/baseline.cjs`). Discovery reads `overview.md` in full when it exists — the universal opener for new work, the epic session loop on re-entry; the other docs surface per-topic through the KB.

**Shared references** (`skills/workflow-shared/references/`): loaded by multiple skills across phases. Define protocols and checks that apply uniformly regardless of the calling skill — casing conventions, compliance self-check, topic discovery and dispatch, analysis approval gates, convergence analysis, background agent surfacing, natural break detection, and more; the directory is the authoritative list. Review findings surface in **lanes**: classified by the move owed (never severity) into the protocol's four presentation shapes — batch-apply (corrections the record determines, applied together), batch-decide (calls the record settles, presented for a scan and a veto before they land), walk (one at a time, a genuine choice each), batch-route (sent to the owning topic) — with each caller's `Lanes` declaration owning its lane names, walked-lane heading, and resolutions; batch lanes render in screens of at most five, engine-enforced; a maturity-graded sufficiency bar applied at the agent — early findings are fuel, settled ones face the consuming-phase test; sub-bar findings land in the report as Observations, never raised — the batches fixed at announce time, and promotion only ever toward the walk, never away from it. A raised finding the user turns down has two rejections, neither writing into the artifact: **not now** (dropped, nothing recorded, organic resurfacing) and **dismiss** (the ground joins the topic's `dismissed_grounds`, carried into every later review dispatch as do-not-report grounds, reversible with `manifest pull`).

`framework.md` is the head-of-skill composition point: every flow skill's `## Instructions` section is a single load directive pointing at it, and it in turn loads `instructions.md` (the STOP-gate and step-discipline rules), `casing-conventions.md`, `voice.md`, and `ask-or-decide.md` (whether a point needs the user at all — a question is owed only when the answer comes from them, never for a call the record settles). Skills carrying a context-refresh recovery protocol re-load it there by name — a compaction summary drops instructions held only by reference. `voice.md` governs how Claude speaks in every turn composed for the user to read; it explicitly does not touch engine-emitted `DISPLAY`/`MENU` sections or the artifact prose written to disk, which stays technical and as long as the material needs. How hard to challenge stays with each phase's own guidelines — `voice.md` owns the manner, never the frequency.

### Phase Entry Skill Routing

Phase entry skills (`workflow-*-entry`) receive positional arguments: `$0` = work_type, `$1` = work_unit, `$2` = topic (optional) — no exceptions. Topic resolution: `topic = $2 || (wt !== 'epic' ? $1 : null)`.

**With topic** (feature/bugfix always; epic when caller provides it):
- Check manifest phase status → new entry (bootstrap questions) / resume / reopen
- No discovery needed — topic is already determined

**Without topic** (epic only — scoped path):
- Run discovery scoped to work_unit → analysis/selection flow → determine topic
- Only used by discussion and specification (research also, but simpler — just asks seed questions)
- Planning, implementation, review always receive a topic

## Key Conventions

**Work types and work units**: *Work type* = one of five pipeline shapes: epic, feature, bugfix, quick-fix, cross-cutting. *Work unit* = named instance of a work type (e.g., "auth-flow" is a feature work unit, "payments-overhaul" an epic work unit). Each work unit gets its own directory under `.workflows/` and its own `manifest.json`.

- **Epic**: Multi-topic, multi-session, phase-centric (Discovery → Research (opt.) → Experiment (opt.) → Discussion → Specification → Planning → Implementation → Review)
- **Feature**: Single-topic, single-session, linear (Discovery → Research (opt.) → Experiment (opt.) → Discussion → Specification → Planning → Implementation → Review)
- **Bugfix**: Single-topic, investigation-centric (Discovery → Investigation → Specification → Planning → Implementation → Review)
- **Quick-fix**: Single-topic, scoping-centric (Discovery → Scoping → Implementation → Review)
- **Cross-cutting**: Single-topic, project-level (Discovery → Research (opt.) → Experiment (opt.) → Discussion → Specification — terminal)

**Topics**: *Topic* = the item within a phase. For feature/bugfix/quick-fix, topic name equals work unit name. For epic, topics are distinct from the work unit name. All work types use per-topic manifest items (unified structure).

Work-unit-first directory structure with uniform `{topic}` in all paths (`{topic}` = `{work_unit}` for feature/bugfix/quick-fix).

- Project manifest: `.workflows/manifest.json` (work unit registry + project defaults)
- Manifest: `.workflows/{work_unit}/manifest.json`
- Discovery sessions: `.workflows/{work_unit}/discovery/sessions/session-NNN.md`
- Discovery briefs: `.workflows/{work_unit}/discovery/briefs/{topic}.md` (per-topic views synthesised at the epic harvest — soft decisions, rejected paths, open questions; regenerable, never records; pointed to by the discovery item's `brief_path`, read in full by the topic's research/experiment/discussion and tracked via `brief_incorporated`; a brief written or regenerated over in-flight downstream work sets `reconcile_needed`; a first-written brief for an existing topic gets its pointer backfilled at the harvest)
- Research: `.workflows/{work_unit}/research/`
- Experiment: `.workflows/{work_unit}/experiment/{topic}/{id}-{slug}/` (per-record directory — `problem.md`, `design.md` frozen at the confirm, `report.md` with append-only corrections, `data/`; sub-experiments nest inside the parent's directory; the series itself lives on the manifest at `phases.experiment.items.{topic}.experiments`)
- Discussion: `.workflows/{work_unit}/discussion/{topic}.md` (flat file)
- Investigation: `.workflows/{work_unit}/investigation/{topic}.md` (flat file)
- Specification: `.workflows/{work_unit}/specification/{topic}/specification.md`
- Planning: `.workflows/{work_unit}/planning/{topic}/planning.md` (+ `phase-{N}-tasks.md` + task files in output format)
- Implementation: `.workflows/{work_unit}/implementation/{topic}/`
- Review: `.workflows/{work_unit}/review/{topic}/report.md`
- State: `.workflows/{work_unit}/.state/` (per-work-unit analysis files)
- Global state: `.workflows/.state/` (migrations, environment-setup.md)
- Cache: `.workflows/.cache/{work_unit}/{phase}/{topic}/` (scratch files for any phase; gitignored via `.workflows/.gitignore`, purged when the work unit closes — complete/cancel/absorb — and backfilled for already-closed units by migration 050)
- Imports: `.workflows/{work_unit}/imports/` (user-shared reference files copied in during discovery's opener; tracked via the `imports[]` manifest field; KB-indexed at copy time)
- Seeds: `.workflows/{work_unit}/seeds/` (the work unit's **origin** — the promoted inbox item, or several items of one type, *moved* here at the work-type commit; tracked via the `seeds[]` manifest field, one entry per item, each with a `source: inbox:{idea|bug|quickfix}` tag; KB-indexed under the `seeds` phase. Distinct from imports: the trigger the work was spawned from, not reference material it pulled in)
- Baseline: `.workflows/.baseline/{area}.md` (project-level brownfield assessment docs — no work unit; session material under `.workflows/.baseline/.state/`)
- Roadmap: `.workflows/.roadmap/` (project-level product layer — no work unit; `sessions/session-NNN.md` product session logs, `imports/` the project-level imports home; the map itself lives on the project manifest's `roadmap` node; `roadmap` is a reserved work-unit name; `engine commit --roadmap` is the session cadence commit)
- Inbox: `.workflows/.inbox/{ideas,bugs,quickfixes}/` (pre-pipeline capture. The inbox pickup is a **working set** — select one or more items *of a single type* to promote, moving them into the work unit's `seeds/`; or archive any selection, regardless of type, to `.archived/{type}/`. The `.archived/` store is live: archived items can be restored to the inbox or hard-deleted (`git rm`) from the archived sub-view. It holds *declined* items, never promoted ones)

**Work unit lifecycle**: Each work unit has a `status` field in its manifest tracking lifecycle state:
- `in-progress` — actively being worked on (default on creation)
- `completed` — pipeline finished (set automatically on pipeline completion, or manually via manage menu)
- `cancelled` — abandoned (set manually via manage menu)

Discovery filters by status — active work by default, with options to view completed/cancelled or manage lifecycle. Work units can be reactivated.

**Feature-to-epic pivot**: Convert features to epics via manage menu (`p`/`pivot`). After pivot, continue immediately as an epic or return to the previous view.

**Feature absorption**: Merge a feature into an in-progress epic via manage menu (`a`/`absorb`). Moves the feature's discussion and research into the epic as a new topic, then deletes the feature. Guarded: requires a discussion, no spec-or-beyond, at least one in-progress epic. Git history serves as provenance.

**Epic topic cancellation**: Cancel/reactivate individual topics via workflow-continue-epic menu (`a`/`cancel`, `e`/`reactivate`). Cancellation sets item's phase status to `cancelled` and stashes prior status in `previous_status`. Cancelling a discussion or investigation a live specification sources collapses that spec: the engine refuses the bare cancel naming the spec(s); `topic cancel … --cascade` cancels source and spec(s) in one transaction after the menu's confirm. Experiments take the softer edges: a series cancel abandons every open record (`reason` kept on each row) and refuses bare while conversations await its evidence — `--cascade` releases every wait, flagging non-terminal holders; a research/discussion cancel over live `awaiting_experiments` refuses bare and its `--cascade` abandons exactly those records and closes only that conversation's waits — the experiment item is never cancelled (its derived status settles over what remains) and a sibling conversation's experiments are untouched; `topic reactivate` refuses the experiment phase — the rows stand, and a new spawn revives a cancelled series. Cancelled items remain visible in state display but excluded from phase aggregation (`phaseStatus`), gating flags, next-phase-ready logic, and discussion/spec entry discovery. Reactivation restores `previous_status` and deletes the field. Epic-only — other work types use work-unit-level cancellation since topic = work unit.

**Epic soft gates**: Forward navigation between epic phases warns via `render epic-soft-gate` (empty on pass). The specification row counts the discussions still in progress; the planning and implementation rows read the build order and name the topics sitting ahead of the selection that are still unplanned/unbuilt. Informational, not blocking — system recovers via re-analysis if user proceeds early. Specification entry is the deliberate exception: it hard-blocks on an unsettled discussion record (see Workflow Phases #7) — a spec cannot be reliably built from an in-flight record.

**Staleness hops**: When a phase item's upstream input moves — at `topic reopen`, a triage landing, a spec-side `sources stale` (a discussion document amended in place during specification, no lifecycle transition), or a top-level `experiment conclude` (evidence arriving after a decision must surface before the record is trusted), never the later re-completion — the engine flags the downstream neighbour one hop away (`transitions.cjs flagDownstream`): the next pipeline phase's same-named `completed` item gets `reconcile_needed = <upstream phase>` (terminal states skipped, an existing flag never clobbered; the derived experiment slot is walked past unconditionally — a flag must land where an entry flow can clear it, and the series item has none); a discussion's or investigation's downstream is every spec item naming it in `sources` (reverse join), whose `incorporated` rows also flip to `stale` until the spec's own reconciliation re-incorporates them (`stale` blocks spec sign-off alongside `pending`). Entry skills surface and clear the flag via `workflow-shared/references/reconcile-advisory.md` (value-keyed branches); for the linear work types `computeNextPhase` routes back to the earliest flagged phase (`input moved — reconcile`), so the bridge never reads `done` past a live flag; epic surfaces cue flagged items per-item (`· input moved`).

**Build order (epics)**: one soft execution sequence over an epic's live specification topics — `order` on `phases.specification.items.{topic}`, joined by name into planning and implementation. Born at the grouping analysis (riding the reconcile's `manifest apply`; the unify branch assigns too), refreshed by `workflow-continue-epic` Step 8 / the bridge's section D whenever `build_order_needs_sequencing` reports true (a live topic without an order, a non-contiguous or duplicated numbering, or `build_order_stale` — set by an epic spec's completion, cleared by sequencing), and re-derived manually via the epic menu's `o/order`. Advisory everywhere: it sorts the dashboard trees, the spec-entry menu, and the epic menu's entries (phase outranks order in the recommendation), and feeds the planning/implementation soft gates — it never blocks. `engine build-order sequence` writes it (whole live set, contiguous 1..N, terminal statuses refused; live set = every spec item not cancelled/superseded/promoted, completed items keep their number). A spec cancel stashes the item's order as `previous_order`; reactivate restores it only while no live topic holds the number. A dep-blocked plan carries no implementation menu row — the ⚑ list, the tree cue, and `u/unblock` carry the state. Design: `design/build-order.md`.

**Discovery map (epics)**: Discovery builds a manifest-backed map at `phases.discovery.items.{topic}` that drives auto-routing for research and discussion. Each item carries a `source` provenance field recording how the topic landed on the map — one of `discovery`, `gap-analysis`, `direct-start`, `migration-seeded`, `legacy-split:{parent}`, `reroute:{origin}` (off-topic concern rerouted in from another topic), `roadmap` (a product-roadmap item pulled into the epic), or the historical `research-analysis:{parent}` / `research-split:{parent}` on existing maps (still rendered, still walked for the discussion-time parent read). Multi-source items are comma-accumulated (e.g. `discovery,gap-analysis`). A `legacy_split_state: in-progress` sentinel field is set by `workflow-legacy-research-split` while an apply runs — the success path deletes the sentinel-bearing source item, so a surviving sentinel marks a crashed apply (surfaced by detect as `stranded_sentinels`); items with this field set are excluded by `detect-trigger`. Map items have no `status` field — lifecycle (`fresh`, `researching`, `ready for discussion`, `discussing`, `decided`, `handled` (rendered as dead end — completed research with nothing to carry forward under its own name; set by the conclude gate's dead-end row or a map op, reversible), `cancelled`) is computed at render time by joining the discovery item against per-phase items. Removal during an discovery session hard-deletes the item and adds its name to a *dismissed list* so the analysis won't auto-re-add it (a "show dismissed" recovery option is available in any discovery session). Hard-delete is only allowed for items with no per-phase work; once research or discussion items exist, the map item is preserved as historical anchor. Auto-routing operates at the map-item level — research vs discussion is determined by the item's `routing` field (initial intent) overlaid with whichever per-phase items actually exist. The map gates the **birth** of a topic's research or discussion item: `topic start` refuses a phase the map's next action does not name (an in-progress item always resumes; a parked research stub always drains — research is downstream of nothing, and a discussing topic's parked research has no menu row), and the epic menu's `d`/`r` free-text doors refuse a name already on the map via `render direct-entry-gate` — the menu row is the way in. A research/discussion item may carry `status: triaged` — a rerouted concern parked on an unstarted topic via `engine topic triage`; it renders as fresh with a `triage waiting` cue, is excluded from phase aggregation, and exits only via `topic start` (migration 052 repairs legacy phantom in-progress stubs).

**State ownership**: workflow state is engine-owned — durable state in the work-unit manifest, ephemeral session machinery in per-topic `.workflows/.cache/{wu}/{phase}/{topic}/state.json` (colocated with the content it describes; deleting a topic's cache dir is a complete cleanse). Frontmatter is never written or read as state; the sole exception is local-markdown's task files (the format's backend). Migration 051 translates pre-programme frontmatter state forward.

**Commit door**: every engine-made commit routes through `domain/commit.cjs` and is **confined** — it names the paths its action wrote and commits `-- <paths>` under a process-wide commit lock, so a peer session's dirty or staged files are never swept up under someone else's message. Workflow artifacts commit by layout-derived scopes: `--topic {phase}/{topic}` (one topic's artifacts + the work-unit manifest, `--kb` when the action indexed, `--sweep` when the commit is over a topic this session is not working), `--discovery` (session logs + briefs + manifest), `--plan {topic}` (the planning topic's directory, both manifests, and the plan's declared `storage_paths`). Code has no layout, so `commit --paths <file>… -m msg --for {wu} {implementation|review}/{topic}` takes Claude-declared paths — validated (in-project, literal, never `.workflows/`), confined, and answered with `left_dirty` so a forgotten path comes back. Deliberately still work-unit-wide: the spec-entry grouping/reconcile commits, the shared analysis commits, and the work-unit lifecycle transactions (create, cancel, pivot, absorb).

**Presence**: per-topic session heartbeat, cache-resident (`.workflows/.cache/{wu}/{phase}/{topic}/presence`, gitignored) — awareness, never mutual exclusion. Every phase a session sits in carries one — research, experiment, discussion, investigation, scoping, specification, planning, implementation, review — except discovery, which `discovery-session open` already serialises to one session per epic. **Beats are mechanical and the prose never mentions them**: the engine stamps the heartbeat as a side effect of the verbs a session already runs on its own topic (`commit --topic` on a live item, `topic queue`, `topic start`/`absorb`, the agent-store verbs, the experiment verbs — `create --from` beats the spawning conversation, `create --parent`/`advance`/`approve` the laboratory's own topic — `commit --paths … --for`, and the code gate's empty render — claiming the slot is the same act as reading it); `topic complete` *clears*, as do a top-level `experiment conclude`/`abandon` (the record's close is the laboratory's release) and any `commit --topic` on a terminal item or carrying `--kb`, so the close is the release; `--sweep` suppresses both on a commit made over a topic this session is not working; and no field write beats at all — a three-segment `manifest set` is frequently one phase's session writing another's item. `scan` answers two verdicts per row — `held` (owning pid + start time verified alive) and `live` (held and beaten within 900s) — plus `live_sources`, the research and discussion rows alone; work-unit-less it walks the whole project. Consumers: the epic view strikes through held topics, skips them as recommendations, and confirm-gates entering one; the **code gate** at the implementation and review entry skills reads the project-wide scan (one code session per checkout — the tree and the index do not partition); analysis dispatch and the spec-entry grouping analysis defer while a source session is live; the conclude sweep leaves a held row's dirt alone; the spec-side resolution flow checks the target discussion before editing its document in place. The SessionEnd hook runs `presence cleanup` for the exits that keep the process alive. Design: `design/concurrent-phases.md`.

**Session labels**: opt-in tmux rename showing where a session is working (`{original} · {wu} · {phase} · {topic}`, topic collapsed when it equals the wu). `engine session label` is called by every process skill at Step 0 and by discovery at its run step; `engine session cleanup` restores the original name — its own SessionEnd hook on every session skill. Presence and session labels are separate domains sharing only the session-end trigger: presence verbs never touch labels, and every presence-phase process skill hooks both. Opt-in recorded under `session.tmux_labels` in `~/.config/workflows/config.json` (shared with the knowledge key — both sides preserve sibling keys); a `defaults.tmux_labels` boolean in the project manifest overrides it per project (the prose-test harness stamps `false` into every world so walks never label the developer's terminal). Boot reports the effective state as `tmux_labels`, and workflow-start's Step 0.2 asks once when the value is unset inside tmux. Always a no-op outside tmux, on any tmux error, or with the feature off; a manual rename is adopted, never clobbered. Original names stash machine-globally under `~/.config/workflows/state/session-labels/` (keyed by tmux socket + session id — a tmux session spans projects, so its restore record must too).

Commit docs frequently (natural breaks, before context refresh). Skills capture context, don't implement.

## Migrations

Migrations keep workflow files in sync with current system design (run via `engine boot` in Step 0 of `workflow-start`).

**How it works:**
- `skills/workflow-migrate/scripts/migrate.cjs` (Node) runs every script in `skills/workflow-migrate/scripts/migrations/` — both the frozen `*.sh` fleet and modern `*.cjs` migrations — in one strict numeric-prefix ordering
- Each migration is idempotent — safe to run multiple times
- Progress tracked in `.workflows/.state/migrations`: numeric-only IDs, one per line, extension-independent. An ID is recorded only after its migration completes; any failure aborts the whole run without recording (boot treats a non-zero exit as fatal — migrations must never half-run silently)
- Delete the log file to force re-running all migrations

**Two migration formats:**
- **`*.sh` — the frozen fleet (001–046).** Shipped and already run by real installs; treat as immutable. Edit only to harden a failure path, **never** to change semantics — fix forward with a new numbered `.cjs` migration instead. The orchestrator sources each in a spawned bash with `report_update`/`report_skip` helpers, `PROJECT_DIR` pinned to `.`, cwd = project root, under `set -eo pipefail` (`return 0` semantics preserved).
- **`*.cjs` — all new migrations.** A `.cjs` migration is a module exporting `id`, `description`, and a `run` function, executed in-process:
  ```js
  module.exports = {
    id: '050',
    description: 'short summary',
    info: 'optional — what the migration does, project-agnostic',
    run({ projectDir, reportUpdate, reportSkip }) { /* ...; may return { verify: '…' } */ },
  };
  ```
  Read/write files under `path.join(projectDir, '.workflows')` (`projectDir` is always `.`). Signal outcome only through `reportUpdate()` / `reportSkip()` (display counters — call `reportUpdate()` once per changed unit); never write to stdout. A thrown error aborts the run; if a migration should instead degrade to a skip on unexpected input, catch internally and `reportSkip()`.

  **Verification addenda** (optional): when a migration transforms judgment-written content its code can only exact-match, export `info` (what the migration does, any project) and have `run()` return `{ verify: '…' }` — natural-language instructions for what to check in this project, returned on skip paths too (a skip can be a false negative: content the parser didn't recognise). Addenda from migrations executed this boot ride the boot response (`migrations.verify`); workflow-start Step 0.1 performs the checks with judgment before the migration confirm gate and folds fixes into the migration commit. Addenda fire once — never again for a recorded migration.

**Adding a new migration:**
1. Create `skills/workflow-migrate/scripts/migrations/NNN-description.cjs` (next number after the highest existing)
2. It runs automatically in numeric order; once its ID is in the log it never runs again

Migration `038-add-inception-phase.sh` seeds the phase for existing in-progress epics (`040-rename-inception-to-discovery.sh` then renames it to `discovery`) so legacy work units pick up the discovery map without manual intervention.

**Critical: Migrations must not use `engine manifest`**

Migrations are point-in-time snapshots. The engine's field surface validates against the current schema, which changes over time — a migration using it today may break silently later. Always read/write `manifest.json` directly (`node`/`fs` in `.cjs`; `node`/`jq` in the frozen `.sh` fleet).

**Bash 3.2 compatibility** (frozen `.sh` fleet only): the shipped bash migrations must run under stock macOS `/bin/bash` 3.2 — avoid `mapfile`/`readarray`, `declare -A`, `local -n` (all bash 4+). New `.cjs` migrations run under Node and are exempt.

**Testing migrations:**

Every migration has a matching test suite.

*New `.cjs` migrations* — a node:test suite at `tests/scripts/test-migration-NNN.cjs`, registered in `package.json`'s `test` script (runs under `npm test`). `require` the migration module and drive `run({ projectDir, reportUpdate, reportSkip })` directly against a temp `projectDir`. Follow the sibling suites (`test-migration-047/048/049.cjs`): `describe`/`it`, `node:assert`, per-test `setup`/`teardown` with a `mkdtemp` dir, counting `reportUpdate`/`reportSkip` stubs. Cover at minimum happy path, skip/no-op, idempotency (run twice), content preservation, and every defensive guard. The Node orchestrator itself is covered by `tests/scripts/test-migration-orchestrator.cjs` (mixed `.sh`/`.cjs` ordering, legacy tracking-log compatibility, failure-aborts-without-recording, the `.sh` path under stock `/bin/bash` 3.2, `PROJECT_DIR` pinning).

*Frozen `.sh` fleet* — the existing `tests/scripts/test-migration-NNN.sh` suites (run under `npm run test:migrations`) stay as-is. Their harness: `set -euo pipefail`, `PASS`/`FAIL` counters, `report_update`/`report_skip` stubs, an `assert_eq` function, `setup`/`teardown` with a temp dir. Conventions:
- **Invocation**: `source "$MIGRATION"` (the fleet uses `return 0`).
- **Isolation**: each test function calls `setup` at the start and `teardown` at the end. No shared state.
- **Assertions**: only `assert_eq` (`label`, `expected`, `actual`). File exists → `assert_eq "desc" "true" "$([ -f "$path" ] && echo true || echo false)"`; content match → `... "$(echo "$content" | grep -q 'pattern' && echo true || echo false)"`; fixed-string → `grep -qF`.
- **grep with leading dashes**: always use `--` before patterns starting with `-`.
- **Test naming**: functions prefixed `test_`, comments `# --- Test N: Description ---`.
- **Summary**: `echo "Results: $PASS passed, $FAIL failed"` then `[ "$FAIL" -eq 0 ] || exit 1`.
- **Coverage**: happy path, skip/no-op, idempotency (run twice), and content preservation where applicable.

## Manifest Field Surface

`engine manifest` (`node .claude/skills/workflow-engine/scripts/engine.cjs manifest <command> …`, implemented in `skills/workflow-engine/scripts/domain/fields.cjs`) is the single source of truth for all workflow state. Dot-path syntax: `command <work-unit>[.<phase>[.<topic>]] [field] [value]`. Segment count determines access level (1 = work unit, 2 = phase, 3 = topic). Reserved prefix `project` routes to project manifest — e.g., `get project.defaults.plan_format`. Reads (`get`, `exists`, `list`, `key-of`, `resolve`) print bare stdout; mutations (`set`, `push`, `pull`, `delete`, `apply`) answer with the engine's one-line JSON response; `set` takes one positional pair or a uniform `<field>=<value>` batch (never mixed) in one locked write, and `apply <work-unit> --file <ops.json>` batches set/delete ops across dotpaths in one atomic write. The engine `SKILL.md` is the authoritative API reference. Contract suite: `tests/scripts/test-engine-manifest.sh`.

**Project defaults cascade**: `project.defaults` → topic level. Project defaults are suggestions (user confirms or overrides). Topic level records the actual value in use. No phase-level storage for settings like `plan_format`, `project_skills`, or `linters`.

**Shell quoting**: Always single-quote values that zsh would interpret — `'[]'`, `'[...]'`, `'{}'`, `'~'`. Bare `[]` is a glob pattern (causes `no matches found` errors) and bare `~` expands to the home directory.

## Pipeline Simulation

`tests/scripts/test-pipeline-simulation.cjs` (under `npm test`) drives the engine CLI end-to-end through the call sequences the skill prose prescribes — every work type's mainline plus the supported edges (reopen, supersession, cancel/reactivate, pivot, absorption, promotion, restarts) — auditing the whole state after every mutation: schema-valid manifests, no shadow roots, every derivation computes, every navigation gateway discovers and formats, render surfaces hold. It is the detector for silent state corruption — writes that succeed and only break a menu phases later.

**Any change to the workflows must update the simulation** — a new engine verb, a changed prose call sequence, a new phase ordering, a new manifest field: extend an existing scenario, add a new permutation, or re-pin changed expectations. A red simulation is the design speaking — decide deliberately whether the flow or the scenario is wrong, never paper over it. New permutations are cheap: a scenario is an ordered list of engine calls with assertions.

## Prose Tests

`tests/prose/` — end-to-end tests for the prose logic (design: `design/prose-tests.md`). A case is a directory under `tests/prose/cases/{case-id}/`: `case.json` (values code branches on: the required `entry`, deterministic `invariants`, scripted `answers` and/or a `conduct` description of the user, stub arming, `world: "claims"` for model-authored end states judged against stated claims), `fixture.md` + `fixture-state.cjs` (the starting world), `act.md` (the coarse instruction a walker agent follows through the real skills), `assert.md` (the expected path, seen only by the asserting agent), optional `assertion-state.cjs` (the world the walk should produce; absent = unchanged), and the two generated snapshots. What a snapshot cannot hold directly, a recipe declares in a **sidecar** the snapshot carries and `materialise` turns into real world state, never landing in the world itself: `.world-history.json` (layered commits), `.world-presence.json` (heartbeats a *peer* session holds — presence files are excluded from every snapshot as timing noise, so a fixture needing a peer's hold declares it here and it is stamped last, freshest in the world, which is what makes the peer read live), `.world-dirt.json` (snapshot paths held out of the world's commits — a bare string for untracked, `{path, committed}` for modified over a committed version — written back after the last commit). Nothing is parsed and prose never shares a file with code. **A case starts where a session starts and stops where its claims can be answered**: `entry` must name `workflow-start`, a `workflow-*-entry` skill, `workflow-discovery`, or `workflow-roadmap` — never a navigation or processing skill, never a reference — because a walk begun mid-session lacks the context the prose was written for. A handoff is a fine ending (recorded actions are as deterministic as a world delta); what a case must never do is stop where only display claims remain, since text put on screen is evidenced by no hook. Claims that code can settle belong in `invariants` (`engine_before_write` — declared only where the walk writes, `calls_include`, `calls_exclude`, `calls_in_order` — whose entries may be `write:<path>` tokens standing for the path's *first* recorded write, ordering artifact creation against the calls around it), which run before the asserter and whose verdicts it cannot overturn. Shared pipeline stages live in `tests/prose/mainlines/`. Walks cost tokens — run on command via the `/prose-test` dev skill, never as part of a routine gate. The deterministic perimeter runs under `npm test`: corpus validation plus snapshot goldens — every snapshot must rebuild byte-identical from its recipe under the frozen clock, skipped when nothing feeding it changed. When an engine change moves a world, regenerate with `node tests/prose/run.cjs snap {case-id}` and land the snapshot diff in the same PR; never hand-edit a snapshot. Every review finding lands twice: the fix, and the case that would have caught it. At the end of a PR that touches skill prose, run `node tests/prose/run.cjs select --diff main` and suggest running the intersecting cases.

## Knowledge Base Subsystem

Retrieval-augmented store of completed workflow artifacts (research, discussion, investigation, specification — never experiment/planning/implementation/review), plus epic discovery **session logs** (indexed under a `discovery` phase — the running exploration record), seed material for early-phase context: user-shared `imports` and the inbox-promoted `seeds` (the work unit's origin), the project **baseline** docs (`.workflows/.baseline/*.md`, reserved pseudo work-unit `baseline`), and the product **roadmap**'s session logs and imports (`.workflows/.roadmap/`, reserved identity `roadmap`, phase `roadmap`/`imports`). Every entry-point skill gates on knowledge base initialisation before any phase runs.

**Source vs bundle**: Source lives in `src/knowledge/` (multi-file Node.js — `index.js`, `store.js`, `chunker.js`, `embeddings.js`, `config.js`, `setup.js`, `setup-forms.js`, `providers/openai.js`, `providers/openai-engine.js`, `providers/openai-compatible.js`). Committed CLI at `skills/workflow-knowledge/scripts/knowledge.cjs` is a single-file esbuild bundle. AGNTC installs from git tags with no build step, so the bundle must be present and current at tag time.

**Building**: `npm run build` runs `node build/knowledge.build.js`, which esbuild-bundles `src/knowledge/index.js` into `skills/workflow-knowledge/scripts/knowledge.cjs`. Always rebuild after editing `src/knowledge/` and commit the bundle alongside the source change.

**Allowed tools**: Skills that invoke the CLI must declare `Bash(node .claude/skills/workflow-knowledge/scripts/knowledge.cjs)` in their frontmatter. SKILL.md is the authoritative API reference — read it before adding a new call site.

**Mandatory boot gate**: `engine boot` (Step 0 of `workflow-start`) runs `knowledge check` and, when ready, `knowledge compact` (progress-based decay). A `not-ready` response carries a `system_config` report (valid/absent/invalid + active provider/model, never secrets) and routes into `workflow-start`'s knowledge gate (`references/knowledge-gate.md`), which initialises the store conversationally via the non-interactive `knowledge setup` forms (`--from-system`, `--keyword-only`, `--provider ...`) — boot itself never initialises anything. API keys never transit chat or argv: they resolve from `$OPENAI_API_KEY` or `credentials.json`, written by the `--key-only` terminal detour or the interactive wizard (which remains human-only). When the store is ready, boot commits any store dirt scoped to `.workflows/.knowledge` — `chore(knowledge): initialise store` on the first boot after setup, `chore(knowledge): compact store` otherwise.

**Phase-completion indexing**: Processing skills invoke `knowledge index <path>` at phase completion to add the new artifact. Spec promotion and work-unit cancellation invoke `knowledge remove --work-unit ... [--phase ...] [--topic ...]` to clean up. Pending queue handles transient failures with retry on next `index` call. Corrections to a concluded specification follow `workflow-shared/references/correcting-historical-artifacts.md` — specification only, the golden record; other phase artifacts decay and are never corrected — in-place edit + corrigenda entry, then a single-file `knowledge index <path>` (replaces that file's chunks; the owning manifest is never touched). Two entries: another unit's completed spec is gated (`render correction-gate`); the working unit's own spec, defect found by a downstream phase (consolidation finder, analysis, review synthesis), is corrected **silently** when the record settles the side or a defensible derivation (an honest technical call included) pins an open one — the corrigendum records the reasoning; code-wrong verdicts and product-intent gaps route back as walk proposals, never spec edits. (A spec still in its own phase differs: the spec resolution flow — construction or review — edits the owning source document and reindexes it single-file.)

**Stub mode**: When no embedding provider is configured, CLI runs in keyword-only mode (BM25). Treat as supported degraded mode, not broken state. `query` output prepends `[keyword-only mode — ...]` note.

**Tests**: `tests/scripts/test-knowledge-*.{cjs,sh}` cover the subsystem — store, chunker, embeddings, config, OpenAI provider, integration, retry, build, CLI surface. Node suites run under `npm test`, shell suites under `npm run test:cli`. Add a test alongside any `src/knowledge/` change.

**Project layout**: `.workflows/.knowledge/` (per-project store + metadata + config), `~/.config/workflows/config.json` (system defaults), `~/.config/workflows/credentials.json` (mode 0600, optional API key store).
