01 · Overview

A web UI for a process that already knows when it needs you

The agentic-workflows system computes exactly when a human is needed and what kind of act is owed. The bridge's whole job is to deliver that knowledge — to a browser, a phone, a teammate — without adding any noise of its own.

The product is a phased engineering process for Claude Code: discuss, specify, plan, then a gated build loop, with a deterministic engine owning every state transition. Today you drive it from a terminal. The Workflow Bridge puts a channel-based web app in front of it — one channel per work unit, decision cards for its gates, an attention system derived from the process's own classifications — while changing nothing underneath.

◆ rule 1

Zero new workflow state

The repo, the manifests, and the engine stay the record. The bridge is a veneer; everything it persists is UI-native (cursors, ownership, digests). If the UI and the terminal ever disagree, the UI is wrong.

◆ rule 2

Gates are never guessed

A turn the bridge can't confidently parse as a structured ask renders as plain chat with a reply box. Pass-through is a correct rendering of an unstructured question, not a failure mode.

◆ rule 3

Ceremony, never disposition

The UI decides what pings, badges, or waits for a digest. It never answers anything on the human's behalf — every stop in the process stays a stop here.

Where the project stands

Fully planned, not yet built — deliberately. Eight phase plans, five pre-code specification artifacts, and an upstream-proposal ledger live in ui/plans/, and the whole set has been through ten adversarial review passes (intent, ground truth, scope, coverage, sufficiency ×2, consistency, failure modes, a two-persona walkthrough, and an upstream-fit review) with every confirmed finding folded back in. Phase 0 is buildable by its own reviewers' standard.

The thesis in one line: the system already knows exactly when it needs a human and how much ceremony the moment deserves; the UI's only job is to deliver that knowledge without adding any of its own.

02 · Value

Four surfaces carry all the value

Everything else — SPA shell, chat rendering, markdown, graphs, auth — is off the shelf. The build spends its effort on exactly four things.

1 · The gate card

Every decision the process asks for arrives as a structured card: the ask told in product terms, the engine's own option rows as buttons, free text always available (the menus map prose by design). Answered from a browser or a phone, the answer feeds back into the live session as an ordinary user turn.

payments-overhaul · retry-policy · specification gate · open
The specification for retry-policy is constructed: 14 decisions extracted from the discussion, both sources incorporated, one consult reference addressed. Three review passes are clean.
◆ Sign off this specification?
never-auto gate — signing off requires typing the confirmation, not one tap

Cards are parsed, not invented: for bridge-driven sessions the engine's demarcated menu sections arrive byte-exact in the tool-result stream, and the card renders from that ground truth. Gold marks the human's moment — everywhere in the UI, gold means a gate.

2 · The needs-you queue

One cross-work-unit list of everything waiting on a human, honestly split in two tiers: live open asks from bridge-driven sessions, and durable waiting-state derived from the manifests — reconcile flags, blocked specs, undrained review reports — which covers terminal sessions too. Ordered by what answering unblocks: escalated first, live before durable, earlier phases first (the cone says early decisions are the cheap-to-fix ones), oldest never sinking.

3 · The attention policy

Mechanical rules for what may interrupt, derived from the process's own classification of findings and a designed table for everything else — covered in full on page 07. The one-line version: everything badges, almost nothing pushes, and nothing is ever silently disposed of.

4 · The artifact lenses

Every document gets three views: Read (typeset, with the firmness gradient as chrome — research casual, discussion working, specification golden), Structure (a register sourced from wherever structure actually lives — the manifest for discussion maps and spec sources, stable headings for investigations, reviews, and briefs), and History (git timeline, with "what moved since your sign-off" as a real diff). The spec sign-off surface joins sources, consult references, and measured claims live from the manifest — a sign-off is decidable entirely in the browser.

06 · Channels

Channel = work unit, plus a lobby for everything else

A channel is born at discovery's shaping commit — the moment the product makes work durable — and archived at close. Epic topics are threads. The spine carries gates and phase completions only; commits and machinery live in threads and a drawer.

The project lobby

A whole tier of the product lives outside any work unit, so it gets a project-level home: the start overview, the inbox working set, the product roadmap, the baseline assessment — and the pre-durability shaping conversation. Shaping happens as a lobby thread; at the type-confirm commit the thread is promoted into the newborn channel. Abandon it and it simply ends — mirroring the product's own zero-residue rule.

Identity through reshaping

  • Pivot (feature → epic): same channel, new type badge, history kept.
  • Absorb: the feature's channel archives with a tombstone pointing at the epic topic thread that continues it.
  • Quick-fix promotion: the channel ends with a tombstone into the new feature/bugfix channel.
  • Spec promotion: a new cross-cutting channel, linked from the originating thread.

Tombstones are UI-native metadata, never workflow state — and the event stream carries a workunit.removed event (with its successor inferred from the same commit) so the tombstone has a trigger.

Mixed-stage density

The collaboration cone is the layout — but it's a per-topic-thread property, not a channel one. An epic is routinely in Discovery and Delivery at once; each thread carries its own density (conversation-dense early, telemetry-quiet late), the channel frame stays stage-neutral, and delivery telemetry collapses per thread.

07 · Attention

Everything badges, almost nothing pushes

Four ceremony levels — push, in-app alert, badge, digest. Every pending act gets a queue row the moment it exists; policy only decides which ones also interrupt. Severity never drives it; the kind of act owed does.

What pushes

SituationCeremony
walk-lane findings returnOne push at report-landing, opening the drain — never per finding; the walk is one seated conversation
batch screens (apply / decide / route)Badge + digest — made calls arrive for a scan and a veto, not an interruption
three-strike consult · replan verdictPush — the loop has genuinely stopped needing judgment
typed-confirm (never-auto) gatesPush — the product itself refuses to proceed without the human
task-loop gates · bootstrap asksBadge; escalation is the safety net
any session idle at a stop > 15 minEscalates to a push, once per attendance — a stopped session is spent attention nothing is buying
teammate comment on an open gateBadge on the card + an unread indicator on the confirm control — a sign-off can't be finalised past an unseen concern

The rules that keep it honest

  • Two-level activity. App open → OS pushes downgrade to in-app alerts. Focus is scoped to the topic thread, so attention to one topic never suppresses a sibling's urgency — and a session you just left gets a grace period before it escalates at you.
  • Quiet hours. Overnight, pushes accrue into one morning roll-up. Nothing is so urgent it beats sleep; the queue has it either way.
  • A durable push ledger. Every push decision is recorded — a bridge restart re-pushes nothing.
  • A watchdog for the watcher. Escalation lives in the bridge, so the SPA's service worker alarms when the bridge itself goes silent: a dead notifier is a visible state, not a quiet one.
  • The floor guarantee. With every notification off, queue + badges alone suffice. Push is acceleration, never the only path to a pending decision.

The overnight test (a walkthrough finding, now a done-criterion): a background reviewer returning at 2am produces no night-time push, one report-pending queue row, and one morning roll-up that opens directly onto the drain.

09 · Hardening

Ten review passes before a line of code

The plan set was attacked the way the product attacks its own work: parallel adversarial reviewers, findings verified against the codebase before acceptance, every confirmed finding folded back in — and a ledger recording all of it.

The campaign

Round one hit the plans from five angles: intent fidelity, technical ground truth, scope and sequencing, a 54-item coverage inventory, and buildability. Round two hit the freshly written specs with consistency and sufficiency passes, then failure-modes-and-concurrency, a two-persona day-in-the-life walkthrough, and an upstream-fit review. Roughly ninety findings survived verification; the best of them changed the design:

  • The phantom-gate bug — the engine renders auto-mode menus explicitly marked "do not stop"; naive ask detection would have carded gates the product had already sailed past, and answering one injects a stray key. Caught by the consistency review; killed by the STOP-instruction rule.
  • Dedupe swallowing reality — content-hashed event ids made a reopened-and-recompleted topic invisible. Fixed with occurrence-unique discriminants and a two-layer stream.
  • The missing epoch — a rebase or branch switch would have silently shifted every cursor and diff base. Now detected at boot; degradation is visible.
  • The MCP injection hole — a model in any MCP host could have synthesized a typed confirmation. Typed-confirm gates now require user-gesture attestation, with a negative parity test.
  • The overnight strand — a returned review report had no queue row and its push was structurally impossible. Both fixed; the case is a done-criterion now.
  • The recorder circularity — Phase 0's fixtures needed Phase 2's parser. Resolved: v0 converts a terminal session; the live recorder waits for phase 2.

Full ledger with dispositions: ui/plans/REVIEW.md.

Giving back upstream

The reviews also judged what the product itself should gain — as its own maintainers would, against its own doctrine:

propose now · broader presence propose now · read-only currency verb propose now · never-auto surface export later · lane recording at agent ack later · render journal (the reshaped outbox) withdrawn · park origin token withdrawn · engine tasks verb

The pattern in the keepers: each closes a gap the product has independently of any UI — heartbeats its own reliability page already promises, a version surface its own boot story implies, an invariant its own gates already encode. Proposals that only served the bridge didn't survive the review.

Next milestone: Phase 0 — the specs are its entry criterion and they're written; first code is the monorepo, the event spine, and a fixture converted from a real terminal session.
