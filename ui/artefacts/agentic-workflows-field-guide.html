01 · Overview

A phased engineering process for Claude Code

Claude Code is a capable engineer with no memory and no process. Agentic Engineering Workflows adds both: discuss, specify, plan — then let it build, hands off, while every decision lands in a versioned document in your repo.

your project
$ npx agntc add leeovery/agentic-workflows
# then, inside Claude Code:
/workflow-start

That is the whole interface. Describe what you want to build and the right pipeline picks you up: a discussion that pushes back, a specification you approve, a plan broken into tasks, then implementation running in a gated test-first loop while you do something else. Kill the session whenever — the next one resumes from disk, exactly where it stopped.

◆ recall

Real memory

Everything the process produces is indexed locally with provenance. “Why did we rule out email as an identity field?” has a citable answer months later — and dead ends are remembered, so no future session re-explores them.

◆ autonomy

A loop you can leave alone

Agentic loops fail when the agent improvises. Here the thinking is front-loaded into discussion and specification, so implementation executes decisions that are already written down — task by task, test-first.

◆ enforcement

Spec-driven, by construction

A deterministic engine owns every state transition. Phases can’t be skipped, status displays are computed from disk rather than remembered, and Claude cannot editorialise your status.

What a session looks like

Every menu and status display below is emitted byte-for-byte by the engine, computed from state on disk. One screen shows all your work — active units, the pre-pipeline inbox, and the routes into each.

02 · First principles

Why it’s built this way

Three commitments shape everything the system does. Understand them upfront and the rest of this guide reads as consequences, not rules.

◆ commitment 1

Documents drive the work

Every phase produces a durable document in your repository — not notes the system keeps for itself, but the working material of the next phase and the record you approve along the way. Thinking is front-loaded into writing, so building becomes the execution of decisions already made. That’s why a spec exists before a plan, and a plan before code.

◆ commitment 2

A deterministic core owns the state

The assistant reasons, proposes, and talks with you — but it never decides on its own what the true state of your work is. Anything computable from disk is computed the same way every time by a rule-bound core. There is one authority on what is true, and everything reads from it. The system does not drift.

◆ commitment 3

Work is validated against what was agreed

“Done” is not a feeling. The final phase holds the delivered work up against the record that produced it — the discussion that shaped it, the spec that defined it, the plan that scheduled it — and confirms they match. The loop closes.

The token argument

The engine exists for an economic reason before an ideological one. Before it, every session paid to rebuild the same facts: reading through directories to infer progress, recomputing which phase each topic occupied, redrawing the same dashboards from written instructions, turn after turn. That is a great deal of a model’s finite attention spent reconstructing things that had not changed.

The obvious alternative was considered and rejected: hand the whole orchestration to plain code and call the model only as a hired hand through an API. That trades away the thing that makes the model worth having. So the design inverted instead — the assistant stays the driver of the work; the code becomes a reliable thing it consults. A single request now returns a finished snapshot of the state, and the model reads it rather than rebuilding it. Less is spent on bookkeeping, more on your actual problem — and the bookkeeping is correct every time rather than usually.

The division of labour in one line: judgment decides, code records.

Guarantees you can feel

A system you hand months of work to has to be trustworthy in a specific way: it must not quietly drift. The status it shows you today should mean the same thing tomorrow; a decision captured last week should still be there next month; a crash mid-task should not leave you guessing what actually happened. You don’t manage any of the machinery below — you just never experience the drift it prevents.

  • One authority on state. Status is derived from your files, not remembered; a phase is complete because the record says so, not because someone said “done”. Resumption is exact about decisions too: a question you answered before a crash is not asked again, and half-done work is picked up precisely or retired visibly — never silently rerun, never silently dropped.
  • Written down as it happens. Finished thinking lands in git continuously — at natural breaks, before context refresh, as each document completes — never left floating in a conversation that could be lost. Each commit is scoped to the action that produced it, so parallel work is never swept into a record it doesn’t belong to.
  • Files stay current with the design. As the system improves, older projects are brought forward at start-up — safely, repeatably, with a plain-language summary when anything moved. Where an update must transform judgment-written content, code alone isn’t trusted to have matched it: verification notes are left behind and checked, with judgment, before you confirm.
  • Never read over stale ground. Move something a later phase was built on and that phase is marked input moved at that moment — visible on every menu, routed back to instead of past, refusing sign-off until genuinely reconciled. Staleness travels hop by hop, in the open — never as a silent cascade (page 10).
  • Two sessions don’t trample each other. Every running session leaves a per-topic heartbeat: the epic view strikes through topics open elsewhere, background analyses hold off while a peer is live, and a crashed session’s heartbeat is recognised as dead rather than blocking you forever.
  • Every path is rehearsed before it ships. The system’s own test bed replays every pipeline end-to-end against the deterministic core — each work type’s full arc plus the awkward edges — auditing the entire recorded state after every step. It is aimed squarely at the worst class of bug: the one that writes fine, raises nothing, and shows up three phases later as a menu that looks wrong.

03 · Work types

Five shapes of work, five pipelines

Work comes in five shapes, each with a pipeline suited to its size — from months of multi-topic discovery down to a one-file fix. You never pick a pipeline by hand: describe the work and Discovery settles the type with you.

Two ideas that make this work

  • Discovery is universal. Every work type begins with the same first phase, which confirms the type, shapes an outline, and commits the work unit to disk before routing into the pipeline. Nothing persists before that commit — abandoning a conversation early leaves no debris.
  • A work unit is an instance of a type. “auth-flow” might be a feature; “payments-overhaul” an epic. Each gets its own directory under .workflows/ and its own manifest, so many units can be in flight at once — even in parallel sessions.

When work changes shape

Shapes aren’t prisons. A feature that outgrows its scope pivots into an epic, one that belongs inside an epic gets absorbed as a topic, finished work reopens cleanly, and a spec that turns out to be project-wide gets promoted to a standing document. The full set of reshaping operations — and the input moved machinery that keeps them safe — has its own page: 10 · Changing shape.

03 · Phases

Nine phases, three stages

The phases group into three stages — the three D’s. Discovery explores and decides, Definition specifies and plans, Delivery builds and verifies. Each phase writes a durable artifact before the next begins.

Expand any phase for what it actually does. The right-hand tag shows which work types pass through it.

Discoveryexplore & decide
▸1 · Discoveryevery work type

The universal first phase. You describe the work; Discovery confirms its type, shapes the outline, and commits the work unit — the durability boundary where the manifest, session log, and any seed material land on disk. For epics the same conversation continues into topic curation: naming topics, routing each toward research or discussion, and synthesising per-topic briefs that seed the later phases. Existing files you share are attached as imports and surface through the knowledge base.

▸2 · Researchepic · feature · cross-cutting (optional)

Explore — feasibility, market, viability, early ideas. Scoped per topic, one file per topic. A background review agent challenges topical gaps while you work, and a document review reconciles the session against the file at conclusion, catching substance the conversation produced but nobody wrote down. Deep-dive agents can investigate independent threads in parallel.

▸3 · Discussionepic · feature · cross-cutting

An organic conversation that pushes back, guided by a live map of points moving pending → exploring → converging → decided. Off-topic concerns don’t derail the session — they’re rerouted into the right topic’s triage queue and block that topic’s conclusion until drained. The same gap-challenging background agent and closing document review apply.

▸4 · Investigationbugfix only

Bugfix’s replacement for research and discussion: symptom gathering plus code analysis, driving to a root cause before anything is specified or fixed.

Definitionspecify & plan
▸5 · Scopingquick-fix only

Quick-fix’s single-pass definition: context, spec, and plan in one sitting, sized for a change that doesn’t warrant the full pipeline.

▸6 · Specificationepic · feature · bugfix · cross-cutting

Turns the decided record into a standalone spec you approve. The spec makes decisions clear, never makes them: when a source conflicts, the conflict comes to you; when a genuine gap appears, it lands back in the owning discussion rather than being papered over. Spec review then runs three sequential verification passes — claims are re-measured against the actual code, fidelity is checked against sources (in both directions), and a standalone gap analysis closes it out. Specification hard-blocks on an unsettled discussion: a spec cannot be reliably built from an in-flight record.

▸7 · Planningepic · feature · bugfix

Defines how: phases, tasks, acceptance criteria. Tasks are written to the tracker format you choose — Tick, local Markdown, or Linear — behind one adapter contract, so the rest of the pipeline doesn’t care where your tasks live.

Deliverybuild & verify
▸8 · Implementationepic · feature · bugfix · quick-fix

Executes the plan through a gated test-first loop — executor, reviewer, and a fix cycle capped at three attempts before you’re consulted. Each task lands as its own commit. Covered in full on page 06.

▸9 · Reviewepic · feature · bugfix · quick-fix

Per-task verifiers report only what is wrong, naming the concrete failure, whether it’s inside the delivered change-set, and whether it spreads. Every finding is verified against the code before anything acts on it. Contained in-scope fixes are applied and committed in-session; a spreading problem fails the review and triggers a replan — a verdict that is derived, never chosen. Out-of-scope findings are banked durably and offered later, never silently filed.

05 · Under the hood

Skills in tiers, an engine underneath

The prose that guides each conversation is organised in tiers of skills, and none of them holds state. A deterministic engine owns every transition, every status display, and every commit — Claude narrates; the engine records.

What the engine buys you

  • Durable by construction. State transitions are transactions: validated first, refused cleanly, committed atomically. A crash mid-anything leaves files byte-identical, and the next session resumes from disk.
  • Displays you can trust. Menus and status screens are computed from disk and emitted byte-for-byte. The model cannot claim a phase is done that isn’t.
  • Zero-maintenance upgrades. Updates ship migrations that bring existing projects in sync on the next run — no manual steps.
  • A full audit trail. Every phase, decision, and review finding lands in git through engine-owned commits, versioned alongside your code.
  • Session awareness. Parallel sessions see each other through per-topic presence heartbeats — a topic held by another live session is struck through, skipped as a recommendation, and confirm-gated.

What lands on disk

Everything lives under .workflows/ in your repo — human-readable Markdown plus a manifest per work unit. Commit it and your whole team (and Claude Code for Web) shares the same state.

.workflows/ ├── manifest.json — work-unit registry · project defaults ├── .inbox/ — captured ideas · bugs · quick-fixes ├── .roadmap/ — the product layer above work units ├── .baseline/ — brownfield assessment docs ├── .knowledge/ — the local knowledge-base store └── payments-overhaul/ — one work unit (an epic) ├── manifest.json — engine-owned state ├── discovery/sessions/ — the running exploration record ├── research/{topic}.md ├── discussion/{topic}.md ├── specification/{topic}/specification.md ├── planning/{topic}/ — plan + task files ├── implementation/{topic}/ └── review/{topic}/report.md

An expert in the room

The system is multi-agent by design — more than thirty specialised agents work alongside the pipeline, each reading its material cold and handing back a structured result. Who they are, when they act, and the idea about context that justifies them all has its own page: 09 · The agents.

06 · Implementation

The hands-off loop

By the time implementation starts, every decision is written down. What remains is execution: task by task, test-first, with a reviewer at the gate — and you only when the loop earns your attention.

Why it stays on the rails

  • Graduated autonomy. Every gate accepts auto mode. Hand over as much or as little of the loop as you trust, per work unit, reversibly — from approving each task by hand to a fully unattended run.
  • Engineered context, not a dumped transcript. Each agent sees briefs, read-in-full contracts, and scoped handoffs — the context the process built for it, not whatever happened to be in the window.
  • Environment aware. Implementation discovers your linters and project-specific skills and applies them through the test-first cycle and review.
  • Convergence diagnostics. A loop that stops converging is diagnosed rather than repeated: cycle tracking distinguishes what’s resolving from what’s recurring before escalating to you.

Then review, with teeth

After implementation, the review phase re-verifies the whole delivered change-set task by task (page 04, phase 9). The verdict is binary and derived: contained in-scope problems get fixed in-session; a spreading one fails the review and sends the work back to planning. There is no “pass with notes”.

07 · Memory

A memory that cites its sources

Not a scratchpad. Every completed artifact is indexed locally with provenance, so later phases — and later months — can ask questions in plain language and get answers that point at the document that decided them.

Semantic or keyword — both are supported

With an OpenAI-compatible key (entered in your terminal, never the chat) the store uses embeddings for semantic recall. Without one it runs in keyword-only mode — a supported degraded mode, not a broken state. The first /workflow-start walks you through the choice conversationally.

Starting in an existing codebase

A project that grew up on the workflows accumulates its record as it goes. A project you install them into has none — so the first run offers a baseline assessment. Research agents fan out over the code, then the system interviews you about what they found: the intent, constraints, and history only you can supply, with the evidence woven into every question. The answers land as a doc set the knowledge base surfaces in every later phase — observed structure, your stated reasoning, and honest open questions kept separate. It’s pausable mid-interview, resumable from the start menu, and expandable as the product grows.

The product roadmap

Above the work units sits a product layer for the conversations that aren’t yet a piece of work: horizons you name in your own release language, capability-grain items with pointers back to the thinking. Ideas surfacing mid-work park there with one confirmed line (“that’s a v2 thing”), everything unpulled stays visibly waiting, and a pull births a work unit already fenced to the slice you chose. Cancelling delivery hands the item straight back.

08 · Collaboration

How the system works with you

The amount of you a phase needs is not constant. It is widest at the start and narrows toward the end — a cone, from a conversation where you shape everything to a delivery loop that mostly runs itself.

Stops that mean it

Everywhere the system needs a decision from you, it stops and waits — structured decision points, not the assistant checking in for reassurance. It will not answer a gate for you, even under pressure to keep going: a stored preference or project default pre-fills a question, it never skips one. “The user already decided this” is exactly the shortcut the design forbids.

What a stop shows you is written for the person deciding, not the machinery that produced it: findings and outcomes are told in the product’s terms first — what you’d see happen and where — with the same facts retellable from the code’s perspective, or verbatim, on request. You choose the lens; the record on disk stays fully technical either way.

Ask or decide

Before any question reaches you, the system locates where the answer lives:

  • The record — decisions already made, sibling artifacts, convention, first principles. When these admit exactly one defensible answer, the call is made, stated in a line, and recorded with its derivation — never presented for ratification. A settled call posed as a question costs you a full read to say “yes”.
  • You — taste, appetite, product intent, priorities, facts only you hold. Then it asks, and the question carries the fork: what turns on the answer, not a recap of everything already known.

Three overrides send an otherwise-derivable call to you anyway: the consequence leaves the topic (it would amend ground outside the current artifact), it’s expensive to reverse (wrong means rework, not a patch), or the system doesn’t believe its own derivation — in which case it says so plainly. When it’s unsure which side a point falls on, it asks: a needless question costs one exchange; a wrong silent call is a decision you never saw.

Lanes — ceremony by the move owed, never severity

Background agents run while you talk — gap analyses, reviewers, perspective panels. Their findings don’t arrive as a wall of notes: each is classified by what it asks of you, and each class gets exactly the ceremony it earns.

The surfacing itself is polite by rule, not by mood: the report is announced first with a micro-menu and drained only when you opt in; if you’re mid-thought it waits for a natural break; and a maturity-graded sufficiency bar keeps noise down — in early exploration findings are fuel, but once ground is settled, a finding must survive the consuming-phase test or it lands in the report as an Observation, never raised at you.

Managing the discussion itself

  • A live map, not a transcript. Discussion runs against a map of points moving pending → exploring → converging → decided, so both of you can see what’s settled and what’s still open — and conclusion is blocked while anything genuinely isn’t.
  • Off-topic is captured, not chased. Raise something that belongs elsewhere and it’s rerouted into that topic’s triage queue with one confirmed line, keeping the current thread on course.
  • A challenger in the background. While you talk, a review agent hunts topical gaps; at conclusion a document review reconciles the session against the written file, catching substance the conversation produced but nobody wrote down. Both are mandatory before a topic concludes.
  • Perspective panels. For contested decisions, agents argue both sides independently before a synthesis reaches you — you get the tension, not a premature consensus.

The voice it holds

The conversational register is a colleague’s, by explicit rule: it has a position and says what would change its mind, it opens with substance rather than “great question”, it cites the record (file:line, the actual decision) rather than a fabricated past, and it ends turns without ceremony. Menus and status displays are exempt — those are engine-emitted bytes it cannot editorialise. How hard it pushes back is set per phase; the manner stays constant.

The through-line: eager to do the work, unwilling to make your decisions. It drafts, analyses, builds, and checks tirelessly — and stops dead at the line where a choice is yours, handing that line over only when you deliberately choose to hand it.

09 · The agents

Thirty agents, one idea about context

The session you talk to was in the conversation — it remembers what was said, what was meant, what was waved off. That memory is an asset for catching what was discussed but never written down, and a liability for judging what was written down: a participant reads a document already knowing what it was supposed to say.

So the system pairs the two. A sub-agent has no such memory — it reads the artifact cold, with nothing but the artifact in front of it, and that is exactly what makes its critique worth having. The orchestrating session catches what was said but not written; the fresh agent catches what was written but not right.

The common shape

  • Stateless, every time. Each run starts from nothing and is handed its inputs in full — no drift, no accumulated bias.
  • Findings go to files, not the chat. Most agents write reports rather than flooding the conversation; what reaches you comes through the lanes (page 08).
  • They propose; they never commit. No agent touches git or changes your project’s state. Committing and record-keeping belong to the orchestrating session and the engine alone, and nothing an agent produces enters a plan or spec without passing a gate you control.

Context engineering — what each agent is given

The context an agent sees is built by the process, not inherited from whatever happened to be in the window. Three instruments do the work:

  • Briefs. An epic’s wide, expensive shaping conversation is projected into a per-topic brief — the soft decisions and why, the paths rejected and why, the open questions carried forward. Each topic’s downstream phase reads its brief in full as starting context, inheriting the thinking instead of re-deriving it and re-walking the same dead ends.
  • Read-in-full contracts. Durable phase inputs — the seed, the brief, completed research — are read whole by the phase that consumes them, at its own initialisation, never paraphrased through a hand-off. A relay can compress; a contract can’t.
  • Scoped hand-offs. What passes between skills is the minimum that routes the work — work type, work unit, topic — not a dumped transcript. And because instructions held only by reference can drop out when a long session’s context is compacted, skills re-load their operating rules by name after every refresh rather than trusting memory.

Why this matters: most multi-agent failures are context failures — the agent that saw too much and anchored, or too little and guessed. Engineering what each mind reads is the quiet half of the system’s reliability.

10 · Lifecycle

When work changes shape

Work does not always run cleanly from start to finish in the shape it began. The system treats that as normal — a small set of deliberate operations you invoke, never something done behind your back.

The three states — and no one-way doors

Every work unit is in-progress, completed, or cancelled. Active work is what you see by default; closed work sits behind the v/view door, kept but not cluttering. Cancelling also removes the unit’s material from the knowledge base — an abandoned decision should not resurface as advice — and closing a unit clears its scratch working files while keeping every real artifact. Nothing is final: reactivating a cancelled unit restores its material to the knowledge base, since it is live thinking again.

Pivot and absorb — the two reshapes

  • Pivot: a feature that grew. When one feature’s discussion starts feeling like several discussions trying to happen at once, that’s the definition of an epic. Pivot converts it in place — everything already done is kept, and the work gains multi-topic structure. Carry straight on in the epic or step back.
  • Absorb: a feature that belongs elsewhere. The opposite: a standalone feature that is really one facet of an epic already underway. Absorb moves its discussion, research, seeds, and imports across as a new topic, then deletes the redundant feature — git history remains as provenance. It’s guarded (a discussion must exist, nothing past discussion, an in-progress epic to receive it), because merging half-specified work would tangle two pipelines; when a guard blocks, you’re told which one, and nothing is touched.

Topics inside an epic

Epic topics have their own lifecycle. Cancel a dead-end topic without touching the rest — it stays visible as a record but drops out of progress counts and stops holding up dependent phases. One guard: cancelling a discussion that a live specification is built from would leave that spec standing on rejected ground, so the cancel names the spec that falls with it and, on your confirmation, cancels both together. Reactivating restores the topic’s prior state, returning any completed thinking to the knowledge base.

Promoting a spec

Occasionally a specification written for one topic turns out to describe a project-wide pattern — a convention the rest of the codebase should follow. It can be promoted into its own cross-cutting concern, becoming a standing document of record instead of a step toward one build: the same recognition cross-cutting work is built around, applied after the fact.

Revisiting finished work — the input moved ripple

Completed phases reopen cleanly, without reactivating anything. What makes this safe is that the system tracks what the revisit sits underneath:

Moving ahead of yourself, safely

Navigate forward out of turn and the system warns rather than blocks: early on it counts what’s unfinished upstream; from planning onward it reads the build order and names exactly which topics you’re stepping past. You can proceed anyway — if the earlier work later changes what you did, the mismatch is re-analysed and surfaced on your return. Specification is the one deliberate wall: a spec is built from the settled discussion record, so it refuses to start over open discussions and blocks while a source discussion is reopened. Everywhere else an informed nudge serves better than a locked door; there, a spec built on moving ground would be a false contract.

11 · Menus

Reading and driving the menus

Every screen below is computed from disk and emitted byte-for-byte by the engine — the menu you see is the state you’re in. Here’s the grammar they all share, then the four screens you’ll live in.

The grammar every menu shares

  • Numbered rows are things; lettered rows are actions. 1, 2, 3… select a work unit, topic, or inbox item. s/start-style rows are actions — type the key (s) or the word (start), either works.
  • Plain words always work. You’re in a conversation, not a form. “Add 2 and 4”, “cancel the tooltip one”, “archive the bugs” — the menu maps your phrasing onto its rows, selection included. Asking a question instead of choosing is fine too; the menu waits.
  • (recommended) is a suggestion, never a rail. At most one row per menu carries it — the engine’s read of the best next move, from phase order and the build order. Every other row stays open.
  • Menus only offer what state allows. A row that would be invalid simply isn’t rendered: no absorb without an in-progress epic, no reactivate without a cancelled topic. If you don’t see an action, the state doesn’t permit it yet.
  • y/yes rows are commit points. The big one is discovery’s shaping gate — until you say yes there, no work unit exists on disk. Confirms are where things persist, atomically, in one commit.
  • b/back is always safe, and so is walking away. Every menu is a stop: the system waits, state is already durable, and killing the session mid-menu leaves nothing half-done.

p/pivot      → Feature → epic, when scope outgrows one topic
a/absorb     → Merge this feature into an epic as a topic
v/view-plan  → Read the plan and task status

The habit that matters: trust the recommendation but don’t obey it. The menus are computed so you can’t get lost; the (recommended) row is where the process thinks momentum is, and everything else is one keystroke of disagreement away.

12 · Worked example

A feature, end to end

Every mechanism in this guide, threaded through one piece of work: a retry idea that surfaces mid-session and ends as shipped, reviewed, remembered code. Illustrative, but true to how each step behaves.

  1. It starts as an interruption

    You’re deep in unrelated work when the thought lands: webhook deliveries should retry with capped backoff. You say “log that as an idea” — the capture skill writes one file to .workflows/.inbox/ideas/ and the conversation you were having keeps moving. No pipeline, no ceremony, nothing forgotten.

  2. Pickup, days later

    /workflow-start shows the idea sitting in the inbox. You press i, add it to the working set, and choose w/work. Discovery opens with the captured note as its starting material.

  3. The shaping gate

    A short conversation settles what this is — one coherent topic, so a feature. Then the one hinge:

    discovery
    ◆ Have I read this right?
A feature — smart retry with capped backoff for webhook delivery.

y/yes        → that's the right shape, set it up
o/other      → it's something else (tell me what)
Keep shaping → tell me what I'm missing

    Until you say yes, nothing exists on disk. On yes, everything lands atomically in one commit: the work unit smart-retry gets its home and manifest, the inbox note moves in as its seed, and a session log captures the shaping. Walk away before this and there is zero residue.

  4. Discussion

    Routed to discussion (the ground is known; no research needed), the conversation works a live map: retry policy, failure classification, idempotency. It pushes back — “I’d cap at five attempts unless delivery volume says otherwise; what changes your mind?” Mid-way you mention rate-limiting the retry queue; that belongs to another concern, so it’s parked with one confirmed line rather than chased. Behind you, a background critic flags that nothing covers permanent failures — a real gap, raised at a natural break, and the map gains a point. At conclusion a document review reconciles the session against the written file, and the record lands: decided, with the rejected paths (exponential jitter, dead-letter-first) recorded alongside the reasons.

  5. Specification

    The spec extracts the decided record — never deciding anything itself. A claim about the current delivery code is measured, not assumed: the checking command and its result are recorded in the spec. One extraction turns out to conflict with a decision the discussion actually made; the conflict comes to you as a numbered choice, and your answer is mirrored back into the discussion’s timeline. Then three validation agents run in strict sequence — claims re-measured against the tree, fidelity checked against sources in both directions, a cold gap read — and you sign it off. From here on, this document is the contract.

  6. Planning

    Four agents build the plan in relay — phase structure from the spec, tasks per phase, full task detail, then dependencies and ordering — with you approving between them. Tasks land in the tracker format you chose at setup. Two plan validators trace and stress-read the result before you approve it.

  7. Implementation

    The loop runs: executor writes each task test-first, the independent reviewer checks it against the acceptance criteria, and each pass lands as its own commit. Task three fails review twice — the findings loop back — and passes on the third attempt, one short of consulting you. After two hand-approved gates you switch the gate to auto for the rest of the sitting. When the phase’s last task lands, the consolidation finder reads the combined surface and spots two near-identical backoff helpers no single task could see; the merge becomes a gated task you approve before the phase closes.

  8. Review, and the close

    Verifiers re-check every task against the spec and plan. One in-scope, contained finding — a missed error branch — is verified against the code, applied, and committed in-session. One out-of-scope observation is banked on the manifest for later, never silently filed. The verdict is a derived pass; the unit completes, its scratch files are cleared, and its discussion and spec are indexed into the knowledge base.

  9. Months later

    A different session, planning a related queue, asks why fixed backoff was chosen over jitter. The knowledge base answers with provenance — the discussion file, the date, the rejected path and its reason. Nobody re-litigates it; nobody re-walks the dead end. That’s the payoff the whole pipeline was built for.

The inbox habit

The inbox is the pre-pipeline holding area. When you next run /workflow-start, pick up one item — or several of the same kind — and promote them into a new work unit, where they become its seeds: the origin material the discovery conversation starts from. Items you decline archive rather than delete, and can be restored later.

Trust dials worth knowing

  • Gate modes. Every approval gate in implementation can be set to auto, per work unit, reversibly. Start supervised; loosen as it earns it.
  • Task format. Plans write tasks to Tick (native dependency graphs, built for this), local Markdown (zero dependencies), or Linear (your team already lives there) — chosen once, per project or per plan.
  • Edited artifacts are noticed. Documents are checksummed. Hand-edit a research file and the system offers to re-analyse; edit a spec and it offers to replan. Nothing silently drifts.
  • tmux session labels. Opt in once and your session renames to show exactly where it’s working — myproject · payments · discussion · auth-flow — restoring the original name on exit.

A working rhythm

The shape that emerges in practice: spend your attention where it compounds — the discussion that pushes back and the specification you sign — and let the delivery stage run gated in the background, in tmux, while you think about the next thing. Capture stray thoughts the moment they occur; the inbox and roadmap make sure nothing falls on the floor, and the knowledge base makes sure nothing is re-litigated.

Where to go deeper: the repo’s docs/ directory covers every phase in detail, the engine, the knowledge base, all the agents, and the history of the project — start with docs/how-it-fits-together.md.

14 · History

Where it came from

The one page that speaks in the past tense. The shape of the system makes more sense once you know which problems bent it into place — and every era tells the same story: one more class of work moving from “the model re-derives it in prose” to “code answers, the model consults”.

  1. Late November 2025 — the seed

    A couple of markdown files

    The very first taught Claude Code to write a planning document before writing code; within the hour it was a three-phase idea — discuss, then plan, then implement. Everything since is that one conviction deepened: documents drive the work, and the quality of the document chain sets a ceiling on the quality of the code.

  2. Winter 2025–26 — the prose era

    Everything carried in the model’s head

    Review, specification, and research joined the family, work split into distinct pipeline shapes behind one entry point, and installation got a real CLI. But all state lived in prose: Claude worked out where things stood by reading around directories, and every dashboard was hand-drawn text, re-derived from written instructions each time it was shown.

  3. March–April 2026 — state finds a home

    The busiest month

    A project’s state moved from narrated markdown into a structured record with a real read-and-write surface. The inbox landed, the project cut its first release as an installable product, and in April it gained a memory: completed artifacts became a searchable index with provenance, so a phase could finally ask whether a question had been settled before.

  4. May 2026 — discovery

    The front of the funnel

    An “inception” idea became the universal first phase every piece of work begins in, with the topic map and self-healing analysis for large initiatives. This is also when the firmness gradient was articulated out loud: discovery is soft, discussion hardens the thinking, the specification is golden.

  5. June 2026 — the bug that built the engine

    A wrapped line snaps a tree

    Resuming a large epic, two topics in the hand-drawn map wrapped past their margin and broke the tree on screen. The fix was trivial; the diagnosis was not: layout fully determined by the data was being reconstructed, by hand, from prose — “wrong by default, correct only when watched closely” is not a rendering strategy. A survey found the pattern everywhere. Handing orchestration to code was ruled out — the model is the better driver — so the architecture inverted the other way, and the engine was born. Judgment decides, code records.

  6. June–July 2026 — the re-platforming

    A rebuild in waves

    Core skeleton, then the epic dashboard, the state transactions, the start-up pipeline, migrations, the implementation loop’s machinery, the reshaping operations — each wave proven against a live copy of a real project, with an endgame of adversarial review fleets, a certification pass, and a final re-review before the record closed as complete.

  7. Late July 2026 — the last margins

    The markdown left saying only content

    The final hidden state — background-agent bookkeeping and gate decisions living as annotations inside the documents they described — moved into engine state, with a migration carrying live projects across. The proving mattered more than the move: rehearsal first, then reviews that hardened from sampling to enumeration, until the campaign ended the only way it was allowed to — with a round that came back empty-handed.

The through-line: at no point did the conversation stop being the driver. That balance — not any single subsystem — is what the system is.
