# Engine Commands

*Reference for **[leeway-engine](../SKILL.md)***

---

The CLI door: `node .claude/skills/leeway-engine/scripts/engine.cjs <command> [args]`. Skill prose prescribes these calls at exact points; this catalogue exists for understanding a command's full contract.

**Response contract (every mutation/transaction):** one decision-ready JSON line on stdout — `{"ok": true, …}` with derived state riding so no follow-up read is needed. Failures: `{"ok": false, "error": "…"}` on stderr, exit 1. Knowledge-base side effects are warn-don't-block — failures land in `warnings`, never abort. Commands that commit report `committed` (short sha, or `null` plus a note on a clean scope — the code commit, `commit --paths`, a list of `{repo, sha}`, `[]` beside the note); commands documented as commit-free rely on the calling flow's commit cadence. The workflows' state is `.leeway/` in the repository's main checkout, a worktree of its own branch, `leeway-state` (`kernel/state-root.cjs`, `domain/state-worktree.cjs`): a commit there — a state commit — is made on that branch and pushed, and a commit of code or of the files the workflows own in the code tree on the branch checked out (see **`commit`**). Every command runs whole under the state's writer lock, `.leeway/.lock`, its writes and its commit one hold, so no peer's write lands between them — but those `WRITER_LOCK_EXEMPT` in `engine.cjs` names, which read, write outside the state, or take the lock around their own writes alone, and, beside them, the `manifest` reads and the code commit (`commit --paths`); the work unit's lock and the project lock the entries below name are that one lock, and a write refuses where the state worktree is not there. Every engine-made commit is confined to the paths its action wrote — a state commit with the layout's logs changed since — and none carries the knowledge directory — git-ignored in the state, the store a derived index each clone builds for itself. One noun answers otherwise, deliberately: `knowledge`, the knowledge base's door, answers in text on both streams (see its **Answers in text, not JSON**).

## Grammar

Every command follows six rules — new commands must too:

1. **Identity is positional, in containment order**: `{work-unit}`, then `{topic}`, then `{item}`.
2. **Required values with closed vocabularies are positional enums** (`discussion-map set … {state}`, `cache stamp {wu} gap-analysis`, `workunit create {wu} {work-type}`).
3. **Payloads are always named flags, even when required** (`-m {message}`, `--findings-file {path}`).
4. **Optional modifiers and alternate addressing are flags** (`--skipped`, `--parent`, `--external {id}`).
5. **Mappings are `key=value` pairs** (`discovery-map sequence {wu} {topic}={order} …`).
6. **A reserved word sharing a slot with user-named values must be a flag** — why `commit --inbox`/`--workflows`/`--roadmap` are flags beside positional `commit {work-unit}`.
Two carve-outs. The **`render` surface catalogue** passes every non-address scalar as a flag (`--gate`, `--phase`, `--m`, `--variant`, …), including required closed vocabularies — the address is the only positional. Uniformity across the render surfaces beats rule 2 there. The **`knowledge`** noun takes identity as flags (`--work-unit`, `--phase`, `--topic`), against rule 1: each is a filter narrowing the chunks a verb acts on, never an address, and a query's positionals are its search terms.

**The guards** answer otherwise too. `layout guard`, `brief guard` and `shell guard` (`guards.cjs`) are Claude Code's hooks before a tool call — Write, Edit and NotebookEdit; Agent and SendMessage; Bash — which boot installs in every project's `.claude/settings.json`, each fed the call's JSON on stdin and acting from its `cwd`, else the folder the hook runs for. Each answers in Claude Code's terms: silent where the call goes through as made; the hook's answer on stdout where it hands the call on changed; a refusal on stderr with exit 2, the code Claude Code blocks the call on. Any other failure lets the call through, and a stray argument is a usage error, exit 1. A guard stands before every call of its tools, so the shell door runs it before the engine loads anything else, loading only the guard's own module, and it takes no lock. Each is under its own noun: **`layout`**, **`brief`**, **`shell`**.

## Commands

**`boot`** — the entry pipeline (`domain/boot.cjs`). **The git floor.** First it reads the git on the PATH, once: one older than the engine's floor (`GIT_FLOOR` in `domain/git-floor.cjs`, 2.40.0 — the landing replays a task's commits with `git merge-tree --merge-base`), or none, stops boot before anything else runs. Then it drops the calling conversation's position — the start menu is no position — and appends the trust-log events any conversation keeps waiting (`trust-pending.jsonl`, see **`conversation`**), a boot that stops below included. **The state** comes next, before anything writes it (`domain/state-checks.cjs`), under a lock of its own in the main checkout's git directory, two boots checking one after the other. `.leeway/` is kept in the repository's own exclude file, which no branch carries. The remote is asked once where its `leeway-state` stands. A state branch this clone lacks is made from the remote's — a fresh clone — or, under a folder still there, at the commit the folder's files stand at, which the catch-up then moves on; one the remote lacks is pushed back to it. The worktree is added where it is gone, relinked where the project folder moved or was copied — a copy's state becoming its own, a warning naming the original, which is left untouched — and locked where it is not. With no state branch here or on the remote: a project on the layout before the state branch — `.workflows/` on the code branch checked out — stops for the migration, with nothing written; one whose repository holds the workflows' trace — the workflows' hooks in its `.claude/settings.json`, or a line naming `.leeway/` in its `.gitignore`, on any branch, the remote's fetched first, or in any tree checked out — lost its state, and boot stops until the person's yes, `boot --start-again`, which makes a fresh state; and a project with neither is being set up, and gets one. A fresh state is the orphan branch, its first commit (`chore: begin leeway-state`) built with plumbing so the main checkout's branch, HEAD and index are never touched — the state's `.gitignore` and the project manifest holding the project's `project_id`, minted there once and never changed, which keys the project's evidence in the trust log (`manifest set` refuses it) — then the worktree added and locked. Boot refuses, with nothing written to the state or the code, where the remote is out of reach and this clone holds no state branch of its own, where the remote's branches cannot be fetched to read the trace from, where a `leeway-state` holds code history, and where the state's folder stands in a shape it cannot account for — there while its branch is gone everywhere, or with another branch checked out. A remote out of reach is never read as holding nothing: boot works on what this clone holds, with a warning. **While the migration runs** — `leeway-state` checked out at `.leeway/` with no commit yet, and `.workflows/` still on the code branch checked out — boot takes the state as the migration's move left it: the worktree is locked where it is not, and nothing is made, restored or pushed; under the writer lock only the migrations run; and boot commits nothing, its session hooks written and left to the migration's commit. **Under the writer lock** (`.leeway/.lock`), held around these alone: the ledger's entries a killed write, or a commit git refused, left uncommitted are committed (`ledger: the entries a write left uncommitted`), a warning counting them — only where each is a whole line a read takes, else nothing is committed and a warning names the line; the catch-up from the remote runs (**`state-merge`**), whose stop on a manifest field both clones changed ends boot there; the session's own `.gitignore` gets the state's ignore line, `.leeway/`, the workflows' trace, committed on the branch checked out (`chore: ignore .leeway/, the workflows state`) as the session hooks are below; and the migrations run: `leeway-migrate/scripts/migrate.cjs`, resolved relative to the engine, from the code root, recording into the state's `.state/migrations` and journaling what a run owes the run that completes — its handbacks and its counts, so a run that stops at a directive or aborts loses neither — in the state's cache, `.leeway/.cache/migrate/`. **A stop** answers `{"ok": true, "state": "git"|"lost"|"migrate"|"merge", "warnings": […]}` and nothing else — `git` drawn by `render git-floor-stop`, `lost` by `render state-lost-gate`, `merge` by `render state-merge-gate` and answered by `state-merge pick`; `migrate` has no screen, the reshape's migration being the way on. **A directive** the migrations record does not hold stops the run (the format and the runner's stop are the header of `leeway-migrate/scripts/migrate.cjs`), and boot goes no further, committing nothing: it answers `{"ok": true, "state": "directive", "id", "file", "done", "of", "warnings": […]}` — the directive's id, `NNN-{slug}`, and its file, and its pieces done of all of them as its check counts them (**`migrate`**) — both left out where the check fails, as it may on what a session that died part-way left, and `migrate check` names why. `render directive-stop --directive <id>` draws the stop; the session carries the directive out and closes its checklist, which records it (**`checklist`**), then boots again — one start may meet several. Past the stop points, boot renders the ledger's copies under `.knowledge/` again (a failure a warning), then runs `knowledge check`, then — when ready — brings the store's keyword side in line with the files (the bulk `knowledge index` without its wait for vectors) and compacts it, launching the background `knowledge fill` for the vectors the store awaits. Where a decision landed unchecked and no late check has judged it, boot launches the late one-decision check, detached (**`ledger`**); what keeps it from launching is a warning. Response: `{"ok": true, "state": "ready"|"restarted", "migrations": {"changed": false, "ran": 0, "output": "<trimmed report>", "verify": [], "notices": []}, "knowledge": "ready"|"not-ready", "indexed": false, "compacted": false, "migrations_committed": null, "warnings": [], "tmux_labels": "no-tmux"|"on"|"off"|"prompt", "label_repaired": false, "session_hooks_installed": false, "gate_surface": "on"|"not-running"|"outdated"|"unavailable", "baseline": "none"|"native"|"in-progress"|"completed"|"skipped", "walkthrough": "none"|"walked"|"skipped", "github_rule_offer": false, "github_squash_offer": false}`. `state` is `restarted` where this boot started a lost state again on the person's yes, else `ready`. `github_rule_offer` is true where the state's remote is on GitHub, the code host's driver can set the rule, and the offer of a rule there against deleting or force-pushing `leeway-state` was never answered — `render github-rule-gate` offers it, and **`github-rule`** answers; `github_squash_offer` where the project lands through GitHub and the squash default was never answered — `render github-squash-gate`, answered by **`github-squash`**. The knowledge directory `.leeway/.knowledge/` — the store, its metadata, the knowledge config, beside them the store's writer lock (`.lock`) and the vector fill's claim (`.fill`) — sits in the one state every checkout and worktree of the project shares, git-ignored there and never committed. `tmux_labels` reports the session-label opt-in read from the project manifest's `defaults.tmux_labels` (see `session`): `prompt` means the session runs inside tmux and the choice was never recorded — leeway's one-time prompt keys on it; every other value renders nothing. `label_repaired` reports the `session repair` pass boot runs — true when a label on this terminal was put back to its original name: the calling session's own (leeway is the start menu), or a stranded one whose owner is gone; informational, nothing renders on it. `session_hooks_installed` reports boot's sync of the session hooks in the project's `.claude/settings.json` — SessionEnd's `presence cleanup` and `conversation end`, and PreToolUse's `layout guard` (matcher `Write|Edit|NotebookEdit`), `brief guard` (matcher `Agent|SendMessage`) and `shell guard` (matcher `Bash`), each its own group, for every project, SessionEnd's `session cleanup` and SessionStart's `session resume` while labels are on — true only when this boot changed the file; false when it already carried exactly those. Neither the hooks nor the state's ignore line above is written while git holds a merge, cherry-pick, revert, rebase or bisect open in the code tree — a later boot writes them. Boot commits its own change to either file confined to it, on the branch checked out (`chore: install workflow session hooks`), and only where that change is the file's whole difference from the branch: a file that also holds the person's own uncommitted changes is theirs to commit, a warning saying so, and the next boot commits the workflows' change once theirs is in; a file the project's git ignores is never committed; a commit git refuses is a warning, and the next boot tries again. When `migrations.changed` is true the hooks' commit is left to the reviewed `commit --migrations`, which takes every path the workflows own. Informational, nothing renders on it. Boot also tidies the conversation folders (see `conversation`) — every one, whichever project's conversation made it: a folder whose `transcript` names a file that no longer exists is deleted, unless trust-log events still wait in it, and nothing is reported. `gate_surface` reports the `leeway-gates` mod, part of the workflows. It runs only in Claude Code's terminal app or the Desktop app's Code tab (`CLAUDE_CODE_ENTRYPOINT` is `cli`, `claude-desktop` or `claude-desktop-3p`; not on the web, where `CLAUDE_CODE_REMOTE` is set), in a project that installed it (`.claude/skills/leeway-gates/`), from version 2.1.287 (read off `AI_AGENT`, `claude-code_2-1-287_agent`), where Claude Code loads mods by default. Boot reads and writes no settings file for it. Outside those two apps — the VS Code extension, a Desktop session that runs in the cloud (`remote_desktop`), any other entrypoint — in a project without the mod, or where `AI_AGENT` is absent or does not read as a version, it reports `unavailable`, and the workflows carry on with the text menus; at a readable release before 2.1.287 it reports `outdated`. Where the mod can run, `on` means it is running: its announcement, `LEEWAY_GATE_SURFACE=1`, is in boot's own environment; `not-running` means it is not — the session started before the mod was installed or updated, mods are turned off (`--safe-mode`, `--bare`, `"disableAllHooks": true`, or an organization's policy), or Anthropic's rollout switch serves installed mods off. leeway's Step 0.2 shows a notice on `not-running` and carries on with typed menus, and ends the session on `outdated`; `on` and `unavailable` render nothing. `baseline` reports the project baseline status from the project manifest (`baseline.status`) — `none` means nothing recorded yet (a missing manifest or unrecognised value also reads `none`), the state leeway's one-time Step 0.6 judgment keys on: a project that grew up on the workflows records `native` and is never asked again; a codebase that predates them gets the assessment offer. A `none` response additionally carries `"baseline_signal"` — the project's own account of what came before the workflows, read across every repo in it (the repos `code` reads), handed to that judgment as evidence to read: `{"root_date", "workflows_date", "commits_total", "commits_before", "history_before", "files_at_arrival", "tree_at_arrival"}` — the author date of the earliest first commit in any repo; the author date of the state's first commit, the workflows' arrival (null when the state holds none yet, so the whole history predates the workflows); every commit reachable from each repo's HEAD, summed — a project inside a larger repository reading the commits that touched its folder, and a shallow nested clone adding its tree alone; the commits before the arrival, summed — in each repo the last commit on its first-parent line made before the state's first commit, and that commit's ancestors — and those commits as `date  subject`, oldest first across the repos (head and tail kept around one elision line when the run is long); the project files in the tree the workflows arrived into, named from the project — each repo's at that last commit, a submodule's pointer never one of them (outside `.claude/`; each repo's HEAD tree when the state holds no commit yet) — and that tree's top-level shape (`dir/ (n)` and root files, largest first, elided past a dozen); a repo with no commits yet adds nothing — or `null` when there is no honest history to read (no repository, no commits in any repo, a shallow root, a failed read). Every read is bounded and tolerant: the signal is advisory and never makes boot unusable. `walkthrough` reports the answer to the walkthrough offer from the project manifest (`walkthrough.status`) — `none` means nothing recorded yet (a missing manifest or unrecognised value also reads `none`), the state leeway's one-time offer keys on; the two project-level records are independent, and neither says anything about the other. `migrations.verify` carries the verification addenda of migrations executed this boot — `{id, description, info, verify}` per entry, where `info` is what the migration does (project-agnostic) and `verify` what to check in this project; the calling skill performs those checks with judgment before its migration confirm gate and folds fixes into the migration commit. Addenda never re-fire for recorded migrations; an unreadable addenda block degrades to a warning. `migrations.notices` carries what migrations executed this boot hand back for the person — `{id, description, notice}` per entry, `notice` a sentence the calling skill shows in its migration summary; like the addenda, never re-fired, an unreadable block a warning. `migrations.changed` mirrors the orchestrator's own files-updated signal; `migrations.ran` counts the migrations executed, which is the other fact — each over the runs since the last that completed — a migration that ran and found nothing to do still recorded its ID, so a run can leave the migrations record, `.state/migrations`, dirty under a report of no changes. Whenever `changed` is false boot commits a dirty record itself, a state commit confined to it (`chore: record workflow migrations`, sha in `migrations_committed`, null when there was nothing to commit, and a commit failure a warning, never a block: the record is already right on disk). That dirt is the line this run recorded or one an earlier boot left: a boot that runs no migrations at all commits it too. When `changed` is true the calling skill's reviewed `commit --migrations` carries the record in with the diff the user approved, and boot leaves it alone. An unreadable run report degrades to a warning, `ran` reading 0. `output` is the report with the prose stop-gate lines stripped (update counts kept). A failing migrate.cjs is a hard error (`{ok:false}` on stderr, exit 1) — migrations must never half-run silently. A project that is set up — its `.leeway/.knowledge/config.json` — but has no store gets one built: `check` answers `buildable` when this machine's config says how (a provider whose key resolves, or keyword-only chosen outright in the system config or pinned by the project config), boot's keyword pass creates the store, and `check` again decides whether it stood. A failing `check`, or any other not-ready state — no project config, no system config, an invalid one, a provider whose key cannot be resolved — reports `not-ready`, and boot never sets a project up itself: a not-ready response additionally carries `"system_config": {"status": "valid"|"absent"|"invalid", "provider": <name|null>, "model": <name|null>}` — read from `~/.config/leeway/config.json` only, never the credentials file, so no secret can enter the response — which the calling skill's knowledge gate branches on to drive `knowledge setup` conversationally. `indexed` and `compacted` report that each step ran clean — `indexed` that the keyword side came in line with every file. A knowledge config setting the load ignores, a file that fails to index, a failing keyword pass or compact, a provider key that does not resolve, and a vector fill that fell short each land in `warnings` as an entry of their own (`knowledge config: …`, `knowledge index failed: …`, `knowledge compact failed: …`, `knowledge vectors wait: …`, `knowledge vector fill fell short: …`), never a block — leeway surfaces them and continues. The conversational pieces (migration summary, review gate, the knowledge gate) stay in the calling skill.

```bash
engine boot                  # every start
engine boot --start-again    # the person's yes at the lost-state stop: a fresh state where it is still lost
```

**`state-merge`** — the person's pick at the stop boot's catch-up leaves (`domain/state-merge.cjs`; the merge by path `domain/state-merge-paths.cjs`, the rules `domain/state-merge-rules.cjs`). **The catch-up** runs at every boot, before anything writes the state, losing nothing and never rewriting what was pushed: where only the remote's `leeway-state` moved the branch fast-forwards to it; where only this clone's moved it pushes what a failed push left behind; where both moved it merges. No remote, or one holding no state branch, leaves nothing to do; a remote out of reach is a warning, and the session works on the state it has. A side holding code history is refused before anything is merged or pushed. **The merge** is one new commit (`state: merge onto the remote's leeway-state`) whose parent is the remote's tip, its tree merged path by path from the common ancestor. A path one side changed takes that side's version. Where both changed it: the ledger takes the remote's lines, then this clone's the remote lacks, and the migrations record likewise; each manifest merges field by field (a list both sides only appended to keeps both sides' appends; the project manifest's `project_id` is the remote's wherever they differ); other text goes through git's three-way merge, both versions of lines both changed kept, the remote's first; and any other file, other JSON among it, is kept whole, the remote's at the path and this machine's beside it, each such keep a note in `warnings`. The merge is then checked as every state commit's ledger is, and pushed with a lease on the tip it was merged onto, merged again a bounded number of times where the remote moved meanwhile; this clone's unpushed commits are replaced by it. The working tree then moves to the merge's tree, its uncommitted files merged in and left uncommitted; the landing is recorded first, and a landing a kill cut short is finished before anything else. **The stop.** A manifest field both sides changed to different values stops the merge with nothing written, and so does a field the working tree's uncommitted copy and the merge changed differently, once every field on the branch is picked. The stop is kept in the state worktree's git directory, never on the branch, so it outlives the session; each choice keeps its pick, and the merge is worked out afresh from the sides each time, asking only a choice it has not met before. `render state-merge-gate` draws the one choice it asks now — the field and the two values — its DATA carrying the choice's identity. `pick <1|2> <choice>` answers it — `1` keeps this machine's value, `2` the remote's — naming the choice the screen showed; a pick naming any other than the one the merge now asks is not taken (`warnings` says so, the new question in `conflicts`), and the last pick finishes the merge. It refuses where no merge waits on a pick, and any key but `1` or `2`. Response `{"ok": true, "action": "nothing"|"unreachable"|"pushed"|"fast-forwarded"|"merged"|"stopped", "reason": "no-remote"|"no-remote-branch"|"current"|null, "remote", "commit", "pushed", "uncommitted": {"kept": […], "merged": […]}, "conflicts": […], "warnings": […]}` — `stopped` with the choices still open, `commit` the local branch's tip after.

```bash
engine state-merge pick <1|2> <choice>   # the person's pick at the state merge's stop; <choice> from the screen's DATA
```

**`github-rule`**, **`github-squash`** — the person's answer to setup's offers on GitHub (`domain/github-setup.cjs`), each made through the code host's driver — the landing driver serving the state's remote, whatever the project's landing setting — and only on yes. `github-rule` answers the offer of a rule on `leeway-state` refusing its deletion and any push that is not a fast-forward, for anything run outside Claude Code: offered wherever the code host's driver can set it. `github-squash` answers the offer of the squash default — a squash merge's commit made from the pull request's title and description, so each task lands under its own subject and id — offered only where the project also lands through that driver, since landing refuses a stack merge until it is set, and made on every repository the project lands in there: its own, and each nested in it whose own remote the driver serves, each left as it is where it is set already. `yes` makes the setting, `no` makes nothing; either way what happened is recorded on the project manifest — `github_rule`, `github_squash` — as `{"status": "set"|"declined"|"failed", "reason"?}`, `failed` with why, and committed confined to it on the state branch, so the offer is never made again, to this clone or another. A setting the driver could not make is a warning naming the repository and where to make it by hand, and setup carries on. It refuses any answer but `yes` or `no`, a `yes` where the offer is not made, and an offer already answered — but a `yes` to the squash default, which is taken again, setting it on any repository nested since. Response `{"ok": true, "github_rule"|"github_squash": "set"|"declined"|"failed", "reason"?, "committed", "note"?, "warnings"?}`, its commit `chore: {the offer} {status}`.

```bash
engine github-rule <yes|no>      # the answer to setup's offer of the rule on leeway-state
engine github-squash <yes|no>    # the answer to setup's offer of the squash default
```

**`manifest`** — the field surface: read and write work-unit manifest fields by dot-path. Thin dispatch in `engine.cjs`, logic in `domain/fields.cjs`, schema validation and locking from the kernel modules.

**Dot-path addressing.** Every command takes `command <dotpath> [field] [value]`. The path joins work unit, phase, and topic with dots; segment count determines the access level:

| Segments | Level | Path | Field | Resolves to |
|----------|-------|------|-------|-------------|
| 1 | Work unit | `my-epic` | `work_type` | `work_type` |
| 2 | Phase | `my-epic.discovery` | `dismissed` | `phases.discovery.dismissed` |
| 3 | Topic | `my-epic.discussion.auth-flow` | `status` | `phases.discussion.items.auth-flow.status` |

Topic-level access routes through items (`phases.{phase}.items.{topic}.{field}`); the field argument may itself be a dot-path (`sources.auth-api.status`). The wildcard topic `*` collects from every item in a phase (`get`/`exists` only; `get` returns a JSON array of `{topic, value}` objects). The reserved prefix `project` routes to the project manifest (`.leeway/manifest.json`) with the field embedded in the dot-path — `get project.defaults.plan_format`, `set project.defaults.plan_format {format}`; a `set`, `push`, `pull` or `delete` of `project.project_id` is refused, the engine minting it as it creates the state and it never changing — which is why `project` is a reserved work-unit name, alongside `baseline` (the project baseline's knowledge-base identity), `roadmap` (the product layer's identity) and `none` (the literal a skill takes where an argument names nothing — see `handoff`); dots and phase names are also barred, enforced at `workunit create`.

**Output contract, deliberately split.** Reads print bare stdout — they are prose substitution surfaces: scalars raw (no quotes), subtrees as two-space-indented JSON, `exists` printing `true`/`false` (always exit 0), `key-of` the bare key, `list` a JSON array of manifests, missing `get` paths empty stdout exit 0. Read errors keep `Error: …` on stderr with exit 1 (real error) or exit 2 (expected miss — `key-of`/`resolve` on a missing work unit, or a `key-of` value not found; `get` misses are the empty-stdout exit 0 above, never exit 2). Mutations answer with the engine's one-line JSON response and fail as `{"ok": false, "error": …}` stderr exit 1 like every other verb. `apply <work-unit> --file <ops.json>` is the batch form of set/delete: ops `{"op": "set", "path": <dotpath>, "fields": {…}}` / `{"op": "delete", "path": <dotpath>, "field": …}`, values native JSON (`null` is `null`, never `'~'`), every op validated with the entry named before anything is written, all paths inside the one work unit (one lock, one atomic write — the project manifest is out of scope), a missing delete target failing the whole batch. No git commit — the calling flow's commit covers it.

```bash
engine manifest get    <dotpath> [<field.path>]          # scalar raw / subtree JSON; missing → empty, exit 0
engine manifest set    <dotpath> <field> <value>                 # single field (positional shorthand)
engine manifest set    <dotpath> <field>=<value> [<field>=<value> …]  # uniform batch — never mixed with positional
engine manifest push   <dotpath> <field> <value>         # append, creating the array
engine manifest pull   <dotpath> <field> <value>         # remove first deep-equal match; no-op safe
engine manifest delete <dotpath> <field.path>            # errors when the path is absent
engine manifest apply  <work-unit> --file <ops.json>     # batch set/delete across one work unit — atomic
engine manifest exists <dotpath> [<field.path>]          # true/false, always exit 0
engine manifest list   [--status <s>] [--work-type <t>]  # JSON array of manifests
engine manifest key-of <dotpath> <field.path> <value>    # reverse lookup (e.g. task_map external → internal)
engine manifest resolve <work-unit>.<phase>[.<topic>]    # artifact paths for KB-indexed phases
```

`set` batches: additional `<field>=<value>` pairs after the positional pair land under one lock in one write, answered by one response listing every field written (`{"ok": true, "path": …, "set": {…}}`); pairs split on the **first** `=` only, so values may contain `=`. Values parse as JSON first (arrays, objects, numbers, booleans), falling back to string; a bare `~` is null, the same sentinel `task complete --next-task` takes — shell-quote anything zsh would eat (`'[]'`, `'{}'`, `'~'`). Validation is schema-driven (`kernel/manifest-schema.cjs`): `work_type`, work-unit `status`, per-phase item statuses (discovery's empty vocabulary refuses every status write — map items carry no status), and gate modes — a `*_gate_mode` write must name a gate the schema's `GATE_FIELDS` table places on that phase's items, takes `gated`/`auto`/`bounded`, and lands `bounded` only on a gate the table binds (the implementation task and fix gates, to the plan phase); a walk's nested `gate_mode` takes `gated`/`auto`. A refused value fails a whole batch with nothing written. A `status` write onto a phase item that is `cancelled`, `postponed` or `promoted` is refused whatever the value, and so is a `delete` of the item or of any field of it — `{phase} item "{topic}" is cancelled — reactivate it instead (engine topic reactivate {wu} {discovery|specification} {topic})`, the reactivate addressed by the unit that frees the item, `{phase} item "{topic}" is postponed — pull it forward from the roadmap instead`, or `{phase} item "{topic}" is promoted (to "{unit}") — promotion is terminal; continue it from the cross-cutting work unit` — the same refusal every transition makes, so the field surface is never the permissive path around them (a grouping analysis re-run over a cancelled specification's freed sources can pick its key, and a reconcile's `delete items.{name}` would erase the stash with the item; the item's other fields stay writable). Dot-paths with empty segments are refused outright (an unset shell variable would alias the project manifest), and work-unit-level mutations (`set`, `push`, `pull`, `apply` set-ops) refuse a field whose first segment names a phase — a typo'd dot-path would build a shadow tree beside `phases.*` that no read joins; reads and `delete` stay free so a stray tree can be inspected and repaired. Mutation responses: `set` echoes the fields written; `push` carries `pushed` and the new `length`; `pull` carries `removed` (`false` on any no-op) and `length`; `delete` carries `deleted: true`.

**`knowledge`** — the knowledge base's one door: a local store of every completed research, discussion, investigation, and specification artifact in `.leeway/`, searched by meaning and by word, plus markdown imports and promoted seeds indexed as they land, the gap-analysis cache indexed when topic-discovery rewrites it, epic discovery session logs indexed at each harvest, the product roadmap's session logs and imports (`.leeway/.roadmap/`) indexed at each session close and landing, the project baseline docs indexed as each area completes, and the ledger's records, rendered as copies under `.leeway/.knowledge/records/` — a topic's at `{unit}/{topic}.md`, a unit's own level at `{unit}.md`, phase `record` — again at every ledger write and every boot, and indexed (**`ledger`**). Chunks are the text itself at full fidelity, never summaries, each carrying its provenance — work unit, phase, topic, and the source document's date. It surfaces prior context that would otherwise be lost across work units or forgotten within one: a spec written months ago, a discussion that rejected an approach, an investigation that ruled out a cause. The knowledge directory (`.leeway/.knowledge/` — the store, its metadata, and the knowledge `config.json` setup writes, beside them the store's writer lock (`.lock`) and the vector fill's claim (`.fill`), git-ignored with them) sits in the one state every checkout and worktree of the project shares, and is never committed: the store is derived from the committed artifacts, each clone sets up and builds its own, and a worktree reads the one its main checkout's state holds. Mechanism lives in `kernel/knowledge/` (the store's file format, word search and its stemmer, ranking, chunking, excerpts and outlines, the embedding providers, the config), the workflow side in `domain/knowledge/` (artifact identity and discovery against the manifests, indexing and retirement, the vector fill, query, status, setup; `commands.cjs` is the door), and the per-phase chunking configs in `content/knowledge/chunking/`. The transactions reach the same modules in process — their knowledge-base syncs never go through the door.

**What is indexed**, with the confidence each phase carries:

- `research` (low — exploratory, may contain dead ends)
- `discussion` (low-medium — conversational, may contain corrected assumptions)
- `investigation` (medium — diagnostic, tied to specific symptoms)
- `specification` (high — validated decisions, "what we decided to build")
- `imports` (low — user-shared reference material, often loose, may contain multiple topics. Markdown only — any other import keeps its own extension, is tracked on the manifest's `imports[]`, and is never indexed; `index <path>` refuses it by name)
- `seeds` (low — the work unit's origin: the promoted inbox item(s), verbatim capture)
- `analysis` (low — the gap-analysis cache, a meta-summary derived from low-confidence material)
- `discovery` (low — epic exploration logs: the running record, not validated decisions; topic = session, so a work unit's whole discovery is `--phase discovery --work-unit {wu}`)
- `baseline` (low — the project baseline: brownfield assessment docs at `.leeway/.baseline/{topic}.md`, project-level rather than per-work-unit. Chunks carry the reserved pseudo-identity `baseline` for both work unit and work type. Observed and user-stated context about the pre-existing codebase — it informs, but is never a settled call a phase may lean on silently)
- `roadmap` (low — the product-road session logs at `.leeway/.roadmap/sessions/session-NNN.md`: the running record of product-altitude conversation, graded like discovery logs; topic = session. Project-level — chunks carry the reserved pseudo-identity `roadmap` for both work unit and work type. Roadmap imports land at `.leeway/.roadmap/imports/{name}` under the same identity with phase `imports`, markdown alone indexed)

Planning, implementation, and review are never indexed: they describe execution, not knowledge, and searching them would surface task IDs and code fragments, not insight. Operational `.state/` files (migrations, environment-setup) are excluded too — only the gap-analysis cache filename is accepted from `.state/`.

**Answers in text, not JSON.** Every verb acts on the project the call's directory sits in and prints what it did. The verbs that talk to the embedding provider — the bulk `index`, `query`, `fill`, `setup`, and `rebuild` — wait on it; every other verb answers at once. `--help`, `-h` or `help` writes the usage to stdout, exit 0; a call naming no verb writes it to stderr, exit 1. A failure is said on stderr, exit 1 — `Error: …` wherever the verb does not word it itself. `check` is branched on by its output — it always exits `0`. `query` is branched on first by its exit code, non-zero a failure — a usage error (no term, a blank term, a malformed `--boost`), a knowledge config it cannot use (one that cannot be read, or a provider that cannot be built), or a store that cannot be read or whose metadata is missing — and on `0` by its output.

```bash
engine knowledge query "<term>" ["<term>" …] [--work-unit <wu>] [--work-type <t>] [--phase <p>] [--topic <t>] [--boost:<field> <value> …] [--limit <n>] [--explain]  # in a conversation, kept as its last query in its folder, `knowledge-query.json` — terms, filters, then what it printed or why it failed — what `brief plain-search` draws; no lock
engine knowledge check                                   # ready | buildable | not-ready
engine knowledge index <path/to/artifact.md>             # one artifact — its keyword side at once, its vectors filled in the background
engine knowledge index [--work-unit <wu>]                # the bulk index — the store brought in line with the files, its vectors filled while it waits
engine knowledge fill                                    # embed the chunks awaiting vectors — what an index launches in the background
engine knowledge remove --work-unit <wu> [--phase <p> [--topic <t>]] [--dry-run]
engine knowledge status                                  # full health report — for people, never automation
engine knowledge compact [--dry-run]
engine knowledge rebuild                                 # human-only — asks for `rebuild` typed back
engine knowledge setup [--from-system | --keyword-only | --provider <id> … | --key-only [--provider <id>]]   # no flag: the interactive wizard, human-only
```

`query` searches the store. Several positional terms run as separate searches in one invocation — one store load — merged, deduplicated by chunk ID (highest score wins), then cut to `--limit`. Within what remains, each topic's records run in its order: among one topic's results that kept the same term, its specification first, then its discussion or investigation, then its research, each in the places the topic's results already hold — nothing enters or leaves. The topic is read from the manifests at query time: a specification heads every discussion and investigation its `sources` name (a cancelled, superseded, promoted or postponed one heads nothing), and research joins the discussion of its name. How a phase constructs its terms and weighs what comes back — natural-language terms, boosts before filters, confidence tiers, two-step retrieval — is `skills/leeway-shared/references/knowledge-usage.md`. Flags:

| Flag | Behaviour |
|------|-----------|
| `--work-unit <wu>` | Filter to one or more work units. Comma-separated list accepted. Hard filter — non-matching chunks excluded |
| `--work-type <type>` | Filter to a work type. Comma-separated list accepted (e.g., `--work-type cross-cutting` or `--work-type epic,feature`). Hard filter |
| `--phase <phase>` | Filter to one or more phases. Same comma-separated syntax. Hard filter |
| `--topic <topic>` | Filter to one or more topics. Same comma-separated syntax. Hard filter |
| `--boost:<field> <value>` | **Re-ranking hint, NOT a filter.** Boosts chunks where `<field>` equals `<value>` by `+0.1` per match, additive — keyword-only, that only breaks near-ties. Repeatable. Valid fields: `work-unit`, `work-type`, `phase`, `topic`, `confidence` |
| `--limit <n>` | Cap result count after merge + re-rank. Default 10 |
| `--explain` | Print beneath each result how it ranked — for diagnosing retrieval, never needed to use the results |

**Search modes**, settled per query. **Hybrid** — the store was built with the provider, model and dimensions the config names: every term embedded in one request, keyword and vector searches blended, results re-ranked by any `--boost:<field>` directives, plus an always-on confidence-tier boost and a progress-based decay that down-ranks units the project has moved past. **Keyword-only** — full-text search alone. Still useful: semantic expansion is lost, but a word still finds its other forms (`limit` finds `limiting`), and the commonest words (`the`, `of`, `is`) match nothing. A supported degraded mode, not a broken state. The output opens with a note naming why, and the fix:

- no provider configured — `[keyword-only mode — configure embedding provider for semantic search]`;
- a provider configured over a keyword-only store — the next start embeds the store, no rebuild;
- whatever keeps the query from a vector the store can compare — a key that does not resolve, a provider down or unreachable, a rate limit that outlasts the query's waiting, an account out of quota, a config that dropped its provider, a store built with another provider, model or dimensions (fixed by `knowledge rebuild`).

A query never fails for want of a vector: whatever its note says, it exits `0` with its results. Nor does it stall on the provider: each request gets 5 seconds to answer and a second try, and a rate limit only the waiting a query is allowed (see `index`), before the query runs keyword-only.

**Output.** A `[N results]` header — the merged, deduplicated, re-ranked count after `--limit`; `[0 results]` with nothing beneath it when nothing matched — then per result a provenance line, `[phase | work_unit/topic | confidence | YYYY-MM-DD]` (the source document's date, its mtime), closing on `| reopened` where its topic is in progress again; the headings enclosing its excerpt, title first, joined by ` › `; the excerpt; and a `Source:` line naming the source artifact at the chunk's lines in it (`path:L3-39`, one line `path:L9`, counted from the file's first line, frontmatter included), a blank line between results. A topic is in progress again while the result's own phase item reads `in-progress` in the manifests at query time — reopened, its chunks live meanwhile; a specification sourced from a reopened discussion stays unmarked, and the marker never moves the ranking. The excerpt is the passage of the chunk, at most 1000 characters, whose lines share the most of the query's words — the words of the framing the result ranked on, as the search tokenizes them, rarer words weighing more — widened by the lines around it; heading lines are never part of it, a chunk with no line sharing a word shows its opening lines, and a line over the budget alone is cut at word boundaries around its matching stretch, `…` marking each cut. The headings and the range are read from the file as it stands: where the file no longer holds the chunk's text (edited since its last index, or gone), the headings line is absent and `Source:` names the bare path; a document with no heading enclosing the excerpt has no headings line either. Notes sit above the header, one line each: why the query ran keyword-only (see Search modes), and, over a store with chunks awaiting vectors, `[N chunks await vectors — searched by keyword alone; each start retries them]`, followed, where the last vector fill fell short, by `[the last vector fill fell short — …]` naming the first file it failed and why; then a `[knowledge config — …]` line for each config setting the load ignored (see `setup`). `--explain` adds, beneath each source line, a `Framing N:` line per term — its keyword score and vector similarity, each raw → over its search's best (`absent` where that search missed the chunk), and their blend (keyword-only: the raw keyword score). A framing whose hits, cut to twice the limit, lack the chunk reads `not in its top 20` at the default limit, whether or not the term matched it. Then `Score:` names the framing whose score the chunk kept and works it through decay, boosts and confidence tier to the final value, and a result its topic's order moved closes on `Topic order: moved from N by score to M`.

`check` is the readiness probe. It always exits `0` (unless the filesystem itself is unreadable) and prints one state: `ready` — the knowledge base is initialised and the store is loadable; `buildable` — this clone is set up (its `.leeway/.knowledge/config.json`) but has no store, and this machine's config says how to build one: a provider whose key resolves, or keyword-only chosen outright — a system config holding knowledge settings that name no provider, or a project config unsetting the provider. No system config, an invalid one, or a provider whose key cannot be resolved is never read as a keyword-only choice; `not-ready` — missing directory, missing config, unloadable store, or a missing store this machine cannot build. `boot` runs it at every start: `buildable` has boot build the store; `not-ready` routes into leeway's knowledge gate, which drives `setup` through its non-interactive forms.

`index` writes to the store, in two forms. **With a file** — what a skill runs over a document it writes outside a phase completion (a specification's corrigendum, a resolution landed in a source document, a baseline doc); `topic complete` and the lifecycle transactions index in process — it writes the file's chunks searchable by keyword and returns at once, re-indexing replacing the file's existing chunks (idempotent); it then launches the vector fill (see `fill`) when a provider that can embed is configured and chunks await vectors. The path, absolute or from the working folder, must be in the state (`Not in the workflows state: {path}` otherwise) and match `.leeway/{work_unit}/{phase}/...` so identity can be derived — an identity named from the state root, so it never moves when the checkout does. For imports, the path is `.leeway/{work_unit}/imports/{filename}.md` and the topic is the filename basename without extension — a non-markdown import is refused by name. For the gap-analysis cache, the path is `.leeway/{work_unit}/.state/discovery-gap-analysis.md`; the phase is `analysis` and the topic is `gap-analysis`. For baseline docs, the path is `.leeway/.baseline/{topic}.md`; the work unit and phase are both `baseline` (removal is `remove --work-unit baseline [--phase baseline --topic <t>]`). For roadmap material, the paths are `.leeway/.roadmap/sessions/session-NNN.md` (work unit `roadmap`, phase `roadmap`, topic = session basename) and `.leeway/.roadmap/imports/{name}.md` (work unit `roadmap`, phase `imports`); removal is `remove --work-unit roadmap [--phase … --topic …]`. Output: `Indexed N chunks from {file}`. A file that fails to index exits non-zero, saying the next start retries it.

**Without a file** — the bulk index — it brings the store in line with the files and fills the vectors it is owed while it waits. A clone with no store gets one, in the mode this machine's config names — empty when there is nothing to index, its metadata replacing any left without a store. Every chunk records the sha256 of the content it was indexed from and the version of the chunker that cut it; the bulk index compares those against each discovered artifact (completed phase artifacts, the markdown `imports[]` and `seeds[]` entries, gap-analysis caches, closed epic discovery sessions, closed roadmap sessions and roadmap imports, baseline docs — a live session's log is indexed when it closes) and indexes the ones with no chunks (`new`) or with chunks from other content or another chunker version (`changed` — a chunk with no recorded hash or chunker version counts as changed, and a re-cut that leaves a text as it was keeps its vector; a file with a chunk awaiting its vector is cut again, and counts as changed when its chunk texts differ from the stored ones); the rest are `unchanged`. It skips the non-spec artifacts `compact` prunes, so it never re-embeds them. It then removes the chunks of identities positively known to be gone, deciding from the manifests as they stand when it writes: a source file inside the project no longer on disk, a work unit absent from a non-empty registry or cancelled, and a research/discussion/investigation/specification item absent from its manifest or `superseded`, `cancelled`, `postponed`, or `promoted`. An `in-progress` item (a reopened topic) keeps its chunks; baseline and roadmap chunks go only with their files; a work unit whose manifest cannot be read keeps its chunks. `--work-unit <wu>` confines both halves to one unit. Output is a line per file acted on, then `N new, N changed, N removed, N unchanged.` (`, N failed` when any file failed to index, `, N chunks awaiting vectors` when any chunk's vectors failed). Setup and `rebuild` end with it; `boot` runs its keyword half at every start and hands the vectors to the fill.

**Keywords first, then vectors.** Either form writes each file's chunks searchable by keyword — carrying the vector of any text the store already holds — before a vector is embedded, about 100 texts to a request, each batch saved as it lands. The bulk index embeds every chunk awaiting a vector in its scope — a pruned one excepted — so a chunk whose embed failed gets its vector at the next start, bar one the endpoint refused. A keyword-only store takes a provider configured over it at its next index, and every chunk its vector — no rebuild. Over a store built with a provider whose key does not resolve, the chunks are written all the same and no fill is launched; the bulk index exits non-zero naming the key's fix (`Cannot embed: …`) even with no chunk awaiting a vector. A store built with one provider, model or dimensions refuses another, as it refuses a config that names no provider: that takes a `knowledge rebuild`.

A rate-limited request (HTTP 429) waits the time the provider names — capped at a minute, growing waits when it names none — and is retried alone, up to five times. An index or fill waits at most 60 seconds in all, a query 5: a request whose wait does not fit what remains fails at once, as does one from an account out of quota. Other transient failures of a request to the provider (network, server error) are retried with exponential backoff — three tries in all, two for a query; nothing but a provider request is retried. A rejected request (HTTP 400/413/422), a bad key, or a provider configuration the model contradicts fails at once. A file whose vectors fail stays searchable by keyword: the bulk index names it on stderr (`Failed to embed <file>: …`) — its vectors coming at the next start, or, where the endpoint refused a chunk of it, that chunk going without one — and exits non-zero. When the endpoint refuses an input in a batch, the batch is embedded file by file, and a refused file text by text, so the refused text alone goes without its vector; any other failure stops the embedding, the files left awaiting named with it. The bulk index attempts every file, names each failure on stderr, and exits non-zero at the end. A manifest the bulk index cannot read aborts it before anything is removed. Either form exits non-zero if the file doesn't exist, the path can't be parsed, or the path names a non-markdown import — and when there is no store to write and this machine's config does not say how to create one (the rule `buildable` states): a provider whose key cannot be resolved is never stood in for by a keyword-only store, and no configuration at all is never read as a keyword-only choice.

`fill` embeds every chunk awaiting a vector a provider can give — bar those `compact` prunes — batch by batch, saving each as it lands (the rules above). A single-file index, a transaction's knowledge-base sync, and `boot` each launch it detached when a provider that can embed is configured and chunks await vectors — never for a keyword-only store, nor for a provider whose key does not resolve — so none of them waits on embedding and vectors land seconds after a phase closes. One fill works at a time: a second finds the first's claim (`.leeway/.knowledge/.fill`) and ends at once. It is silent unless a chunk went without its vector, when it names each file on stderr and exits non-zero. A fill that falls short records why in the store's metadata (`fill_failure` — the first file it failed, why, and how many more), said in the next query's note, in `status`, and in boot's warnings; a fill that lands everything clears it, and the next start retries what awaits.

`remove` removes the chunks matching its filter: `--work-unit <wu>` alone every chunk of the unit, `--phase <p>` narrowing to one phase, `--topic <t>` (which requires `--phase`) to one topic. A work unit the registry does not hold is refused unless the store still holds its chunks — then removed as an orphan cleanup; the reserved identities `baseline` and `roadmap` are never registered. `--dry-run` counts what the filter matches without touching the store. Output: `Removed N chunks for {scope}`. It is what a skill runs over a document it deletes outside a transaction (a scoping restart's specification); the lifecycle transactions — a cancel, a postpone, a supersession, a promotion — remove chunks in process. Exits non-zero on usage errors and when the removal fails, saying the next start removes them.

`status` is the human-readable health report: chunk counts by work unit, phase, and work type; last-indexed timestamp; provider info; the mode a query runs in — keyword-only naming why and the fix, in its note's words; the chunks awaiting vectors in a store built with a provider, and why the last vector fill fell short; a knowledge config that cannot load, named, and each config setting the load ignored (`WARNING: …`); and what the next bulk `index` does — completed artifacts not yet indexed, artifacts changed since they were indexed, artifacts pruned below the decay floor (never counted as unindexed or changed), and indexed identities it retires, each with its reason. Not used in skill automation — intended for debugging and user inspection.

`rebuild` is destructive: it deletes the existing index and re-indexes everything currently discoverable — completed phase artifacts (research, discussion, investigation, specification), the markdown entries on each work unit's `imports[]` and `seeds[]` arrays, epic discovery session logs (`discovery/sessions/session-NNN.md`), any present gap-analysis caches (`.state/discovery-gap-analysis.md`), the roadmap sessions and markdown imports (`.leeway/.roadmap/`), and the project baseline docs (`.leeway/.baseline/*.md`). It asks the user to type `rebuild` literally to confirm — read from the terminal, or from the first line of stdin where there is none — refusing before the prompt, the store untouched, where this machine's config does not say how to create a store (the rule `buildable` states) — and sets the old store aside until the new one stands, putting it back if the index throws. **Human-only** — no skill runs it. Non-deterministic: rebuilt chunks won't match the originals (embedding variance, edited artifacts).

`compact [--dry-run]` is the storage backstop: it removes a work unit's non-spec chunks once their retrievability `R` has decayed below `decay_prune_below` — once enough later work has completed that they're effectively unreachable in query ranking. Decay is progress-based (how much work completed after the unit, weighted by work type), not wall-clock; specifications are exempt; `false` disables it. `--dry-run` previews without deleting. Skills call neither `compact` nor `rebuild`: `boot` compacts at every start, and `rebuild` is the user's.

`setup` initialises the knowledge base: the system config (`~/.config/leeway/config.json`), this clone's init (`.leeway/.knowledge/` — never committed, so every copy of the project sets up once), and an initial bulk index of every completed artifact. An artifact that fails to index, or a chunk that fails to embed, does not fail setup: the output names how many, and the next start retries them. Config resolves defaults ← system ← project; `null` unsets a key. Setup writes provider identity only — the provider settings `provider`, `model`, `dimensions` and `base_url`, replaced as a set, every other key of the file's `knowledge` object kept as written. The tuning keys `similarity_threshold` (the vector leg's cosine floor, 0.3; a number from 0 to 1), `decay_prune_below` (0.05; `false` disables, else a number from 0 to 1), `decay_base_stability` (5; a number above 0) and `decay_weights` (per work type, numbers of 0 or more) are honoured as overrides in either file and never written. A key the knowledge base does not know, or a tuning value outside its range, is ignored — the level beneath it, or the default, applies — and named as `<key> in <file> is ignored: <why>` — in the query's notes and in `status` over a store, and in boot's warnings wherever boot brings a store in line or builds one; the provider settings are used as written, a wrong one failing where it is used. **The API key never passes through a flag, a chat, or stdout.** There is deliberately no `--key` flag — any setup invocation carrying one is refused (argv lands in shell history and process listings). Keys resolve from the provider env var (`$OPENAI_API_KEY` — wins) or `~/.config/leeway/credentials.json` (mode 0600, written by `--key-only` or the wizard). Setup output names active settings only (provider · model), never key material. The non-interactive forms, which skills run:

```bash
engine knowledge setup --from-system
engine knowledge setup --keyword-only
engine knowledge setup --provider openai --model <m> [--dimensions <d>]
engine knowledge setup --provider openai-compatible --base-url <u> --model <m> --dimensions <d>
engine knowledge setup --key-only [--provider <id>]
```

- **`--from-system`** — reuse the existing system config: resolve the key (env → credentials; providerless configs need none), validate provider configs with one test embed, create the project store, bulk-index the existing artifacts, print the active-settings summary. Refuses clearly when the system config is missing/invalid or the openai key is unresolvable (the message names the env var and the `--key-only` remedy).
- **`--keyword-only`** — project-level keyword-only init: project config, empty store, provider-null metadata. Never touches the system config — the project config always pins `provider: null`, so this clone runs keyword-only whatever the machine's system config names, and when its store goes missing it is `buildable` keyword-only. A system config it cannot read is refused before anything is written. Idempotent; partial states fill in; a store without metadata refuses toward `knowledge rebuild`.
- **`--provider ...`** — write the system config from flags (validation embed first — a broken provider never lands on disk), then proceed as `--from-system`. A change of provider keeps the file's tuning overrides and every top-level key another subsystem keeps there. `openai` requires a resolvable key; `openai-compatible` allows keyless endpoints and requires `--dimensions` (must match the model's native output).
- **`--key-only`** — the terminal detour: a masked readline prompt for the key alone (TTY-required; non-TTY aborts), written to `credentials.json` (mode 0600), then exit. `--provider` selects which provider the key is stored under (default `openai`).

`setup` with no flags runs the guided wizard — **human-only**, prompting throughout at the terminal; a run without one aborts with `engine knowledge setup requires an interactive terminal`. Safe to re-run: per-step prompts detect existing state and offer skip or reconfigure; the bulk index at the end only indexes what is new or changed. The provider menu offers `openai` (cloud, requires an API key), `openai-compatible` (any local/self-hosted OpenAI-compatible `/v1/embeddings` endpoint — LM Studio, Ollama, vLLM, LiteLLM), or `skip` (keyword-only). For `openai-compatible`, the wizard collects `base_url` (required), `model`, and `dimensions`; the API key is **optional** (press Enter to omit for open servers) and is stored only in `credentials.json` — there is no env-var override. `base_url` is consumed only under the `openai-compatible` provider and ignored under `openai`. Configured dimensions must match the local model's native output; the validation embed fails loudly on a mismatch.

**Exit codes.** `0` — success, `check` reporting any state, or a `query` run keyword-only for want of a vector. Non-zero — a usage error, a knowledge config that cannot be read or names a provider that cannot be built, file not found, unparseable path, lock contention exceeded, an index refusing a provider the store was not built with, an index or remove that failed (the bulk index and `fill` also when any chunk's vectors failed, and the bulk index over a store whose provider key does not resolve), or a `query` over a store that cannot be read or whose metadata is missing. `query` with zero results exits `0` and prints a `[0 results]` header.

**`workunit`** — work-unit lifecycle. `create` is the work-type commit — discovery's durability boundary as one transaction. It creates the manifest (identity fields, `status: in-progress`, empty phases, project-manifest registration; a name a work unit already holds refuses in the validate phase, nothing moved — the calling flow derives another), copies each `--import` into `imports/`, moves each `--seed` — a live inbox path, its folder deriving the `inbox:{idea|bug|quickfix}` source tag — into `seeds/`, installs the `--session-log-file` content verbatim as `discovery/sessions/session-001.md` (the content is model-authored — the engine never writes prose), sets `phases.discovery.active_session = "001"` for an epic, and commits scoped to the work unit and the project manifest, plus `.leeway/.inbox` when seeds moved out of it (`discovery({wu}): create work unit ({work_type})` — engine-owned message). Landing filenames are normalised at the last dot: the stem lowercased with whitespace/punctuation runs collapsed to `-` and trimmed, a markdown-ish extension (`.md`, `.markdown`, `.txt`, `.text`) or none yielding `.md`, any other extension kept and lowercased — a dotfile source, whatever follows the dot, and one whose stem normalises away are skipped and reported in `skipped_imports`, seeds fall back to `seed.md` — and collisions suffix the stem `-2`, `-3` against both the destination directory and the batch. Each copy lands mode `0644`, whatever the source carried. Every landing gets an `imports[]`/`seeds[]` manifest entry with a fresh ISO-8601 UTC timestamp — an import also `origin: "discovery"`, the opener being discovery's own door — and a knowledge-base index (warn-don't-block), imports only where the landing is `.md`: the store reads prose, so a binary import is tracked on the manifest and never embedded. Validation completes before any mutation — an import path that is missing or is not a regular file (a directory among them) fails the whole call with `{"ok": false, "error": …, "missing_imports": […]}` so the calling flow can re-prompt and re-run against untouched state. Response: `{"ok": true, "work_unit": …, "work_type": …, "imports": [{"path": …}…], "seeds": [{"path": …, "source": …}…], "skipped_imports": […], "session_log": …, "committed": "<short-sha>", "warnings": []}`.

`import` is that landing after the opener — a file the user shares mid-session, into the same `imports/` home, stamped with the origin of the place that took it: `--from discovery` (the opener or a discovery session) or `{phase}/{topic}` with the phase one of `research`, `discussion`, `investigation` — a work unit's own vocabulary, narrower than the schema's shared predicate (`kernel/manifest-schema.cjs`), which also accepts `roadmap` for the product layer's `roadmap.imports[]`: `--from roadmap` is refused here and belongs to `roadmap import`. `origin` is required on every entry. Refused when the work unit is missing or not in-progress, `--from` is absent or outside the vocabulary, a `{phase}/{topic}` origin names an item the work unit does not have (`no {phase} item "{topic}" in "{wu}" — check the --from origin`; a mistyped topic would record a provenance nothing resolves and mint a hold nothing clears), any path is missing or is not a regular file — a directory among them is refused with the rest, since a copy that threw mid-batch would strand the files before it (the whole call, `missing_imports` on the error, nothing copied) — or every source is dropped by filename normalisation, a dotfile source included, whatever follows the dot — "imported" must mean something landed. In one lock hold: plan and dedupe against the directory and the batch, copy each file (`0644`), push `{path, imported_at, origin}`. After it: a knowledge index per `.md` landing (warn-don't-block) and ONE commit staging the imports directory and the work-unit manifest (`workflow({wu}): import {n} file(s) for {origin}`, engine-owned) — a peer session's dirt elsewhere in the unit never rides, and a commit failure degrades to a `commit pending` note naming the retry, `engine commit {wu} --imports`. A `{phase}/{topic}` origin beats presence on that topic (the landing is that session's own work) unless the item is terminal; a bare `discovery` beats nothing. Response: `{"ok": true, "op": "import", "imports": [{"path": …, "origin": …}…], "skipped_imports": […], "committed": "<short-sha>"}` plus `warnings` when any — relay `skipped_imports` when non-empty.

`complete`, `cancel`, and `reactivate` are the lifecycle transactions, each one transaction: manifest write, knowledge-base sync (warn-don't-block), scoped commit (`.leeway/{wu}`). `complete` and `cancel` also purge the unit's scratch cache (`.leeway/.cache/{wu}/` — rebuildable per-phase scratch; reactivation regenerates on demand): disk-only, except pre-gitignore tracked residue whose deletions ride the transaction commit. `complete` sets `status: completed` and stamps `completed_at` (today, UTC — same form as `created`); its commit message rides on `-m` because it varies by caller (manual completion vs pipeline-terminal vs review-skipped — the engine can't derive how completion happened). No knowledge-base action — completed units retain their chunks — except when completing a cancelled unit with a finished pipeline directly (the one cancelled state complete accepts): cancellation removed the unit's chunks, so that path re-indexes them (warn-don't-block). `cancel` sets `status: cancelled` and removes the unit's chunks from the knowledge base, in process; commit message engine-owned: `workflow({wu}): mark as cancelled`. It also runs the roadmap's cancel-revert hop, whole-unit form: every roadmap item joined to the unit returns to waiting (`roadmap_reverted: [names]` on the response, project manifest riding the commit — see `roadmap`); reactivate never re-joins. `reactivate` restores `status: in-progress` from completed **or** cancelled — a finished pipeline (derived next phase `done`) is no bar; the reactivated unit surfaces as finalising until a phase is reopened — clears a stale `completed_at`, and — only from cancelled, whose removal emptied the index — re-indexes what cancellation removed (every completed artifact in an indexed phase, shape-valid `imports/` and `seeds/` entries, on-disk analysis caches, and — epics — the on-disk `discovery/sessions/session-*.md` logs); commit message engine-owned: `workflow({wu}): reactivate work unit`. Illegal transitions refuse loudly: complete/cancel refuse an already-completed/cancelled unit respectively and route the opposite closed state through reactivate (complete alone also accepts the cancelled finished-pipeline state); reactivate refuses an in-progress unit. Statuses are validated against the shared schema's work-unit vocabulary — the engine is never the permissive path. Responses: `{"ok": true, "work_unit": …, "status": …, "committed": "<short-sha>", "warnings": []}` plus `completed_at` (complete) or `previous_status` (reactivate); `committed: null` plus a note when nothing was staged.

`pivot` converts an in-progress feature to an epic as one transaction: flips `work_type: epic` in the work-unit manifest **and** the project manifest's registration (upserted when a legacy unit predates registration), registers the feature's single topic (topic name = work unit name) on the discovery map with backfill semantics (`routing` = `research` when the research phase exists, else `discussion`; summary/description left for the next epic entry's summary-backfill), re-indexes the whole unit via the same walk reactivate uses — chunk metadata carries `work_type`, which is why pivot re-indexes — and commits both manifests (`workflow({wu}): pivot to epic`, engine-owned). Refuses a non-feature, a unit that isn't in-progress, and a topic already on (or dismissed from) the map — all before anything is touched. Response: `{"ok": true, "work_unit": …, "work_type": "epic", "routing": …, "committed": "<short-sha>", "warnings": []}`.

`absorb` merges a feature into an in-progress epic as a new topic, then deletes the feature — one transaction owning the mechanical tail; the judgment (choosing the feature, the epic, and the topic name with the user) stays in the calling prose, and the verb takes the decided inputs. Validation completes before any mutation — feature exists and is a feature with a discussion (item **and** file) and no specification-or-beyond phases; every discussion, research, and experiment item is named after the feature (a foreign-named item refuses loudly — the feature directory is deleted afterwards, so a silent skip would lose it); epic exists, is an epic, is in-progress; the topic name is dot/slash-free with no surrounding whitespace and free in the epic (map item, dismissed list, discussion item, discussion file, research item, research file, experiment item, experiment directory, mailbox directory) — so a refusal leaves both work units byte-identical: no crash window between the feature's deletion and the commit. It moves the discussion to `discussion/{topic}.md`, the research file to `research/{topic}.md` — the research always lands at the topic name, the same landing the discussion and the series take, so the map row, the artifact, and every experiment join share one name — the experiment series when the feature ran one (`phases.experiment.items.{topic}` a whole copy of the item — derived status and every record with its slug, status, verdict, or reason — and the record directory renamed to `topics/{topic}/experiments/`), the feature's mailbox where it holds messages (`{feature}/topics/{feature}/mail/` renamed whole to the epic's `topics/{topic}/mail/`, every message file keeping its name — the feature's directory is deleted, so its messages follow the topic), and imports/seeds (filename collisions suffix `-2`, `-3` — the shared landing dedupe — with manifest entries carrying their **original** timestamps and seed provenance; an import the dedupe renamed has its `../imports/{old}` links — the anchored relative form a document writes, any depth of `../` — rewritten to the new name in the two documents this absorb moved — the one content substitution the domain ring makes, bounded to a path its own rename broke, exact and idempotent — and reported under `renamed_imports`; an import whose origin named the feature's own session, `{phase}/{feature}`, is re-aimed at `{phase}/{topic}`, every other origin carrying unchanged, and only `.md` moves are re-indexed); carries each phase item whole onto the epic — the Discussion Map and the thread register, the dismissed grounds, a live `reconcile_needed` flag (the upstream material moves alongside, so the pending reconcile stays true and the epic's map row cues it), a live `awaiting_experiments` (the series moving topic-keyed beside it so the completion refusal and release edges keep holding) — never a field at a time; registers the map item with backfill semantics (`routing` = `research` when the feature did research); removes the feature's knowledge-base chunks and indexes the moved artifacts at their epic identities (completed artifacts of the indexed phases; seeds always, imports where they are `.md` — warn-don't-block); deletes the feature directory, its project-manifest registration, and its scratch cache (`.leeway/.cache/{feature}/`); and lands ONE commit staging `.leeway/{feature}`, `.leeway/{epic}`, and `.leeway/manifest.json` (`workflow({feature}): absorb into {epic}`, engine-owned). Roadmap joins follow the material: every item pulled into the feature is re-aimed at the epic — an idea at `{epic, topic}`, a bug or a quick-fix at `{epic}` alone, riding with the unit as material, never a topic (`roadmap_reaimed: [names]` rides the response) — the un-pull is cancel's move, never absorb's — and so do sources: an item source under the feature, waiting or pulled, is rewritten to the path this absorb moved its file to (`roadmap_sources_rewritten: [{"item": …, "from": …, "to": …}…]`) or dropped where the feature's deletion took the file, the item's `sources` going with the last of them (`roadmap_sources_dropped: [{"item": …, "source": …}…]`); each roadmap field rides only when non-empty. The feature's `discovery/sessions/` logs are not moved — they are deleted with the feature directory; git history is provenance. Response: `{"ok": true, "feature": …, "epic": …, "topic": …, "discussion": {"path": …, "status": …}, "research": […], "imports": […], "renamed_imports": [{"from": …, "to": …}…], "seeds": […], "routing": …, "committed": "<short-sha>", "warnings": []}` (`renamed_imports` empty when nothing collided), plus `experiment: {"path": …, "status": …, "experiments": [ids]}` when a series moved and `mail_moved: {"path": …, "count": N}` (the topic's mailbox in the epic, absolute) when messages waited.

`promote` moves a completed epic specification assessed as cross-cutting to its own cross-cutting work unit — one transaction owning the mechanical tail; the judgment (the assessment, the cc unit's name, the one-line description, user confirmation) stays in the calling prose, and the verb takes the decided inputs. Validation completes before any mutation — the source is an in-progress epic whose topic carries a `completed` specification item with `specification.md` on disk; the `--to` name passes the work-unit name rules (create's own) and is free (no `.leeway/{to}` directory, no project-manifest registration); spec source names that would break path addressing refuse as tampered — so a refusal leaves the epic byte-pristine and no cc unit exists. It moves the spec directory to `specification/{to}/` (topic = work unit name for a cross-cutting unit), moves each spec source whose discussion file exists on disk into the cc unit's `discussion/` (its epic item carried whole under its own name — the Discussion Map and every other field but a reconcile flag, whose upstream stays in the epic — reading `completed`, and a source of the cc spec item at the epic row's status — sources of a completed spec were incorporated — so a reopen of it flags the spec), carries the imports the moved material rests on — every entry a moved document links (`../imports/{name}`, any depth of `../`, in the specification or a moved source discussion) and every entry a moved source attached (`origin: "discussion/{source}"`), **copied** rather than moved since another epic topic may link the same file, its entry riding unchanged onto the cc manifest's `imports[]` (origin included), `.md` copies indexed at the cc identity and an entry whose file is missing on disk named under `warnings` — creates the cc manifest log-less and already completed (`status`/`completed_at` — the cc pipeline is terminal after spec — plus `source_work_unit`/`source_topic` origin provenance and the spec item's `date`, all stamped today UTC), registers it in the project manifest — the same write carrying every roadmap item source at the moved specification (a path beneath its directory included) or a moved source discussion to its cc path (`roadmap_sources_rewritten: [{"item": …, "from": …, "to": …}…]`, riding only when non-empty; every other source names a file the epic keeps, and joins stand) — sets the epic's spec item and each moved discussion's item to `status: promoted` + `promoted_to: {to}`, syncs the knowledge base (moved artifacts indexed at their cc identities, the epic's old chunks removed — warn-don't-block), and lands ONE commit staging `.leeway/{wu}`, `.leeway/{to}`, and `.leeway/manifest.json` (`spec({wu}): promote {topic} to cross-cutting work unit`, engine-owned). Response: `{"ok": true, "work_unit": …, "topic": …, "cc_work_unit": …, "cc_status": "completed", "discussions": [{"name": …, "path": …}…], "specification": {"path": …}, "imports": [{"path": …, "origin": …}…], "status": "promoted", "promoted_to": …, "committed": "<short-sha>", "warnings": []}`.

```bash
engine workunit create <work-unit> <work-type> --description <text> --session-log-file <path> [--import <path> …] [--seed <path> …]
engine workunit import <work-unit> <path> [<path> …] --from discovery|{phase}/{topic}   # land shared files mid-session — one confined commit
engine workunit complete <work-unit> -m "<message>"
engine workunit cancel <work-unit>
engine workunit reactivate <work-unit>
engine workunit pivot <work-unit>
```

**`discussion-map`** — Discussion Map subtopic writes. `add` and `set` each load the work unit's manifest, apply the transition, save atomically, and print one decision-ready JSON line: `{"ok": true, "subtopic": "…", "status": "…", "all_decided": false, "unresolved_count": N}` — no follow-up read needed, and no git commit (the calling session's commit cadence picks the manifest change up). `set` takes one positional pair or a uniform `<subtopic>=<state>` batch (never mixed) in one locked write — the batch is atomic (a failing entry means nothing was written) and answers once: `{"ok": true, "set": {"…": "…"}, "all_decided": true, "unresolved_count": 0}`.

```bash
engine discussion-map add <work-unit> <topic> <subtopic> [--parent <subtopic>]   # new subtopic, starts pending
engine discussion-map set <work-unit> <topic> <subtopic> <state>                 # pending|exploring|converging|decided|deferred
engine discussion-map set <work-unit> <topic> <subtopic>=<state> [<subtopic>=<state> …]   # uniform batch, one atomic write
```

Subtopic names are kebab-case slugs; `--parent` nests under an existing top-level subtopic (two levels max).

**`research-threads`** — the thread register's writes: what a research topic set out to learn, kept under `phases.research.items.{topic}.threads` (kebab slug → `{question, status, origin, parent[, note]}`). A lens, not a plan — nothing gates on a thread's state and any state may follow any other. Every verb loads the work unit's manifest, applies the transition, saves atomically, and prints one decision-ready JSON line carrying the row as it now stands plus the register's counts: `{"ok": true, "thread": "…", "question": "…", "status": "…", "origin": "…", "parent": null, "counts": {"open": N, "digging": N, "learned": N, "parked": N}, "total": N}` — no follow-up read needed, and no git commit (the calling session's commit cadence picks the manifest change up). `add` starts a thread `open` and records its origin once — `seed`, `brief`, `user`, `conversation`, a deep dive's id (`deep-dive-NNN`, with or without its label suffix), or the name of the topic that sent the question in (any name the map accepts — one line, no slashes, no dots) — never rewritten; it refuses a slug already present, a missing parent, and a parent that is itself a child (two levels max). `set` takes one positional pair or a uniform `<slug>=<state>` batch (never mixed) in one locked write — the batch is atomic (a failing entry means nothing was written) and answers once: `{"ok": true, "set": {"…": "…"}, "counts": {…}, "total": N}`; `--note` is the reason a thread is parked — legal with `parked` alone, positional form only, kept while the thread stays parked, cleared the moment its state leaves `parked`. `reframe` rewrites the question in place (the research file carries the history). `remove` is the merge's mechanical half — the survivor's file section carries the folded substance, the absorbed row goes; `--into <slug>` names the survivor (existing, top-level, not the absorbed thread) and moves the absorbed thread's children under it in the same write; bare, it is refused while children nest under the thread, naming them; answers `{"ok": true, "thread": "…", "removed": true[, "into": "…"], "counts": {…}, "total": N}` — `into` present on the merge form alone. Every verb refuses a topic with no research item.

```bash
engine research-threads add <work-unit> <topic> <slug> --question <text> --origin <origin> [--parent <slug>]   # new thread, starts open; origin recorded once
engine research-threads set <work-unit> <topic> <slug> <state> [--note <text>]        # open|digging|learned|parked; --note with parked alone
engine research-threads set <work-unit> <topic> <slug>=<state> [<slug>=<state> …]      # uniform batch, one atomic write
engine research-threads reframe <work-unit> <topic> <slug> --question <text>           # rewrite the question in place
engine research-threads remove <work-unit> <topic> <slug> [--into <slug>]              # the merge's mechanical half; --into moves the absorbed thread's children under the survivor; refused bare while children nest under it
```

**`discovery-map`** — the Discovery Map's writes. `sequence` records the suggested execution order as one transaction: validates every topic exists under `phases.discovery.items`, every order is a positive integer, and no row has closed (`"{topic}" takes no order — {why}` for a cancelled, dead-ended, or postponed row — its order is stashed as `previous_order` and comes back with it), sets each topic's `order`, and commits scoped to the discovery paths (`discovery({wu}): sequence topic map`) — the map lives in the manifest, which the discovery scope covers, and a live peer's document does not; response `{"ok": true, "ordered": {"{topic}": N, …}, "committed": "<short-sha>"}` (`committed: null` plus a note when nothing was staged). Choosing the order is the caller's judgment — the command only records it.

The per-item map operations write the manifest with no git commit (the calling session's commit cadence picks the change up) and enforce the map's lifecycle gates in the engine, deriving each item's lifecycle with the same join the epic detail builder uses. `add` creates a map item as `{routing, source, summary[, description][, brief_path]}` — never a `status` field (map-item lifecycle is computed at render time, not stored); the positional routing is validated against the same enum `reroute` takes, `--source` defaults to `discovery`, `--brief-path` records the topic's brief pointer with the row (non-empty when present), the name follows rename's dot/slash-free rule, an active duplicate is refused, and a dismissed name is refused unless `--force-dismissed` carries the user's confirmed re-add decision (the entry is then pulled off the dismissed list). `--backfill` (mutually exclusive with `--summary`/`--description`/`--brief-path`) lands the item without any of them — keys absent, not `""` — so the next epic entry's summary-backfill drafts them from the topic's artifacts; for topics arriving with work already done (absorb, pivot). `edit` sets `summary` and/or `description` — at least one flag, any lifecycle. `remove` hard-deletes a **fresh** item and pushes its name onto `phases.discovery.dismissed`. `rename` moves a **fresh** item to a new key preserving every field and its map position, moving `discovery/briefs/{old}.md` to `{new}.md` when it exists and rewriting the item's `brief_path` when it points at the canonical `discovery/briefs/{old}.md` (a pointer aimed anywhere else is left alone); the new name must not collide with an active item or an existing brief file — checked whether or not the old brief exists — (a dismissed-list match is allowed — the entry is left alone) and must be dot/slash-free. `reroute` sets a **fresh** item's `routing`. The fresh gate on remove/rename/reroute also refuses a topic with messages waiting in its mailbox, naming them and their drain path — a postponed topic's mail makes no phase item and stays through its pull-forward — and whenever ANY research or discussion item exists for the topic, whatever lifecycle the join derives, the map item being those items' historical anchor; the map-operation gate shows the same refusal in place of its confirm. `remove` and `rename` refuse, too, a topic any ledger event names — its entries name it for good (`"X" can't be removed — the ledger holds entries on it, which name it for good; cancel from the epic menu instead`) — what a landing the ledger's read finished said riding in `warnings`. `handle` sets `handled: true` (any lifecycle except handled/cancelled) — rendered user-side as closed-as-dead-end; `unhandle` clears the marker (handled only — a cancelled row, a cancel marker over the dead end included, refuses toward the reactivate). Gate refusals name the blocking lifecycle and the recovery path (e.g. `"X" can't be removed — research is in flight on it; cancel from the epic menu instead`). Responses: `{"ok": true, "work_unit": …, "name": …, "op": …, "lifecycle": …, "map_total": N}` — every op carries `map_total` (items on the map after the op) so the calling flow needs no follow-up read — plus op-specific fields: add and edit echo the values written (add also `undismissed` when forced past a dismissed match), remove carries `dismissed: true` (plus `roadmap_reverted: [names]` when the removed topic held a roadmap join — the un-pull for a never-started topic, its project-manifest write staged in its own commit), rename carries `renamed_from`/`preserved_fields`/`matches_dismissed` (plus `brief_moved: true` when the brief file moved), reroute `routing`, handle/unhandle `handled`.

```bash
engine discovery-map sequence <work-unit> <topic>=<order> [<topic>=<order> …]   # suggested execution order, scoped commit
engine discovery-map add <work-unit> <name> <research|discussion> (--summary <text> [--description <text>] [--brief-path <path>] | --backfill) [--source <tag>] [--force-dismissed]
engine discovery-map add-batch <work-unit> --file <topics.json>   # whole topic set, one lock/save — atomic; entries {name, routing, summary, description?, brief_path?, force_dismissed?}; source always `discovery`
engine discovery-map edit <work-unit> <name> [--summary <text>] [--description <text>]
engine discovery-map remove <work-unit> <name>       # fresh only; name lands on the dismissed list
engine discovery-map rename <work-unit> <old> <new>  # fresh only; every field preserved, brief file + brief_path follow
engine discovery-map reroute <work-unit> <name> <research|discussion>   # fresh only
engine discovery-map handle <work-unit> <name>       # any lifecycle except handled/cancelled
engine discovery-map unhandle <work-unit> <name>     # handled only
```

**`build-order`** — the build order: one soft execution sequence over an epic's live specification topics, stored as `order` on `phases.specification.items.{topic}`, read by specification, planning, and implementation (planning and implementation join on the topic name). `sequence` records the whole order as one transaction: epic-only; every named topic must exist under `phases.specification.items` and be live (terminal statuses — cancelled, superseded, promoted — are refused by name), the assignment must cover **every** live topic (a partial write is refused naming what it missed), and the orders must be a contiguous 1..N permutation — the wholesale renumber is engine-enforced, so completed topics keep a number and terminal topics never take one. Sets each topic's `order`, clears `phases.specification.build_order_stale` (the flag `topic complete` sets when an epic specification concludes), and commits the work-unit manifest alone (`specification({wu}): sequence build order`) — it writes nothing else, and it runs beside sessions holding the unit's topics. Choosing the order is the caller's judgment — the command only records it. Response: `{"ok": true, "ordered": {"{topic}": N, …}, "committed": "<short-sha>"}` (`committed: null` plus a note when nothing was staged).

```bash
engine build-order sequence <work-unit> <topic>=<order> [<topic>=<order> …]   # whole live set, contiguous 1..N; clears build_order_stale; scoped commit
```

**`agent`** — the background-agent lifecycle store, colocated with the topic's content files at `.leeway/.cache/{wu}/{phase}/{topic}/state.json` (engine-owned, cache-resident; deleting a topic's cache directory — restart — or the work unit's cache — close — removes state and content together; agent content files stay markdown and carry no state — frontmatter is never written or read). `dispatch <wu> <phase> <topic> --kind <kind> [--label <slug> …] [--set <NNN>] [--final]` allocates the next per-kind number (`review-001`; `deep-dive-002-auth` with a label; numbering skips past any legacy files in the cache dir), records the row(s) `in-flight`, each naming the Claude process and conversation that dispatched it as a presence record names its owner (`pid`, `pid_start`, `session_id`, null where Claude Code handed none), and answers with the content-file path(s) the sub-agent(s) must write — no skeleton is created; a file's later non-empty existence IS that agent's completion signal. A discussion review refuses while the topic's mailbox holds messages (a waiting message is a pending change to the document the review would read), and while unarmed (9.8.14) — the first review is free; review n+1 needs `min(n, 3)` of the topic's moves on the ledger since the anchor (`domain/ledger-moves.cjs`): each question asked on the topic but a review's finding (`by: review`) and one Claude's own call answers, each decision made on it — a replaced answer among them, the person's or Claude's, "your call" and a finding's answer included — and each question moved, counted on the topic it left and the topic it went to; a finding, a rewording, a confirmation, a keep and a merge move nothing. The anchor is the latest report-backed review or closing-pass row's `ledger_mark`, the id of the ledger's last line when it was dispatched, null on an empty ledger, which every discussion review and closing-pass row is stamped with (a killed dispatch with no report never anchors; a closing pass does, so after a reopen the moves it read arm nothing); `--final` bypasses the movement gate, still stamping the mark — a review the person asked for; refused on any other kind or phase. A closing pass (`closing-pass`) waits on no arming. A `perspective` dispatch is one polarity pair (`domain/lenses.cjs`): two `--label`s, each a lens and the other's counter-lens, any other lens refused. Repeating `--label` dispatches one SET: every row shares the allocated number (that shared number, echoed as `set` on every row, is the set identity a perspective pair and its synthesis are joined by), and the response carries `set` plus per-label `agents: [{id, file}…]`. A synthesis always dispatches `--set` (required; no `--label`), joining an existing perspective set as `synthesis-{NNN}` — refused when the set is unknown, when any member is still in flight (synthesis reads the whole council), when a live synthesis already exists for the set (an incorporated dead one permits a recovery re-dispatch), or when a legacy file already occupies the name. Kinds: `review`, `deep-dive`, `perspective`, `synthesis`, `root-cause-validation`, `fix-validation`, `closing-pass`. Research carries `deep-dive` alone — the deep dive is its instrument, and a review or any other kind is refused there; a research store row of another kind is closed: `scan` never buckets it and no verb addresses it. `scan <wu> <phase> <topic>` promotes finished rows to `pending` and answers the decision-ready snapshot — `in_flight`, `pending`, `acknowledged`, and `incorporated` rows (every row public-shaped, carrying `set` and `created` — freshness and earlier-session judgments read `created`; conclusion gates read `in_flight`), plus `review_arming` on discussion topics — `{armed, cycles, moves_seen, moves_needed, reason}`, the same verdict dispatch enforces, so the session's dispatch check reads drained state and arming from one call. Which row and which finding to take next is the reading flow's judgment, not the store's. `ack … <id> (--findings F1,F2,… | --clean)` records the finding ids the model read from the content file; a clean report incorporates immediately. `announce` marks the user told the report exists. `surface … <id> <finding>[,<finding>…]` records one unsurfaced finding, or a comma batch of them when a whole lane lands at once — every id validated before any is recorded, so a bad entry fails the batch whole; surfacing the last one auto-incorporates the row. `incorporate` is the skip-all exit — remaining ids stay unsurfaced, an honest record of what was offered and declined. `ack` refuses never-surfaced kinds (a perspective is a synthesis input). Off-path calls refuse loudly naming the row's actual status. Responses carry the public row: `status`, `set`, `created`, `announced`, `findings`, `surfaced`, `remaining`.

**`discovery-session`** — the epic discovery-session lifecycle. `open` starts a session at the log's first write (lazy creation): it allocates the next session number from the on-disk logs (highest `session-NNN.md` plus one, first = `001` — disk is the source, no manifest field stores the counter), moves the drafted log into place as `discovery/sessions/session-NNN.md` (moved, not copied — the draft is consumed), and sets `phases.discovery.active_session` — one manifest write under the work-unit lock. **No commit** and no knowledge-base index: the session is live, and the calling flow's commit cadence picks up the log and marker at its next natural break. The draft's content is model-authored and installed verbatim — the engine never writes prose. Validation completes before any mutation — the work unit must exist and be an epic (the sole work type with a resumable discovery session loop; single-phase work gets its log at `workunit create`), no session may already be open, and the draft must exist with content — so a refusal leaves everything pristine, the draft included. Response: `{"ok": true, "work_unit": …, "session": "NNN", "path": …}`.

`close` ends the session the `phases.discovery.active_session` marker names, as one transaction: delete the marker (resume detection on the next entry sees a closed session), index the marker's session log into the knowledge base (warn-don't-block), and commit the discovery scope with the caller's message — session logs, briefs, and the manifest the map lives in, and never a peer session's half-written document. The message rides on `-m` because it varies by caller (topics synthesised vs edits-only finalisation). The log's content is model-authored **before** the call — the engine never writes prose. Refuses loudly, manifest untouched, when no marker is set (the marker is set at open and always pairs with an existing log, so a browse-only session has nothing to close) or when the marker names a session with no log on disk. Response: `{"ok": true, "work_unit": …, "session": "NNN", "session_log": …, "committed": "<short-sha>", "warnings": []}` (`committed: null` plus a note when nothing was staged).

```bash
engine discovery-session open <work-unit> --session-log-file <path>
engine discovery-session close <work-unit> -m "<message>"
```

**`topic`** — phase-item transitions. `start`, `complete`, `reopen`, and `supersede` are lifecycle bookkeeping with no git commit — the calling flow's commit cadence picks the manifest change up; `send` commits its own delivery. `start` creates the phase item with `status: in-progress` when absent (init-phase semantics: `phases.{phase}.items.{topic}`, status only) or sets an existing non-terminal item back to `in-progress` — an `unstarted` stub included, that status's one exit; a completed item must go through `reopen` — resuming is not starting — and a cancelled item through `reactivate`. Every work type holds a discussion for its research: `start` refuses a discussion's birth — absent or `unstarted` — while the topic's research item is `in-progress` or `unstarted`, naming where the research stands (research feeds discussion, so it lands first; the menu's research row is the way in); an in-progress discussion resumes — the discussion's entry gate is its door, and `complete`'s wait is the backstop for research parked beneath a session already inside. On an epic the discovery map additionally gates the birth of a research or discussion item: `start` refuses a phase the map's next action does not name (an in-progress item resumes regardless; outstanding research always starts, since it is the topic's own row on the epic menu). A specification's start from a proposed grouping records `incorporates` on the item — the started specifications sourcing any of its discussions, when there are any — so what the start took in reads the same after it (see `incorporations`). Response: `{"ok": true, "phase": "…", "topic": "…", "status": "in-progress", "created": bool}`. `send <work-unit> <topic> --from <sender> --content <file> --slug <kebab>` (`domain/mail.cjs`) lands a message in the topic's one mailbox, `.leeway/{wu}/topics/{topic}/mail/NNN-{slug}.md`, its path naming no phase (10.1.3): the content is a scratch file under `.leeway/.cache/`, consumed once the message lands, its first line the message's title (leading `#` marks dropped); under the title the engine writes who sent it and when, as the waiting mail heads it (10.4.2) — `From {sender} · {16 Oct}`, the sender titled as the screen titles it. `--from` is a name, never text: a topic of the unit (`Commercialization`), `{unit}.{topic}` for another unit's topic (`First Run, on Fumi`, a single-topic unit by its name alone), or an experiment of the unit — `E{n}[.{m}]` for one in the target topic's series (`Experiment E1`), `{topic}/E{n}[.{m}]` for one in another topic's, where the person moved the question it measures (`Experiment E1, on Commercialization`); the number is the next in that mailbox, taken under the writer lock, so a send racing another lands after it. It refuses, writing nothing and keeping the scratch: a flag missing, a sender that is none of those names, a slug not kebab-case, a scratch outside the cache, missing, or with a blank first line, a topic named across folders, a unit the project lacks (`there is no work unit "{unit}"`), a quick-fix, which talks through no conversation, and any other target the topic's `enter` refuses, by its own rule (`domain/topic-standing.cjs`) and in its words — a unit completed, a unit past its `spec.md` (from the spec on, a change is settled where it is found, 10.2.2), a topic the unit does not hold (a single-topic unit's topic is the unit), and a topic closed as a dead end or promoted out of the unit; a postponed or decided topic takes the message, as follows. The topic's conversation — its discussion, a bugfix's investigation — is parked as a landing parks it: absent, created `unstarted` (a parked message never reads as started work); `unstarted` or `in-progress`, untouched; `completed` — decided — set back to `in-progress` (10.2.7), so the topic shows mail waiting and its next decided needs a fresh close (**`checklist`**) and the gate's yes. A decided close the topic holds, taken or not, is voided by the delivery (`voided`), so a message answered before the yes still has its decision read by a fresh close. A postponed topic is left as it stands, the message waiting in its mailbox for its return (10.1.8). A message to a cancelled topic — its map row or its conversation cancelled — or to a cancelled unit lands in the inbox instead, as an idea, `.leeway/.inbox/ideas/{YYYY-MM-DD}--{slug}.md`, its first line the title as an H1, the line naming its sender under it, then the rest (10.1.6); an idea of that name already there refuses. A landing in a mailbox additionally flags the topic's downstream neighbour in the same locked write, so no completed→in-progress transition ever skips it: the hop rule, shared with `reopen`. Staleness begins when the upstream item goes stale (landing or reopen), never at its later re-conclusion, and it travels one hop only. The downstream neighbour is the same-named item in the work type's next pipeline phase — the experiment slot walked past unconditionally (the series item is derived bookkeeping no phase's start reconciles, so a research reopen flags the discussion whatever series sits between) — except a discussion's or investigation's, which is every specification item naming it in `sources` (the reverse join; a grouped spec's own name may differ). A `completed` neighbour gets `reconcile_needed: "{upstream phase}"` unless a flag is already pending (never clobbered — the reconcile advisory surfaces and clears it, where the phase starts or inside a research/discussion session at its next check); the hop out of research flags an `in-progress` discussion too — the one that could otherwise conclude over research still to land; terminal neighbours are skipped. On the source-phase hop (discussion or investigation), an `incorporated` source row on any non-terminal spec item also flips to `stale` — the persistent record that the extraction predates the revision, cleared only by the spec's own reconciliation. A send writes no ledger entry: the topic it reaches writes the question the message raises (5.3.8). It commits what it wrote — the message and the unit's manifest, as `mail({wu}): send {NNN-slug}.md to {topic}`, or the idea, as `mail({wu}): {slug} to the inbox — {topic or unit} is cancelled`, naming whichever is; a commit git refuses leaves the landing with `committed: null` and a `note` naming the retry — for a mailbox landing `commit {wu} --topic {phase}/{topic} --sweep`, the topic's scope as a sweep, since the session sending is not working the topic; for the inbox `commit --inbox`. Response: `{"ok": true, "unit", "topic", "message_path", "reopened"?: true, "reconcile_flagged"?: true, "sources_staled"?: [spec…], "committed", "warnings"?, "note"?}`, or for the inbox `{"ok": true, "unit", "topic", "inbox_path", "committed", "warnings"?, "note"?}`; the send report is `render send-report`'s. `mailbox <work-unit> <topic>` lists what waits, in the order it landed, taking no lock — the loop's read, so a message landing while the topic is in session is raised from it (10.1.5): `{"ok": true, "unit", "topic", "count", "files": [absolute paths]}`, a folder or a file not `.md` no message; it refuses a unit the project lacks. `answered <work-unit> <topic> <NNN-slug> --entry <id>` removes the message named `NNN-slug` — named whole, since a number comes back once the highest is answered — once `--entry` — a prefix of an id, resolved as a ledger link's is — names the question it raised: one raised on this topic wherever it stands since, moved to another topic or later (5.3.8), or one any live move of the unit's ever took to this topic, wherever it stands since — the message that carried it (9.S17): under the writer lock, refusing, writing nothing, a name of another shape (the number alone, or the file's name), a unit not in progress, a name no message holds, an id no entry begins, an entry that is no question, and a question neither first raised on this topic nor taken to it by any move of the unit's. The removal is committed alone, `mail({wu}): {topic} answered {NNN-slug}.md`, and git keeps the file; a commit git refuses is retried as a send's is, in the topic's scope as a sweep. Response: `{"ok": true, "unit", "topic", "answered": "NNN-slug.md", "entry": "<short id>", "remaining", "committed"}`. `complete` sets `status: completed` on an existing item and, when the phase is research/discussion/investigation/specification, indexes the phase artifact into the knowledge base; completing an **epic specification** also sets `phases.specification.build_order_stale: true` — the declared dependencies sharpen the build order, and the epic menu's sequencing step reads the flag (`build-order sequence` clears it); an `unstarted` item is refused — its messages have never been worked; an item holding a live wait is refused naming every wait — the experiment evidence it awaits, and for a discussion the same-named research while it is `in-progress` or `unstarted` (research feeds discussion; the wait is derived from the research item's status, never stored — concluding the research releases it); a research or discussion item carrying `reconcile_needed: research` or `experiment` — its upstream landed unread — is refused until the session reads what landed and clears the flag (the reconcile advisory's own `manifest delete`; the brief flag `true` and every other phase's flag never refuse); and a specification item is refused while any `sources` row is not `incorporated` (`pending` rows await extraction, `stale` rows await reconciliation — the sign-off checkpoint enforced engine-side; an item with no `sources` field completes freely). Response: `{"ok": true, "phase": "…", "topic": "…", "status": "completed", "warnings": []}`. `reopen` sets a `completed` item back to `status: in-progress` — the resume path `start` refuses — and flags the topic's downstream neighbour under the same hop rule as `send`. Anything not completed is refused (a cancelled item must go through `reactivate`, and a promoted one is reopened in the cross-cutting unit it moved to), a discussion whose research is outstanding is refused the way `start` refuses it, and there is no knowledge-base sync — the item's chunks stay live until re-completion re-indexes over the same identity. Response: `{"ok": true, "phase": "…", "topic": "…", "status": "in-progress"}`, plus `reconcile_flagged: [{phase, topic}…]` / `sources_staled: [spec…]` when the hop landed. `supersede` sets `status: superseded` and `superseded_by: {topic}` (always the absorbing **topic** name) and removes the item's chunks from the knowledge base — legal only in phases whose shared-schema status vocabulary contains `superseded` (schema-driven, no hardcoded list). The `--by` topic must already exist in the same phase; a proposed item is refused (no artifact — reconcile deletes it instead), an `unstarted` item is refused (its messages drain when the topic's phase starts), an already-superseded item is refused, and a cancelled item must go through `reactivate`. No commit — supersession is batch-oriented; the calling flow supersedes the set, then commits once. Response: `{"ok": true, "phase": "…", "topic": "…", "status": "superseded", "superseded_by": "…", "warnings": []}`.

Derived phases (`DERIVED_PHASES` in the shared schema — currently the experiment phase) sit outside the hand lifecycle: the item is derived bookkeeping the phase's own verbs maintain, so `start`, `complete`, and `reopen` refuse it outright (the spawn creates and reopens the series; the last record's terminal transition closes it), and a discussion holding a live evidence wait (`awaiting_experiments`) refuses completion until the wait releases — see `experiment`; `complete` names every wait it refuses over, a discussion's outstanding research included.

`cancel` and `reactivate` are the epic transactions, topic-level over one unit per stage — the phase argument names the stage, never a phase item: `discovery` is the map row with everything under its name (research, discussion, and the experiment series), `specification` is the specification with its same-named plan; any other phase is refused (there is no phase-level cancel), and a cancel never rolls through a stage boundary. Each is one transaction: manifest write, knowledge-base sync in the indexed phases (remove on cancel; re-index on reactivate for each restored `completed` artifact), and a commit of the work-unit manifest alone — plus the project manifest when a roadmap join reverted (`workflow({wu}): cancel {topic} ({stage})` / `… reactivate …`); a cancel additionally releases the calling session's own heartbeat on each item it took, a peer's never (see `presence`), and closes the agents still running on each item it took — each row in flight whose report is not on disk marked incorporated, so a report landing after is never taken in, a landed report's row left for the topic's return, the ids answered as `closed_agents` (a store that does not read is a warning, the cancel standing) — and a reactivate releases nothing. Every commit takes the logs changed beside it, the topic's among them (**`commit`**). A cancel answers its `next` from the calling conversation's position (`domain/topic-leave.cjs`): sitting in the topic it took, at a phase of its stage, the handoff to the epic's menu, `leeway-continue-epic {wu} {phase} cancelled`; from anywhere else `continue`. Both run beside sessions holding the unit's topics — from the epic menu, and a cancel from inside the conversation it closes — so they take nothing but the state they wrote, and a commit failure degrades to the generic `commit pending` note (the manifest alone is narrower than any state scope). A specification is **started** when its status is `in-progress` or `completed` — a `proposed` grouping is a regenerable suggestion, and a status-less item neither locks nor lists.

A **discovery** cancel is refused when the name is on neither the map nor a research/discussion item, when the unit already reads cancelled, when it would take nothing — no live item under the name and no map row to mark (`"{topic}" has nothing to cancel — no live item under its name and no map row`) — and while a started specification sources the topic's discussion (`cancelling "{topic}" is refused while the specification "{spec}" sources its discussion — cancel the specification first`; a proposed grouping never locks) or one was promoted with it (`… the specification "{spec}" (promoted to "{unit}") sources its discussion — promotion is terminal, so the topic continues in its cross-cutting unit`). In one locked write, in this order: every evidence wait the topic's research and discussion hold is released (the holders flagged `reconcile_needed: "experiment"` while still non-terminal, carried inertly until a reactivate brings it back live) and every open record on the series ends `abandoned` with `reason: "topic cancelled"`, the series settling over what remains; every non-terminal research and discussion item of the name — an `unstarted` stub included — takes `previous_status`/`status: cancelled`; every `proposed` specification sourcing the discussion is deleted and named under `discarded`; and the map row, when one exists, takes `cancelled: true` with its `order` stashed as `previous_order` — a never-started topic needs nothing else, and a legacy topic with no map row reads cancelled through its items. After the lock: each cancelled research/discussion item's chunks removed from the knowledge base, in process, the caller's own heartbeat released on each cancelled item, the roadmap's cancel-revert hop (any item bound to the topic returns to waiting, `roadmap_reverted` on the response, the project manifest riding the commit — see `roadmap`), the commit. Response: `{"ok": true, "topic": "…", "phase": "discovery", "status": "cancelled", "cancelled": [{phase, previous_status}…], "discarded": [spec…], "abandoned": [id…], "released_waits": [{phase, released, remaining}…], "roadmap_reverted": [name…], "closed_agents": [id…], "committed": "<short-sha>", "warnings": [], "next"}`.

A **specification** cancel is refused for a `proposed` grouping (`a proposed grouping is not started — cancel its source topic to discard it, or let the grouping walk regroup`), a terminal specification, one whose name has an implementation or review item, any status (`"{spec}" is locked — implementation has started; code in the tree is fixed forward, and the work-unit cancel abandons the epic`), and one that would take nothing (`specification "{spec}" has nothing to cancel — it carries no status`). It stashes the specification's status and build-order `order` (`previous_status`, `previous_order`) and its same-named non-terminal planning item's status; the source discussions are untouched — unaccounted again, free to be regrouped or cancelled. Response: `{"ok": true, "topic": "…", "phase": "specification", "status": "cancelled", "cancelled": [{phase, previous_status}…], "discarded": [], "abandoned": [], "released_waits": [], "closed_agents": [id…], "committed": "<short-sha>", "warnings": [], "next"}` — the three arrays ride every cancel, empty here.

`reactivate` requires the unit to read cancelled. A **discovery** reactivate clears the map marker, restores every cancelled research/discussion item — a stash returns as the status; an item cancelled with none returns to never-attempted, its `status` deleted and `null` in `restored` — and returns the map `order` from `previous_order` only while no live row holds the number — the stash drops either way, a taken number leaving the row unordered so the sequencing flag repairs it. A **specification** reactivate is refused while a source is unavailable, naming every one: a source topic whose Discovery unit is cancelled (`reactivating "{spec}" is refused while its source "{topic}" is cancelled — reactivate the topic first`) or a source another started specification has since taken (`reactivating "{spec}" is refused while the specification "{other}" sources "{topic}" — regroup the discussions from the menu (s/spec)`); it then discards every `proposed` grouping over a returning source (named under `discarded` — the source is accounted for again) and restores the specification and its same-named cancelled plan, the build order restored under the same collision guard. No roadmap re-join — the revert is one-way. Response: `{"ok": true, "topic": "…", "phase": "…", "status": "reactivated", "restored": [{phase, status}…], "discarded": [spec…], "committed": "<short-sha>", "warnings": []}` (`committed: null` plus a note when nothing was staged).

`postpone` is the Discovery unit's other exit, epic-only (a non-epic work unit is refused naming its type — its topic is the work unit, and a pulled unit's "not now" is the work-unit cancel's revert). Cancel says "not doing this"; postpone says "doing this later": the topic leaves whole, nothing on disk moves, and the pull is the way back. `--horizon` is required — the roadmap bucket the topic waits in. The stage is implied: `postpone` addresses the Discovery unit and no other. `postponePlan` is the one reading the gate, the menu row, and the verb share; its locks, in refusal order: the name is on neither the map nor a research/discussion item; the unit already reads postponed (`"{topic}" is already postponed — it waits on the roadmap`) or cancelled (`"{topic}" is cancelled — reactivate it from the epic menu first`) or is closed as a dead end (`"{topic}" is closed as a dead end — reopen it first` — the roadmap holds what is still to do, and a dead end carries nothing forward under its own name); a started or promoted specification sources its discussion (`postponing "{topic}" is refused while the specification "{spec}" sources its discussion — a topic past specification is past "not yet"`, a promoted one named `"{spec}" (promoted to "{unit}")` — no cascade, and a proposed grouping never locks); a non-terminal record sits on its experiment series (named as the gates name them, counted top-level — a laboratory cannot run under a topic that has left, and abandoning it is the destructive act this exit avoids); the horizon is not a legal name (`"{horizon}" is not a legal horizon name — dots and slashes break manifest addressing` — the roadmap could not name it, so the postpone refuses before the epic moves); and a roadmap item of the topic's name that is not this topic's (`a roadmap item named "{name}" (horizon "{h}") is not this topic's — rename or remove it on the roadmap first`). In one locked write, the project lock nested inside the work unit's: every non-terminal research and discussion item of the name takes `previous_status`/`status: postponed`, every `proposed` specification sourcing the discussion is deleted and named under `discarded`, the map row takes `postponed: true` with its `order` stashed as `previous_order` — the experiment series is left exactly as it stands — and the roadmap side lands **before** the epic manifest is saved, so a refusal there (the clash re-read under the project lock) leaves the topic where it was: an item joined to `{work_unit, topic}` **re-waits** (the join deleted, the chosen horizon taken, its own name and origin left as they were), or one is **born** under the topic's name (`summary` the map row's, falling back to the topic titlecased; `origin: postpone:{work_unit}`), the node and the horizon created just-in-time. Either way the item records `postponed_from: {work_unit, topic}` and gains the topic's brief, research, and discussion files as `sources` where they exist (relative to the state). After the lock: each postponed research/discussion item's chunks removed from the knowledge base, in process (the topic's conclusions are on hold and retrieval inside the epic must not surface them; the return re-indexes) and the caller's own heartbeat released on each item taken, and the agents still running on each item taken closed, as a cancel closes them. One confined commit covers both manifests (`workflow({wu}): postpone {topic} → {horizon}`). Response: `{"ok": true, "topic": "…", "status": "postponed", "postponed": [{phase, previous_status}…], "discarded": [spec…], "roadmap": {name, horizon, born_map, born_horizon, reverted_join}, "closed_agents": [id…], "committed": "<short-sha>", "warnings": [], "next"}` — `next` as a cancel's, its outcome `postponed`.

After the postpone the roadmap owns the topic (see `roadmap`): `topic cancel` and `topic reactivate` refuse a postponed row naming the pull, `roadmap remove` cancels the epic's row in the same transaction, and `roadmap pull-forward` back into the same epic restores it. `start`, `reopen`, `complete` and `supersede` refuse a postponed phase item the same way, and the field surface refuses a `status` write onto one and any `delete` of it or its fields (`{phase} item "{topic}" is postponed — pull it forward from the roadmap instead`). `topic send` **accepts** a postponed row: a message for a topic that waits is mail that waits with it. `postponed` is a terminal status (`TERMINAL_STATUSES`, and the research and discussion vocabularies alone), so aggregation, gating, next-phase readiness, sequencing, epic completion, and the gap analysis's input set all pass a postponed unit by exactly as they pass a cancelled one; the map row's lifecycle reads `postponed` (tier `⊖`) from the marker, the cancel outranking it where both sit.

Across the family, the knowledge base is a derived index — its failures land in `warnings`, never block.

**`experiment`** — the experiment series: the ordered run of experiments a topic's discussion spawned, recorded at `phases.experiment.items.{topic}.experiments.{id}` with each record's documents on disk in the topic's folder, `.leeway/{wu}/topics/{topic}/experiments/{id}-{slug}/` (`domain/experiment-paths.cjs`). Every document is model-authored — the engine records the lifecycle, never writes prose. Each command is load → apply → save under the work-unit lock plus one decision-ready JSON line. The spawn commits what it wrote; every other command leaves its commit to the session's cadence (`commit --topic experiment/{topic}`, the record directory plus the manifest).

`create` is the spawn — the phase's one door. With `--from discussion` it allocates `E{n}` (per-topic numbering, highest existing plus one), records it `conceived`, installs the problem statement, opens the experiment item (creating it, or setting a completed series back to `in-progress`), and locks the spawning item: `awaiting_experiments` gains the id on the in-progress discussion the question came from — a locked conversation cannot complete until the wait releases. `--question <id>` names the question on the topic's map the experiment measures, by a prefix of its ledger id resolved as a ledger link is: a current question standing open on that topic's map, refused otherwise (`domain/experiment-question.cjs`). The record keeps its full id as `question`, where `ledger map` reads it: the question shows waiting on the experiment until the discussion writes the result (see **`ledger`**); the response names it by its short id. `--problem <file>` is required on a spawn: the spawning session writes the problem statement to a cache scratch (`.leeway/.cache/…` — enforced) and the create moves it in as `{dir}/problem.md`, scratch consumed — the file lands before the manifest names the record, so no conceived record ever exists without its problem statement. The spawn then commits the problem statement and the unit's manifest on the state branch (`experiment({wu}/{topic}): spawn {id} {slug}`), taking nothing of the discussion's: the response adds `committed`, and a commit git refused leaves the spawn saved, its `note` prescribing the retry, `commit {wu} --topic experiment/{topic} --sweep`. The response's `dir` is where every later document is authored. With `--parent <E{n}>` it is the split: a **running** experiment discovering its question decomposes takes sub-experiments `E{n}.{m}`, each walking the same lifecycle in miniature, records nested inside the parent's directory — no lock moves (the wait stays on the parent and releases once, when the parent as a whole ends), and `--problem` and `--question` are refused: a split carries no spawn-side problem statement — the sub-record's design frames its question, and the parent measures the map's. A split never splits again.

The record lifecycle is `conceived → designed → approved → running → concluded | abandoned`. `advance` walks the mechanical steps (conceived → designed when the design is written; approved → running when measurement begins); `approve` records the briefing gate's freeze (designed → approved) and nothing else — the one transition requiring the user's confirm, never a step a loop drifts past. `conclude` takes a **running** record and its one-line `--verdict` (the decision rule's mechanical outcome); a parent refuses while any sub-experiment is live — its verdict synthesises them. `abandon` is the first-class terminal from any pre-terminal status, `--reason` kept on the row. A top-level conclude or abandon releases the spawning item's wait on that id (`reconcile_needed: "experiment"` on the holder — never clobbering a pending flag — so its next entry, or its session's next check, surfaces the evidence, or the abandonment, before the waiting point settles; the holder's `topic complete` refuses while the flag is unread); conclude additionally runs the one-hop downstream flag from the experiment phase (a decided same-topic discussion learns evidence arrived after its decision), abandon never does — there is no evidence to reconcile against. A sub-experiment's terminal transitions move neither. After every terminal transition the item's derived status settles: `completed` when every record is terminal, `in-progress` otherwise — nothing above the records ever concludes by hand. **A report after its question left the topic:** a top-level conclusion whose record measures a question no longer open on the spawning topic's map — the person closed or moved it while the experiment ran — sends `{dir}/report.md` through `topic send` to the topic the question stands on now: the topic of its unit it was moved to, while live, else the spawning topic — so one moved to the roadmap as later goes to the spawning topic. The copy is the report as written, each relative link (inline, image or reference definition; none naming a scheme, an absolute path or only an anchor, and none in fenced code) rebased to resolve from the topic's mailbox, under the line naming the experiment — `--from {id}` where the report goes to the spawning topic, `--from {topic}/{id}` where it goes to another; the send reopens a decided topic and commits the delivery as any send's. With no report written the conclusion is refused, nothing recorded. A question still open takes the report in the discussion, which writes the result. Responses carry the record (`id`, `slug`, `status`, `dir`) plus `previous` (advance/approve), `verdict`/`reason`, `awaiting` and `question` (create — the lock after the spawn, the question measured), `released_waits`, `reconcile_flagged`, `report_sent` (`{topic, message_path, reopened, committed}`, the report sent as a message and the topic it went to), `item_status` (terminal transitions), and `warnings`.

The register, the briefing confirm, the record picker, the return leg's next-or-menu gate, and the conversation's two pauses — the post-spawn now-or-later choice and the blocked-conclusion gate — are render surfaces (`experiment-register`, `experiment-approval-gate`, `experiment-pick`, `experiment-next-gate`, `experiment-spawn-gate`, and the decided checklist — an open question an experiment still measures holds the topic's close); the epic menu carries one row per topic whose series holds a live top-level record, ranked above every other recommendation, appearing at the first spawn and retiring when no live record remains — which experiment to work resolves inside the phase.

```bash
engine experiment create <work-unit> <topic> --slug <kebab> (--from discussion --problem <file> [--question <id>] | --parent <E{n}>)
engine experiment advance <work-unit> <topic> <id>       # conceived → designed, approved → running
engine experiment approve <work-unit> <topic> <id>       # the freeze — designed → approved, user-confirmed
engine experiment conclude <work-unit> <topic> <id> --verdict "<one line>"
engine experiment abandon <work-unit> <topic> <id> --reason "<one line>"
```

**`sources`** — `stale <work-unit> <discussion> [--except <spec-topic>]` marks every spec extraction of a discussion stale after its document moved without a lifecycle transition — the resolution landing's safety valve: a decision repaired in place during specification construction or review, or landed in the discussion from planning, runs the same reverse join a reopen would, minus the reopen. Every non-terminal spec item naming the discussion in `sources` has its `incorporated` row flipped to `stale`, and completed ones take `reconcile_needed: "discussion"` (an existing flag never clobbered); `--except` names the caller's own specification — the one it is constructing, or the one its plan was built from and has just re-aligned — skipped entirely, its extraction of the resolution current by construction. The discussion item's own status is untouched, the discussion must exist as a phase item, and an `--except` naming no specification item refuses loudly — a typo must never silently stale the invoking spec's own row. No git commit — the calling flow commits the document edit alongside. Response: `{"ok": true, "discussion": "…", "flagged": [{phase, topic}…], "staled": [spec…]}`.

```bash
engine sources stale <work-unit> <discussion> [--except <spec-topic>]
```

**`presence`** — the per-topic session heartbeat, cache-resident (`.leeway/.cache/{wu}/{phase}/{topic}/presence`, gitignored). Awareness, never mutual exclusion. Every phase a session sits in carries one — research, experiment, discussion, investigation, scoping, specification, planning, implementation, review — except discovery, which `discovery-session open` already serialises to one session per epic.

**Beats are mechanical, and no prose ever issues one.** The engine stamps the heartbeat as a side effect of the verbs a session already runs, and only where the verb is structurally self-referential — the session acting on its own topic. A beat writes *this* process's identity, so a beat from a verb acting on another topic would manufacture a false hold there. The read verbs (`topic mailbox`, `agent scan`) are reachable for any topic — a session legitimately checks a foreign mailbox — so they **refresh** instead: re-stamp a heartbeat this session already owns, never create one, never overwrite a peer's.

| Verb | Beat |
|---|---|
| `commit --topic {phase}/{topic}` | beats — the session-cadence commit on a live item, so "last active" means "time since the last real write" |
| `commit --topic …` on a **terminal item** (`completed`, `cancelled`, `superseded`, `promoted`) | **clears** — the topic is finished, so every commit that follows its close (the conclusion, a plan wrap-up, review's complete-then-commit) releases the slot rather than re-taking it until the process dies. An item that does not exist neither beats nor clears |
| `commit --topic … --sweep` | suppressed, **outranking both** — the commit is on a topic this session is not working (the conclude sweep's leavings, a foreign-topic delivery's retry, a resolution landed in another phase's document); stamping it would manufacture a hold, and clearing it would destroy a peer's |
| `render code-gate` (empty) | beats — reading a free code slot is how a session claims it, so the hold starts at entry rather than at the first code commit; a gated read stamps nothing |
| `render phase-note` | beats — only ever rendered where a phase starts, for its own topic, so announcing the start is the same act as claiming the slot |
| `commit --paths … --for {wu} {phase}/{topic}` | beats the named code topic |
| `topic mailbox` | refreshes the topic's row in the phase it is talked through — the loop checks its own topic's mailbox every turn, so a turn with no writes still registers; a read of another topic's mailbox stamps nothing |
| `topic start` · `topic answered` | beat — opening the session's own topic, and taking an answered message out of its own mailbox, the latter in the phase the topic is talked through |
| `workunit import --from {phase}/{topic}` | beats — the landing is the session's own work. The item must exist (the call is refused otherwise) and must not be terminal: material filed against a closed topic is nobody sitting in one. A bare `discovery` origin names no topic and beats nothing |
| `experiment create --from` | beats the **spawning** discussion — the conversation recording the spawn on its own item |
| `experiment create --parent` · `advance` · `approve` | beat the experiment topic — the laboratory session working its own record |
| `experiment conclude` · `abandon` (top-level id) | **clear** — the last record's close settles the item, so the record's close is the release; a cadence commit while records remain re-claims (that is the session still in the laboratory); a sub-experiment's beats instead (the parent still runs) |
| `topic complete` | **clears** — the close is the release; the slot opens the moment the topic is finished |
| `agent dispatch` · `ack` · `announce` · `surface` · `incorporate` | beat — the session's own background agents |
| `agent scan` | refreshes — a read of the store, so it re-stamps an owned hold and creates nothing |
| `topic send` | never — delivery acts on the **target** topic from the origin's session |
| `manifest set` · `apply` | never — a three-segment `set` looks self-referential and frequently is not: review's `updated` stamp and the epic menu's unblock both write one phase's item from another phase's session. The session's cadence commit is its heartbeat |
| `topic cancel` · `topic postpone` | never beats, and **clears the calling session's own row** on each item it cancels — the cancel is reachable from inside the conversation it closes, where a hold left behind would read held to every peer until the process died. A row this session does not own is left standing: a peer still sitting in the topic releases at its own exit |
| `topic reactivate` · `supersede` · `reopen` · `sources stale` | never — analysis and navigation actors reaching across topics |
| every other verb — `manifest push`/`pull`/`delete`, the task verbs, every read, render and projection | never |

A beat is best-effort: it never throws, never changes a verb's response, and no-ops on a phase outside the set or a work unit with no directory.

`beat` and `clear` remain as explicit verbs for tests and repair; a beat with no `CLAUDE_PID` in the environment refuses rather than write a record nothing can hold. `scan` reads every heartbeat with one verdict per row: `held` — the owning process still runs (pid + start time verified, so a dead or recycled pid reads unheld instantly; a record beaten where the start time could not be read falls back to bare aliveness, and so does a start time that cannot be read at the scan — `ps` failing to spawn, answering nothing, or not answering within ten seconds proves nothing, so a pid that is there counts as alive; a record with no identity cannot be verified and is never held), however long it has idled. `age_seconds` is the time since the row's last write — rendered as "last active {age} ago" wherever a hold is named, never a verdict. With a work unit: `{"work_unit": "…", "held": N, "held_sources": N, "sessions": [{phase, topic, age_seconds, held, session_id, pid, checkout}…]}`, plus a `DISPLAY: presence deferral` section after the JSON line when a **source** session is held — emitted verbatim per its marker at the same call, wherever an analysis defers. `held_sources` counts the research and discussion rows alone: the analyses read the settled source record — a laboratory session never touches those corpora — so a held experiment, planning, or code session never holds one up, and the caller's own rows are never counted — a session does not defer to itself; the callout names only the rows that do, each with its last-active age, and names `presence clear` for a holder that is wedged but alive. `checkout` is the work tree the owning session works in — presence lives in the one state every checkout shares, and the code gate reads only the rows of the caller's own checkout. With the argument omitted it walks the whole cache root, the read the code gate filters: the same row shape with `work_unit` on each row and `"scope": "project"` in place of `work_unit`, the `held` total but no `held_sources`, and no deferral section (a deferral always names the work unit whose sources it waits on). An *empty* work unit refuses loudly — that is an unset shell variable, not a request to widen the scope. `cleanup` is the exit sweep — the target of the settings-level SessionEnd hook the engine installs in the project's `.claude/settings.json` (a SessionEnd hook declared in skill frontmatter never fires), with the hook contract: session id from the argument or the hook's stdin JSON, never errors, and with no id at all it touches nothing. It drops every heartbeat the named session owns, across all work units, on the exits that keep the process alive (`/clear`, `/logout`) — rows that would otherwise read held until the process exits; a dead process's row reads unheld the moment it dies regardless, gitignored cache the next beat overwrites. Response `{"ok": true, "session_id": "…", "cleared": [{work_unit, phase, topic}…]}`. Consumers: the epic view marks held topics (menu strike-through, recommendation skip, in-session confirm gate); the topic-discovery dispatch and the specification grouping analysis both defer while a source session is held; the conclude sweep leaves a held row's dirt alone and commits a dead session's leavings action-scoped; the spec-side resolution flow checks the target discussion before editing its document in place.

```bash
engine presence beat <work-unit> <phase> <topic>    # every phase but discovery
engine presence clear <work-unit> <phase> <topic>
engine presence scan [work-unit]                    # argument omitted: the whole project (an empty one refuses)
engine presence cleanup [session-id]                # the SessionEnd hook in .claude/settings.json; reads stdin JSON when no argument
```

**`session`** — tmux session labels, the opt-in "where am I" rename. Every place labels itself on arrival, so leaving a place is never an event: `label <name> <phase> <topic>` renames the user's tmux session to `{original} · {work-unit} · {phase} · {topic}` (topic collapsed when it equals the work unit), called by every process skill at Step 0 — a phase entered through `enter` labels through it instead (**`enter`**) — and by discovery at its run step; `label <name>` alone applies `{original} · {name}` — the navigation skills and the bridge on arrival at a work unit, the roadmap and the baseline with their own identity (`roadmap`, `baseline`: project-level places with no work-unit directory and no phase); leeway puts the original back through boot's `repair`. The rename is a display courtesy, never state: with the feature off, outside tmux, on any tmux error, or on a failed stash write it renames nothing and answers so (`{"ok": true, "labelled": false, "reason": "disabled"|"no-tmux"|"tmux-error"|"stash-error"}`), never blocking a flow, and the position is recorded all the same (see `conversation`) — only a bad argument fails loudly, an authoring bug: a phase without its topic is a usage error, and an unknown phase, an illegal name, or a name that is neither a work-unit directory nor a project identity refuses too — each whatever the opt-in, before anything is labelled or recorded. The original name is stashed in the state's cache (`.leeway/.cache/.session-labels/`, keyed by tmux socket + session id) and written before the rename, with the owning Claude process's identity (pid + start time). The stash key is not stable — tmux ids renumber when the server restarts, and name-restoring setups carry a still-labelled name across under a new id — so the original always resolves by exact applied-name match across the socket's records, chained (a record written against a stranded label carries that label inside its own `original`) and consuming the spent links: phase hops and restart-stranded labels both recompose from the true original and never compound suffixes. Only a name matching no record is adopted as the user's own — a manual rename becomes the new original at the next label. `cleanup` restores the original name — one command of the settings-level SessionEnd hook the engine installs in the project's committed `.claude/settings.json` (`node "$CLAUDE_PROJECT_DIR/.claude/skills/leeway-engine/scripts/engine.cjs" session cleanup`, beside `presence cleanup` and `conversation end`; a SessionEnd hook declared in skill frontmatter never fires, so no skill declares one), with the hook contract: session id from the argument or the hook's stdin JSON, never errors, and with no id at all it touches nothing (an id-less sweep could take a live peer's label). It sweeps stashes the named session owns (an ownerless stash counts) plus any whose owning process is dead; a session is renamed only when its current name is exactly one we applied — found by the stash's id or, after a renumbering, by exact name among the socket's live sessions — and always to the chain-resolved true original. A manual rename is never clobbered; a restored or inapplicable stash is dropped, one whose rename failed is kept for the next sweep, as is a link a live session's name still chains through. Response `{"ok": true, "restored": bool}`. Every `label` call also records the conversation's **position**, labels on or off (see `conversation`), and it outlives the session: `cleanup` restores the name and leaves the position. `resume` brings the label back on `claude --resume` — one command of the settings-level SessionStart hook (`{"matcher": "resume", "hooks": [{"type": "command", "command": "… session resume"}]}`, present while labels are on) — under the same hook contract (session id from the argument or the hook's stdin JSON, never errors, nothing without an id) and `label`'s own gates: with a position for that id it re-applies it through `label`'s path (the stash records the resuming process's identity; a name already worn costs no rename); a position naming a work unit or phase this project does not have — resumed in another clone, or the unit gone — labels nothing and is kept, its lifetime its folder's; and no position, disabled, or outside tmux answers nothing. Response `{"ok": true, "resumed": bool}` **on stderr with stdout empty** — a SessionStart hook's stdout is injected into the resumed conversation as context. `repair` is boot's pass over the current terminal — leeway is the place whose label is the original name, and no position: first, labels on or off, it drops the calling conversation's own position (a dead owner's stays for its resume); then, when the session's name is a label this session applied (its session id, or its pid for a later conversation in the same process — presence's ownership rule) or one whose owner is dead — a session that never restored, a restart that carried the label across — it puts the chain-resolved original back, then prunes dead-owner records nothing live still needs (a record on an unreachable server is kept: an unverifiable name proves nothing). No position ages out: one goes with its conversation's folder. The label pass is gated exactly like `label` — disabled, no-tmux, and tmux-error all no-op — and a peer's label whose owning process still runs is live, never stripped. Response `{"ok": true, "repaired": bool}`. `label-config` records the opt-in as the project manifest's `defaults.tmux_labels` (sibling defaults preserved, under the project lock; a manifest that does not parse refuses loudly, never replaced), syncs the session hooks in `.claude/settings.json` — SessionEnd's `session cleanup` and SessionStart's `session resume` present iff `true`, SessionEnd's `presence cleanup` and `conversation end` and the three PreToolUse guards (`layout guard`, `brief guard`, `shell guard`) always; each event reconciled on its own, merged beside whatever the file already holds (permissions, other events, sibling groups and their matchers) and keyed on the hooks' identity, so a second sync never adds a twin, never rewrites a recognised hook, and a removal takes ours alone. It makes two commits under one message, `chore: record session-label choice`: the project manifest, a state commit on the state branch; and the settings file on the branch checked out, as boot commits its own change to it — only where the workflows' change is the file's whole difference from the branch, so a change an earlier call left uncommitted is committed now, one beside the person's own edits in the file is held back with a warning, and an ignored file is never committed (answering `no` on a project whose boot already installed the workflows' own hooks commits the manifest alone). The hooks are not written while git holds a merge, cherry-pick, revert, rebase or bisect open in the code tree (`session hooks not written: {operation} is in progress in the code tree — the next boot writes them`). Response `{"ok": true, "tmux_labels": bool}`; a settings file that does not parse leaves the hooks untouched (`session hooks not synced: …`), and a commit git refuses leaves the files on disk — the choice is recorded either way and the response gains a `warnings` array. An absent value means never asked — no system config holds it and no migration carries it, so every project re-asks. Boot reports the state as `tmux_labels`, runs `repair` (`label_repaired`), and re-syncs the hooks every start (`session_hooks_installed` when the file changed) — `repair`'s stranded arm stays the backstop for the first session after opt-in (a settings hook takes effect from the next session, since Claude Code snapshots hooks at startup), for crashes, and for a tmux server dying.

```bash
engine session label <name> [<phase> <topic>]       # the name alone on arrival — a work unit, or roadmap|baseline; with phase + topic inside a phase
engine session label-config <true|false>            # records defaults.tmux_labels on the project manifest; syncs the session hooks
engine session repair                               # boot's pass over the current terminal — this session's own label, or a stranded one, comes off
engine session cleanup [session-id]                 # the SessionEnd hook in .claude/settings.json; reads stdin JSON when no argument
engine session resume [session-id]                  # the SessionStart hook (matcher resume); reads stdin JSON when no argument; answers on stderr
```

**`conversation`** — the conversation's folder, `{config}/conversations/{session-id}/` beside the system config (`LEEWAY_CONFIG_DIR`, else `~/.config/leeway`): what belongs to one Claude Code conversation rather than to a work unit or a project, found by the session id Claude Code hands every command (`CLAUDE_CODE_SESSION_ID`) from wherever the command runs, the folder named by the id's safe characters alone. Each concern writes a file of its own: `workflow`, the mark that the conversation runs the workflows, which the gate mod reads to set the workflow harness, to say the phase in its spinner, to answer a compaction and to record the task's executor — written once by every engine invocation that carries a session id (after the command, whatever its exit) and every gateway script (`runGateway`), only where the command runs in a workflows project (its repository holds the state, a code worktree's included), and never by the commands Claude Code's own hooks run (`presence cleanup`, `session cleanup`, `session resume`, `conversation end`, and the three guards, `layout guard`, `brief guard` and `shell guard`), which run for every conversation in the project; `transcript`, written by `end`; `position.json`, where the conversation is working (below); `gate-shown.json`, the gate it was last shown, which `gate` answers against (**`gate`**); `raise-shown.json`, the raises it was drawn, each sealed before the person answers (**`raise`**); `trust-pending.jsonl`, the trust-log events waiting to be appended — one an append failed on, or one a write keeps ahead of its ledger entry — which the conversation's next record and every boot append (**`gate`**, **`ledger`**); `briefs/`, the briefs it issued, each `{id}.md` beside `{id}.json` naming whose it is (**`brief`**); `gate.json`, `sent.json` and `pressed.json`, the gate mod's own, `pressed.json` naming the gate and the row a press answered, and when; `compacted.json`, the gate mod's record of every note it appended to a compaction, which the rows mod reads; `rows.json`, the rows mod's own. `end` is the SessionEnd hook's target — one command of the settings-level SessionEnd hook boot installs in every project beside `presence cleanup` (`node "$CLAUDE_PROJECT_DIR/.claude/skills/leeway-engine/scripts/engine.cjs" conversation end`): it reads `session_id` and `transcript_path` from the hook's stdin JSON and writes the path to the folder's `transcript`, only where the folder exists — a conversation that never ran the workflows gets nothing — under the hook contract: it never errors, and an id or a path missing, empty or not a string records nothing. Response `{"ok": true, "recorded": bool}`. Every project's boot tidies every folder. The path is recorded as the hook hands it, and it does not say where the transcript is — a resume from another directory hands the hook one under that directory's project key while Claude Code goes on writing where the conversation began — so the tidy reads it only for the directory Claude Code keeps its projects in (`<projects>/<project-key>/<id>.jsonl`, a leading `~` the home directory) and looks for the transcript by its file name in every project folder there, reading each projects directory once. A folder goes once none holds it and no trust-log event waits in it — Claude Code has deleted the conversation, so its retention setting is the retention these records keep — and a projects directory that is gone holds none; one that cannot be read, a relative path, or no transcript at all keeps the folder.

**The position** (`domain/position.cjs`). `position.json` holds where the conversation is working — `{"name", "phase", "topic", "task", "executor"}`: a work unit or a project identity, its phase and topic, inside implementation the task in flight as `{phase}.{task}`, and beside it the agent id of that task's executor. The engine is its one writer, only a place the project has and only for a conversation that runs the workflows — recording it marks the conversation first, as any engine call in a workflows project does — and a write that fails never fails the verb it rides. Every `session label` and `enter` call records it, labels on or off — a re-label of the same implementation keeps the task and its executor, and any other place leaves neither; `task start` records its task — re-run for the task in flight, as the skill's recovery steps do, it keeps the executor, and another task starts without one — and that task's `task complete` takes it off, its executor with it; the start menu is no position, so boot drops the calling conversation's own before its migrations run — a boot that fails leaves none — and `session repair` drops it too. The tmux label's `session resume` re-applies it, and the gate mod's spinner reads it. `executor <session-id> <agent-id>` is the gate mod's alone, run as the conversation's main loop dispatches `leeway-implementation-task-executor`: it records the agent id the dispatch answered with on that conversation's position, only where the position holds an implementation task in flight — anywhere else it records nothing — and a later dispatch for the same task replaces it; an agent id of anything but letters, digits, `-` and `_` is a usage error, and a stored one that reads otherwise is ignored. Response `{"ok": true, "recorded": bool}`. `position [session-id]` — the calling conversation's `CLAUDE_CODE_SESSION_ID` when no id is given, refused when neither is — answers what that conversation re-reads to carry on from its position, and writes nothing: the skill that runs the work there — a phase skill (`.claude/skills/leeway-{phase}-process/SKILL.md`), or `leeway-discovery`, `leeway-roadmap`, `leeway-baseline` — then the topic's documents: research and investigation their file; discussion its log, `topics/{topic}/log.md`; scoping its specification and plan; specification its `specification.md`; planning its `planning.md` and its `phase-{N}-tasks.md` files in phase order; implementation, with a task in flight, the plan format's `reading.md` and the file named for the task's internal id in the plan's directory or a folder in it; review its `report.md`; an experiment each live record's `problem.md`, `design.md` and `report.md`, in register order; discovery and the roadmap the open session's log (discovery the latest on disk where none is open). It names only what the project has, each file by its absolute path under the project root the call runs in — with nothing else in context, a relative path invites a guess at the root — and never the start skill, a navigation skill or the bridge: a work unit's menu, like no position at all, answers that there is nothing to carry on from, and so does a place no longer open — the work unit missing from the state or not in progress, the place's item closed (`cancelled`, `superseded`, `promoted` or `postponed`), or, in research, an experiment or a discussion, its topic cancelled or postponed on the map — and a place whose skill this project lacks. Two sections: `DATA`, the note the gate mod appends to the conversation's compaction — that the conversation was just compacted, where it is working (the work unit by its work type, the task in flight with its internal id and its executor's agent id where one is recorded), then to follow the skill's "Resuming After Context Refresh" steps before anything else, re-reading the skill and its framework in full, then the documents in full; a discussion's note carries its recovery whole instead, its skill keeping no steps for it: re-read, before anything else, the skill and its framework, the topic's record by running its `ledger record` call, and the log where it is written; catch the log up from the conversation's transcript from its last write onward, the transcript named where Claude Code keeps it, or, where it cannot be found, say so in one line and carry on from the log; where the log does not yet name the conversation, the line its first write opens with (**`enter`**); then carry on as if the break never happened — and `POSITION` (`json for the gate mod — never display`), one line of `{"session_id", "position", "place", "skill", "files", "text"}` for the gate mod: `place` the position as one line (`fumi › discussion › management-window`, the topic left out where it is the work unit; null with no position), `text` the note unchanged; `skill` null with `files` empty is the empty answer, nothing to carry on from.

**`ledger`** — the project's stream of questions, findings and decisions, `.leeway/.ledger.jsonl`: one event a line, written by the engine alone and never edited (`domain/ledger.cjs`, the events and their schemas `domain/ledger-events.cjs`). Every line opens with its schema version, its id, the event's name, its tags — the unit, the topic (none from the spec on, where everything is the unit's), the phase and the session — and the time the engine wrote it; a session's line says who made it, `by` (`person` or `claude`; a question also `review`), and `who_moved_whom` (`none`, `claude-moved-person`, `person-moved-claude`). The schema is at version 2, which added each entry's `cites`, a finding's `known`, `command` and `result`, a decision's `given`, and the `asset` event; a line of version 1 reads with each at its default — no citation, how it is known in words alone (`known` null, no command or result), and the decision its maker's own. An `asset` line — `{entry, path, status, into}` — links a file, by its path from the state root, to an entry: it gives the file a `status`, `canonical` or `reference`, records a lift into the project at `into`, a path from the project's root, or both, never neither, and the first link of an entry and a path gives its status. It names no maker, is no entry and is never replaced: for an entry and a path the latest live status stands, and apart from it the latest live lift, which no status after it undoes. Every path a line holds is written plain — relative, no part of it empty, `.` or `..` — so one file is one path. **Every read and write is checked first**: the ledger on disk must start, byte for byte, with the one the state branch last committed, and is read a line at a time, each line validated against the shape its version names; a line that is no entry, or repeats an id, stops every read and write, naming it, and one a newer release wrote stops the engine until it is updated — each such stop kept for its screen, `render ledger-stop`. **The write verbs** — `ask`, `find`, `decide`, `replace`, `hold`, `move`, `merge` (`domain/ledger-write.cjs`) — each append one event and commit the ledger on the state branch, pushed: the place as the engine's dot-path, `<work-unit>.<phase>.<topic>`, or `<work-unit>.<phase>` for an entry at the unit's level (`move` always names a topic); the links as flags naming entries by a prefix of their id, resolved as git resolves a short hash; and the content as one JSON object on stdin — `ask` `{"text", "by", "who_moved_whom", "cites"}`, `find` adding `"how"` in words, `"known"` (`measured`, `exploratory` — measured in the conversation with no experiment — `documented`, `spike` or `read`), `"command"` and its `"result"`, and `"product_wide"`, `decide` `{"text", "why", "rules_out", "product_wide", "sealed", "alternatives", "evidence", "kind", "given", "cites", "by", "who_moved_whom"}` — `given` `own`, `your-call` (the person handed it to Claude), `dont-care` (the builder's) or `carried` (carried over by the migration, who decided it unrecorded) — `replace` the content of the kind it replaces with what it `drops`, and `hold`, `move` and `merge` `{"by", "who_moved_whom"}`; `cites` is a list of `{"path", "section"}`, a file's path from the state root and a heading in it. Content never carries a link, nor anything the engine gives, and `rules_out`, `product_wide`, `sealed`, `alternatives`, `evidence`, `kind`, `given` (`own`), `command`, `result` and `cites` may be left out. The person's decision is their own, never given otherwise; a `measured` or `exploratory` finding records its `command` and `result`, on any finding the two come together, and `known` is never null on a finding written now. The unit must exist and be live, the phase discovery or one of its work type's; a topic exists only before the spec and must hold an item in the phase, and an entry of the unit is written only from the topic it stands on; the session is the conversation's own, `CLAUDE_CODE_SESSION_ID`, and a write without one is refused. A decision answers a current question of its own unit; an entry is replaced, held or relied on only while current; a replacement's cause is never what it replaces, a `new-fact`'s being a finding and an `other-topic`'s a decision standing on another topic; only a question moves (to another topic of its unit, or to the roadmap as later, `--to roadmap:{item}`, an item the roadmap holds, which closes it where it stands) or merges (into a current decision, `--duplicate` naming another current decision that already answered it); `hold` confirms an entry still holds after the latest live replacement on the way of one it is held against; and `who_moved_whom` is held to the departure rule (`domain/ledger-verdicts.cjs`). A question an experiment of its unit still running measures is closed by the person alone, their own answer or one they hand Claude: Claude's own decision, move or merge of it is refused, naming the experiment. The engine sets a replacement's kind and the question a replaced decision answers, and, where the content leaves them out, the replaced entry's product-wide mark and who moved whom where the departure rule settles it. **The one-decision check** (`domain/ledger-one-decision.cjs`): a decision `decide` writes, and one `replace` writes in place of a decision, is judged by a separate Claude call before the writer lock — its answer, why and what it rules out, nothing else. Several rules refuses the write, nothing appended, naming each rule and the question, so the writer splits it; a call that cannot run lands the entry `unchecked`, for the late check. **Every run of the check is logged** — here, at a raise's draw, a line for each row, and in the late check — one line appended to `{config}/decision-checks.jsonl`, across the person's projects: `{"v": 1, "at", "project_id", "project", "unit", "verb", "rules", "outcome", "model"}`, `verb` the one whose check it was (`decide`, `replace`, `raise` or `late-check`), `outcome` `one`, `several` or `unchecked` where the call could not judge, `rules` how many it found and `model` the full id of the model that answered (each null where unchecked); never the entry's text. An append that fails is a warning, and the check stands. The layout hook refuses Claude's writes to the log. **What the trust log is told**: Claude's decision, or replacement of a decision, logs a call, but one carried over; the person's replacement standing over a lean the entry it replaces held logs a reversal; any other write logs nothing — the event kept waiting in the conversation before the append and landed after it, so a kill between them neither loses nor doubles it. While the migration runs (**`commit`**) it is told nothing, and nothing is kept waiting. Everything the request alone settles is refused before the writer lock, so a malformed write never waits on a peer; under the lock the ledger is folded, the place's liveness and every link checked again, the entry appended — copied beside the ledger with the line added and renamed over, so a read meets it whole or not at all — and committed (`ledger({unit}): {event} {id}[ in {topic}]`). Every commit of the ledger — each write's, the late check's, an asset link's and boot's catch-up — takes the files the ledger's `asset` lines name with it, as additions and edits alone, never a removal; a ledger with no asset line commits the ledger alone. Then, the lock released, the knowledge base's copies of the ledger are rendered and indexed, a failure a warning. Response `{"ok": true, "id", "committed", "note"?, "warnings"?}` — `id` the entry's short id; a commit git refused is `commit pending`, the entry standing in the ledger, and the next ledger write's commit, or boot's, takes the ledger whole; a commit held while the migration runs is noted `held for the migration's commit` (**`commit`**). **The read verbs** (`domain/ledger-read.cjs`) answer a projection of the ledger as JSON, worked out when read and never kept, current entries only, every id short: `record <work-unit> [<topic>]` the entries standing in a unit or on a topic, each with the live entries it replaced folded beneath it, its confirmations and the person's keeps, and the files linked from it (`assets`, each `{path, status, into}`, its latest live status and lift, either null where none gives one), the moves and merges made there, and the entries standing elsewhere that were made there, that it relies on, or that answer its questions (`{unit, topic, live, questions, findings, decisions, moved, merged, other_topics}`); `map <work-unit> <topic>` a topic's questions as they stand — `open`, `answered`, `merged`, `later` (moved to the roadmap, `moved_to` naming it), `moved-away`, `elsewhere` or `question-set-aside` — each with its current answers, whose and how given, and an open one an experiment of the unit measures marked `waiting_on` that experiment, `{experiment, running}`, whose record names the question's full id as `question` (`experiment create --question`) — running, or concluded with `running` false, until the discussion writes the result; an abandoned one leaves it open (`{unit, topic, live, questions}`); `product` the product-wide findings and decisions (`{findings, decisions}`); `affected <work-unit> [<topic>]` the current entries a replacement they never saw changed under them, waiting there until confirmed or replaced (`domain/ledger-affected.cjs`; `{unit, topic, live, waiting, affected}`); `since <work-unit> [<topic>]` Claude's current decisions the place shows that no look on this machine has covered, none carried over, each with the files linked from it (`assets`, as `record` shows them) — what Claude spiked or read to make the call (`domain/ledger-since.cjs`); and `shown <work-unit> [<topic>]`, answering as `since` does and adding each call it showed to the unit's last-looked mark, `.leeway/.cache/.marks/{unit}.json`, off the state branch, under the mark's own lock. A read takes no lock of its own but `shown`, which takes the mark's; a read whose ledger check fails makes it again under the writer lock, once a landing a kill cut short is finished, before it stops; a decision the late check judged shows `late_check`. It refuses a unit the project lacks and a topic the unit lacks. **`late-check`** is boot's detached job (`domain/ledger-late-check.cjs`): each decision that landed unchecked, with no `checked` event naming it, is judged, then under the writer lock a `checked` event naming it and its rules, `one` or `several`, is appended and committed, one decision at a time; one the call still cannot judge stays owed for the next start. A decision found holding several rules shows flagged wherever its record is read. **`asset`** — spikes, and the files that inform a decision linked from the ledger's entries (`domain/asset.cjs`). **The verb never moves a file**: Claude writes it where it lives, and the verb records where that is. **`spike <work-unit> <slug>`** starts a spike: it numbers the unit's next one in the order spikes start, one past the highest of its `spikes/NNN-{slug}/`, makes its folder and its twin at the same path under the gitignored cache — where the spike's dependencies, builds and run output go — and answers both, `{"ok": true, "spike", "path", "folder", "cache"}`: `spike` the folder's name (`001-frame`), `path` its path from the state root, the one a link names its files by, and `folder` and `cache` absolute. A design spike's rounds go in `round-N/` inside it. Nothing is committed — the folder holds nothing yet — and the writer lock is held around taking the number alone. It refuses a slug that is no kebab-case slug, a slug one of the unit's spikes has already (`… carry on in it, or name the new one apart`), a unit the project lacks, and one cancelled or completed. **A link** is the ledger's `asset` event (**`ledger`**) from an entry to a file, by its path from the state root, written plain. Each names a current entry made in the unit, `--entry` a prefix of its id; is tagged as that entry is — its unit, topic and phase — and carries the conversation's session, `CLAUDE_CODE_SESSION_ID`, a link without one refused; and commits the ledger on the state branch (`ledger({unit}): asset {id} …[ in {topic}]`), as every ledger commit does — with every file the ledger's links name (**`ledger`**). So a file enters the state when a link first names it, and every ledger commit from then on carries its edits and a linked folder's new files; a link whose commit was refused is caught up with the next ledger write's, or boot's; while the migration runs the files go with the line, held for its commit (**`commit`**). No ledger commit removes a linked file: a lift after the file moved into the product commits no removal. A file in `assets/` or a spike that no entry links is not taken by the ledger's commits — it stays untracked until a link names it, and two clones can start the same spike number for spikes nothing links yet — but `engine commit <work-unit> -m`, which takes the whole unit folder, and `--workflows` and `--migrations`, which take the whole state, commit it as they find it. A path is stored as the file system spells what of it exists, so one file is one path where the file system ignores case, and a folder's without a trailing slash. A link belongs to its entry: a replacement carries none forward, so a file the replaced entry linked shows on no current entry until `add` links it from the new one — and `status` on a file only replaced entries link refuses, naming `add`. A link to a question is tagged at the topic the question was written on, so it goes dead where that topic is set aside after the question moved. **`add <work-unit> <path> --entry <id> [--status <canonical|reference>]`** is the first link of an entry and a file, and gives its status: the path must name a file or folder below one of the unit's homes — its `assets/`, or one of its spikes — or the product's, `.product/assets/` or `.product/spikes/NNN-{slug}/`, or a spike's folder itself (`{unit}/spikes/NNN-{slug}`), never the bare `assets/` or `spikes/`; one anywhere else (`… is not where an asset lives`, naming the homes — a unit's `imports/` among them), not written plain, or naming nothing on disk (`{path} names no file — save it there first, or correct the path`) is refused. The argv, the unit and the paths are refused before the writer lock, so a malformed call never waits on a peer; under it the ledger is folded, the entry resolved and checked, the links appended and the ledger committed, and then, the lock released, the knowledge base's copies — which show each entry's files — rendered and indexed, a failure a warning. Response `{"ok": true, "path", "links", "committed", "note"?, "warnings"?}` — `links` each link written, `{id, entry}`, both short; a commit git refused is `commit pending`, the link standing in the ledger for the next ledger commit, and one held while the migration runs is noted `held for the migration's commit`.

**`gate`** — the person's answer at a gate (`domain/gate.cjs`), logged to the trust log by the gate's name, answered with what the row leads to. **The gate shown.** Every MENU's gate is collected whether or not the gate mod announced itself (its GATE block is still emitted only where it did), and a command's output carries one MENU at most, whose gate is recorded for the calling conversation as `gate-shown.json` in its folder — the gate's name, its question, each row by its key with its word, its head, whether the engine recommended it and its `next`, each typed row by its key (its label's words, lowercase, joined by hyphens: `comment`, `1-4`) with its label and its `next`, and when it was shown. The engine's dispatch and every gateway script (`runGateway`) write it once the command has answered, never as the MENU is built, and never for a command that failed; nothing is written without `CLAUDE_CODE_SESSION_ID`, a menu composed inside an illustration is never recorded, a command whose MENU states no gate leaves the last one standing, and a record that cannot be written never fails the command. It is written for a conversation not yet marked too, so a gate before the project has state is answered like any other, its event naming no project. **The name** is the one the MENU declares, up to its first ` — `: one gate is one name, however many entries share it (`in-session gate — 3` is `in-session gate`, and `gate` takes either), and no name is two menus' — a gateway names each of its menus from its own table of gates (`GATES`, `menuBlock(name, body)`); a name the trust log cannot key refuses the answer rather than being made to fit. **The answer.** `--pick <key>` a row; `--typed <key>` a typed row, such as a Comment; `--typed` alone free text naming no row. No typed text reaches the engine: it stays in the conversation, and the event says only that the answer was free text, its reading null until the separate call reads it. The name may be given quoted or as bare words. **How it came:** `pressed` only where the gate mod announced itself to the command and its `pressed.json` names this gate and this row, sent after the gate was shown; otherwise `typed` — with the mod off, always. The recommended row is the engine's, from the record. It refuses, logging nothing, with no session id, no gate shown, another gate's name, a key the gate lacks, and a gate already answered — the record marks the answer, and only the gate shown again takes another. **`next`** is what the row's composer declared — `{"kind": "engine", "argv": […]}`, `{"kind": "handoff", "skill", "args": […]}` or `{"kind": "continue"}` — null where it declared none and for free text; `gate` performs nothing of it. It takes no writer lock: it writes the trust log under that log's own lock, and the conversation's folder. While the migration runs in the project (**`commit`**), the answer reaches no trust log. Response `{"ok": true, "gate", "picked", "recommended", "via", "next"}`, `warnings` where the trust log could not be appended to and the event waits in the conversation.

```bash
engine gate "<name>" --pick <key>       # a row the person picked, pressed or typed
engine gate "<name>" --typed [<key>]    # a typed row, or free text naming none
```

**`raise`** — a call Claude has a lean on, answering a question or replacing a decision, put through the decision point and, where it asks, drawn for the person; or a fact only the person holds, answering a question, always drawn for them; and the person's answer to either, recorded by one command in the ledger and, for a call, the trust log (`domain/raise.cjs`, the screen `domain/projections/raise.cjs`, the decision point `domain/decision-point.cjs`). **The draw**, `raise <work-unit>.<phase>[.<topic>] --answers <question> [--relies-on <id> …]`, takes the place and the links as `ledger decide` does, since the answer lands as that decision, and Claude's call on stdin as one JSON object: `{"question", "rows": [{"key", "name", "text", "notice"}, …], "lean", "why", "sort", "mechanism", "product_wide"}` — the question as the person reads it, cold and product first; each row's key, a short name for what the person would notice, the answer's text and what they would notice; the lean, a row's key; why Claude leans so; `one` or `several`; the mechanism behind the screen's toggle; and whether the answer is product-wide (`true` or `false`). Every other field is text on one line but the mechanism, which may hold several, drawn as written; no field beyond these is taken. **On a replacement**, `raise <work-unit>.<phase>[.<topic>] --replaces <entry> --reason <new-fact|other-topic|changed-mind|was-wrong> [--cause <id>] [--relies-on <id> …]` takes the place and the links as `ledger replace` does, since the answer lands as that replacement, and the same call: its rows Claude's proposed answers in place of the decision's, one at least, and its lean one of them. The screen adds a row of its own, `keep` — `Keep it as it stands`, its text the decision's answer as the draw found it, `nothing changes` — for the person to keep the decision. **It refuses**, drawing and sealing nothing: no `CLAUDE_CODE_SESSION_ID`; no workflows state; a place or a link `ledger decide` refuses — `ledger replace`, on a replacement — checked by that code against the ledger as it stands and said in the raise's words; a question no longer open — answered, or merged into another's answer — whether or not the conversation holds its seal; an entry replaced that is no decision; stdin holding no JSON object, a field the call does not hold, lacks, or holds in another type; on a call, fewer than two rows — on a replacement, none; a key the trust log cannot key (letters, digits, `-` and `_`, up to 24), one two rows share, or one that is the screen's own word in any case (`t`, `e`, `technical`, `explain`, `comment`, and `keep` on every raise, so a raise event's `keep` always means a keep); on a call, a lean naming no row of Claude's; a proposal whose text is the decision's answer as it stands; a row holding several rules; and a seal that cannot be written. **The one-decision check** judges every row of Claude's at once, never `keep` — its answer, and Claude's other rows as what it rules out; the why comes with the person's answer — so the draw waits about one call; a row holding several rules refuses the raise, naming each such row and its rules (`payload.several`), and a row the call cannot judge is drawn all the same. The why is not judged with the rows, so every entry a raise lands lands `unchecked: true`, for the late check to judge whole at the next start: the seal's `rows_judged` records what the draw judged, and the answer makes no call. **The decision point** answers `ask`, `proceed` or `blind`, with the reason the person is shown; until the ask rule is built every call asks, its reason the rule's own. A `proceed` lands Claude's call, drawing and sealing nothing: Claude's decision answering the question — the lean row's text, the other rows what it rules out, its why — through the writer lock and the write `ledger decide` takes, the question checked open under it — on a replacement, Claude's replacement of the decision through the write `ledger replace` takes, dropping the decision's answer as it stood — logged as a `call` event carrying the sort. A `blind` refuses, naming where it is built. **A fact**, `raise <work-unit>.<phase>[.<topic>] --answers <question> [--relies-on <id> …] --fact`, is a fact Claude cannot check and only the person holds — a deadline, an outside constraint, an account Claude cannot reach — taking the place and the links as a raise answering a question does, and on stdin `{"question", "rows": [{"key", "name", "text", "notice"}, …], "mechanism", "product_wide"}`: no lean, no why and no sort, each refused as a field the fact does not hold. Its rows may be none, one or more, each checked as a call's row is — its shape, a key two rows share, the screen's own words. Nothing in it is Claude's to judge or decide: the one-decision check judges no row, its seal's `rows_judged` empty, and the decision point is never reached, so a fact is always asked, whatever the decision point would answer, its reason its own, `Only you know this: it's a fact I can't check.` Its answer, a pick (`{"why"}`, who moved whom refused: it moves no one) or the person's own words (`{"text", "why"}`, with `"rules_out"` where Claude gives it), lands as the person's decision as any raise's does, but with `sealed` null and `who_moved_whom` `none`: no lean, so no departure, and nothing waits in `verdict queue` or shows in `ledger since`. A fact writes nothing to the trust log, neither its answer nor `--didnt-follow`, which still counts on the seal and leaves the raise open: it takes no label, adds no evidence and meets no threshold. `--fact` refuses given twice, and with `--replaces`: a fact that changes is the person's to say, and the decision it changes is replaced as any other. **The seal** is `raise-shown.json` in the conversation's folder, each raise by its id — `{"v", "id", "menu", "place": {"unit", "phase", "topic"}, "answers", "relies_on", "replaces", "call", "fact", "rows_judged", "reason", "at", "answered", "didnt_follow"}`: the call as given, whether it is a fact, the question — null on a replacement — and the entries relied on by full id, the replacement — `{"entry", "reason", "cause", "keep"}`, the decision by full id, the reason, the cause and the `keep` row, so the answer needs nothing more; null on a question — the menu it is declared as, the keys of the rows whose answer and what it rules out the check judged one rule, the reason, when it was shown, its answer (null until given) and how many times the person did not follow it. The id is minted at the draw and is the id the raise's entry lands as. A raise of a question, or of a replacement of a decision, the conversation holds an open seal for — the same place, the same question or decision — draws that seal, whatever call it is given, so the answer is measured against the first lean, and the response says so (`redrawn`). A seal of another version is never matched and stays as written; a seals file that cannot be read refuses the raise. Every write to the seals — a raise sealed, answered, or not followed — takes a lock of their own beside the file, `raise-shown.json.lock`, reads them again under it and changes its own raise alone, so raise commands run at once in one conversation keep each other's; a draw finding an open seal of its question or replacement written while it waited draws that one, `redrawn`. The layout hook refuses Claude's own writes to the seal. **The screen** is one MENU, declared `raise — <id>`: where the question stands (`{Unit} · {Topic}`), the question, `I lean: …`, WHAT YOU'D NOTICE with a line per row, WHY I'M ASKING with the reason, THE MECHANISM where the toggle shows it, then `◆ Which way?` over the rows — on a replacement Claude's, then `keep` — the lean `(recommended)`, `t/technical` (show or hide the mechanism, leading to `raise show`), `e/explain` (I don't follow, leading to `raise answer <id> --didnt-follow`) and `Comment`; every line above the rows is the gate payload's statement. A fact's screen draws no `I lean:` line and no row `(recommended)`, WHAT YOU'D NOTICE only where it has rows, and asks `◆ What's the answer?`, its `Comment` row taking the answer in the person's own words. Claude's words are escaped, so they read as written, never as markup; each of the mechanism's lines is drawn from its first word. **A raise is no gate**: its menu is never recorded as the gate shown, `gate raise …` refuses, naming `raise answer`, and drawing one clears the conversation's gate shown. **`show <id> [--technical]`** draws a raise the conversation drew again from its seal alone — the id or a prefix of it — `--technical` showing the mechanism; it refuses a raise the conversation never drew — saying a raise is answered in the conversation that drew it, so after a `/clear`, or a resume under a new session, raise the question again — and no session id. Neither takes the writer lock: each writes the conversation's folder alone. **`answer <id> (--pick <key> | --own | --didnt-follow)`** records the person's answer to a raise the conversation drew, found by its seal — the id or a prefix of it. A pick takes `{"why"}` on stdin, with `"who_moved_whom": "claude-moved-person"` on a pick of the lean where the person came round to it; the person's own words take `{"text", "why"}`, with `"rules_out"`, a list, where Claude gives it; the why is Claude's account of the person's reason. Either lands as the person's decision at the id the draw minted, where the raise was drawn, answering its question and relying on what it relies on — `sealed` the lean row's text, `product_wide` the call's, `kind` null, `unchecked: true` — a pick's text the row's and what it rules out the rows not picked, own words' text theirs and what they rule out Claude's list, else none. On a replacement either lands as the person's replacement of the decision instead, for the reason and the cause sealed, dropping its answer as it stood, a pick ruling out Claude's other proposals. **`--pick keep`**, on a replacement, takes `{"why"}` on stdin as a pick does: the person's `kept` line lands at the id the draw minted, where the raise was drawn — the decision kept, by full id, the reason and the cause sealed, `why` Claude's account of the person's reason, `sealed` the lean row's text, Claude's proposal — and changes nothing current: the decision stays current, nothing relying on it is affected, and `ledger record` shows the keep beside it, under `kept`. A live keep confirms the decision as `ledger hold` does against the replacement it names as its cause: where that replacement is the latest on a way the decision is held against, `ledger affected` no longer lists it for that way, until a newer replacement on it; a keep naming no cause, or a cause on no such way, confirms nothing. No `ledger` verb writes a keep. **Who moved whom is the engine's alone**: `person-moved-claude` for a pick other than the lean, for own words, and for a keep, which stands over Claude's proposal — a departure, waiting in `verdict queue` with the proposal as its lean; `none` for a pick of the lean, or `claude-moved-person` where stdin says so; any other value given refuses. Claude proposed the replacement, so no answer to it is a reversal. **The same command** logs the trust log's `raise` event naming the line it landed, an entry or a keep — the sort, the lean's key as `sealed` and the row's as `answer` (`keep` for a keep, null for own words), `via`, `with_text` (true for own words), `reading`, `kind`, `label` and `blocked_build` null, `didnt_follow` false — never a word of the question, the rows or the why: under the writer lock, the event kept, then the append, land and commit `ledger decide` takes, then the seal marked answered, `{"at", "answer"}`, with the row the ledger's entry holds. An answer was `pressed` where the gate mod announced itself and `pressed.json` names this raise's menu and the row, pressed after the raise was drawn; anything else was `typed`. **Once**: under the lock, a ledger holding the raise's id means it is answered — answered again, after a kill past the append or a compaction, it writes no second entry and no second event, finishes what a kill left (the event landed, the ledger committed), and says the raise was answered already, with the row the line holds — `keep` for a keep, else the row whose text the entry holds, null for own words — which marks the seal where it is not; the seal keeps its first answer. Killed before the append, the rerun lands its own answer, the event the killed run kept let go. Else the question must still be open. **`--didnt-follow`** takes no stdin and writes no ledger line: a raise event in the trust log alone — no entry, no answer, no reading, `didnt_follow` true — and the seal's `didnt_follow` counted; the raise stays open, for `show` and an answer after. On a raise the ledger holds the answer to — an old screen's press — it logs and counts nothing, and answers `{"ok": true, "raise": "<id>", "already": true, "answer"}`, the row the line holds, marking the seal where it is not. **It refuses**, recording nothing: no session id; a raise the conversation never drew, or a prefix several begin — the first saying the way on, as `show` does; argv of another shape; a key that is no row; stdin holding no JSON object, lacking the why — for a pick, own words and a keep alike — (and the text, for own words), or holding a field its form does not take; who moved whom given where it is the engine's alone; a question no longer open, answered since the draw; and on a replacement a decision no longer current — the refusal names the decision, what replaced or merged it since the draw, and what is current now to raise again on — the person's answer stays in the conversation. The person's answer to Claude's lean is recorded here alone: the person's `ledger decide` or `ledger replace` carrying `sealed` refuses, naming `raise answer`, and the person's `ledger decide` moves no one — `who_moved_whom` `none`, set where it is left out, any other refused, naming `raise answer` — nor does their `ledger replace`, for any reason, of a decision on a chain Claude never leaned on, no entry down it Claude's own or carrying a sealed answer: no departure, no reversal. Response: the draw `{"ok": true, "decision", "reason", "raise": "<id>", "redrawn": bool}` — `redrawn` true where the conversation's open seal of the question or the replacement was drawn and the call given set aside — `warnings` where the ledger's read gave any; `show` `{"ok": true, "raise": "<id>"}`; each followed by the MENU. A proceed `{"ok": true, "decision": "proceed", "reason", "id", "committed"}`, no MENU; `answer` `{"ok": true, "raise": "<id>", "id", "committed"}` — each the line's short id and the state commit, as `ledger decide` answers, `committed` null where an answer given again commits nothing, `note` where the commit is pending; an answer given again adds `"already": true` and `"answer"`, the row's key the ledger holds — `keep` for a keep — or null — or, not followed, `{"ok": true, "raise": "<id>", "open": true}`; `warnings` with any where the ledger's read or an append to the trust log gave any.

```bash
engine raise <work-unit>.<phase>[.<topic>] --answers <id> [--relies-on <id> …]   # Claude's call on stdin; ask, proceed or blind, and the screen
engine raise <work-unit>.<phase>[.<topic>] --replaces <id> --reason <new-fact|other-topic|changed-mind|was-wrong> [--cause <id>] [--relies-on <id> …]  # the same, proposing a decision's replacement; the screen adds keep
engine raise <work-unit>.<phase>[.<topic>] --answers <id> [--relies-on <id> …] --fact   # a fact only the person holds on stdin, no lean; always asked, nothing to the trust log
engine raise show <id> [--technical]                                            # the raise drawn again from its seal
engine raise answer <id> (--pick <key> | --own | --didnt-follow)                # the person's answer on stdin; the ledger and the trust log, or the trust log alone
```

**`verdict`** — the verdicts on departures (`domain/verdict.cjs`; the departure rule and the queue's projection are `domain/ledger-verdicts.cjs`, the departures and verdicts this machine logged `domain/trust-evidence.cjs`). A departure is the person's decision whose answer stood over Claude's lean, or their keep of a decision Claude proposed to replace, standing over the proposal — who moved whom `person-moved-claude` on its ledger line — that this machine's trust log holds as one: a raise answered with another row than the lean — `keep` among them — or in the person's own words, or the person's reversal of an answer that held the lean. The trust log is the machine's, so a departure is judged on the machine where it was made: a departure the ledger brought from another machine is no departure here, nor is the person's replacement of their own departure still against the lean, which logs nothing and is owed no verdict; an event naming an entry the ledger lacks is skipped; and an event under another project's id is that project's. The trust log's events are read landed, waiting in a conversation's folder after an append that failed, or kept there ahead of an entry the ledger holds, by whichever of the project's clones on the machine. `queue` answers every such departure made in a live place, current or replaced since, that has no verdict — in the trust log, or waiting in any conversation's folder for it — in the ledger's order: each its line as a ledger read shows it, with `standing`, where it stands, and `lean`, Claude's lean beside it — the sealed answer of the nearest entry down its chain that holds one, or the answer of the nearest that held the lean; beside a keep, the proposal it seals, the keep's row carrying `text`, the answer it kept, as a decision's carries its own. Response `{"ok": true, "departures": […]}`; a read, holding no lock, refusing any argument. `give <entry> <nothing|fix|loss|skip> --at <point>` logs a `verdict` event in the trust log (`{config}/trust.jsonl`, beside the conversations' folders): the departure by its full id, the verdict, and the point it was given at — `decided` (a topic's decided screen), `ready-to-build`, `conclusion` (an investigation's), `finish` (the finish gate), `close` (a quick-fix's) or `queue`. The entry is a prefix of its id, resolved as a ledger link's is. It refuses an entry the ledger holds as no departure; a departure this machine logged none for — made on another machine, whose verdict is given there, or the person's replacement of their own departure; a departure made in a place no longer live, which the queue leaves out; and a departure whose latest verdict, landed or waiting in any conversation's folder, is no skip: a skip leaves the departure waiting in the queue for the verdict that follows it, and a verdict given is corrected as a correction, never given again. It runs under the writer lock, so a peer's verdict on the same departure never lands between its check and its append, and writes nothing the state holds. Response `{"ok": true, "entry": "<short id>", "verdict": …, "point": …}`; an append to the trust log that fails rides as a warning, the event waiting in the conversation's folder for its next record or the next boot.

```bash
engine verdict queue                                          # the departures waiting on a verdict
engine verdict give <entry> <nothing|fix|loss|skip> --at <point>  # a verdict on a departure, logged in the trust log
```

**`brief`** — a brief for one of the workflows' own agents, filled by the engine from the records and stored for the dispatch to carry (`domain/brief.cjs`, the records `domain/brief-records.cjs`, the spec's sections `domain/spec-sections.cjs`). **The roles**: each names its template, `content/briefs/{role}.md`, the agent it is dispatched as, and the records it draws on — `builder` (`leeway-builder`): the task, its spec sections, the decided calls and the linters; `reviewer` (`leeway-reviewer`): the task, its spec sections, the decided calls, the diff's range and the linters; `fix` (`leeway-builder`, sent to the builder by SendMessage): the pair's two reports and nothing else; `product-researcher` (`leeway-product-researcher`): none; discussion's, each for a topic (9.8.13) — `deep-dive` (`leeway-deep-dive`): the question, the dive's kind, the topic's record, the product record and the report; `perspective` (`leeway-discussion-perspective`): the question, the lens, the topic's record, the product record and the report; `synthesis` (`leeway-discussion-synthesis`): its pair's question, the perspectives, the topic's record and the report; `discussion-reviewer` (`leeway-discussion-reviewer`): the topic's record, its log, the other records, the product record and the report; `closing-pass-reader` (`leeway-closing-pass-reader`): those and the gap review; and `plain-search` (`leeway-plain-search`, 22.6.10): the conversation's last knowledge query alone. A role whose records include the task's takes `<unit> <task>`, the task as `{phase}.{n}`; one whose records include a topic's takes `<unit> <topic>`, refused for a unit the project lacks, a topic the unit lacks, and a topic set aside, cancelled or postponed (5.8.17); any other takes neither. A role takes the flag each of its records names, every one but a read dive's `--path`, once, and no other: `reviewer` `--base <branch>`, `fix` `--report-a <path>` and `--report-b <path>`, `--question <id>` for the question, `--kind <survey|read|feasibility|landscape|verify>` for a dive's kind, and `--path <file>` for the file a read reads, and `--agent <id>` — the dispatch `agent dispatch` answered — for the question it is bound to, its pair's question, the report, the lens and the perspectives. A flag carries a name, an id or a path, never text that reaches a brief: anything else an agent should know goes onto the task (`task add`) or into the ledger. **The template** is markdown: its own words, and a slot, `{{record}}` alone on its line, for each record its role draws on — refused, before anything is read, for a slot that is not alone on its line, one no record answers or its role does not draw on, or a record's slot missing or there twice. **The records**, each in one fixed form: `task` — the task's text whole as the tracker holds it, each of its headings a level down, then each addition in order under a heading of its own, `## Added by the orchestrator` or `## Added by the person`; `spec-sections` — each section the task's `Spec reference` cites, verbatim from the unit's `spec.md`, in the order cited, each once, a part whose own area is drawn left to the area: an area is a heading `## N. Title` and runs to the next heading at level two or above, holding its parts; a part is `### N.M Title` and runs to the next at level three or above; a heading inside a fenced block is text. A reference cites in runs: a run opens at `§` or `§§` and goes on over numbers joined by `,`, `and` or `&` (`§1.1, 1.2`, `§1.1 and 2.1`), and two numbers joined by `–`, `-` or `to` are a range, every section at their level from the first to the last in the spec's order (`§1.1–1.3`, `§1 to 3`); every number a run holds is cited; `decided-calls` — the unit's current decisions at its own level (topic null), the person's and Claude's, in the ledger's order, each one list item, `- {short id}, {the person's|Claude's}: {answer}` with its `Why:` beneath, every line after an item's first indented; `linters` — the project manifest's `environment.linters`, each `- {name}: {command}`; `diff-range` — in each repository holding the task's branch, the project's own first and a nested one only where the branch holds work there, as `land` finds them, its base the `--base` branch where the repository has it as a local branch, else the repository's default branch as `land` picks it, a heading ``## In {the project's repository|`{folder}`}: `{base}...{branch}` `` and beneath it the range's `git diff --stat` fenced, every path whole and the graph at 40 columns, or `Nothing changed in the range.` — never the diff's text; `report-a` and `report-b` — the file its flag's path names, absolute or from the working folder, verbatim, under the template's labels `# Reviewer A's report` and `# Reviewer B's report`; and a topic's, never a word of the conversation (26.1.5): `topic-record` — the topic's record as `ledger record <unit> <topic>` answers it, each current entry with what it replaced (9.2.5), fenced as JSON; `topic-log` — the absolute path of the topic's `topics/{topic}/log.md`; `other-records` — the record of each other live topic of the unit that shows anything, in the order the manifest names them sorted, each under `## {topic}` and fenced as JSON, never a log, and none of a topic set aside; `product-record` — the product record as `ledger product` answers it, fenced as JSON; `question` — the question `--question` names, by any wording or a prefix of one, in its current wording, `{short id}: {text}`, refused where it names no question, is no longer current, stands on another topic or is not open (answered, merged or later); once every record is drawn, the dispatch `--agent` names is bound to it, `question` on its row, by its first wording — refused where the dispatch was bound to another; `pair-question` — the question each perspective of that synthesis's set was bound to, in its current wording, refused where one was bound to none or they differ; `dive-kind` — the kind `--kind` names, or for a `read`, `read — `{absolute path}``, the file `--path` names, refused for a kind that is none, a read naming no file, and another kind naming one; `gap-review` — `A gap review has run since this topic's last decision: {id}.`, naming the latest report-backed review or closing pass whose `ledger_mark` the topic's last decision — a replaced answer among them — does not pass, else `No gap review has run since this topic's last decision.` (9.9.6); `report-to` — the absolute path of the report the dispatch `--agent` names writes, refused where the topic's discussion store lacks it, it is another kind than the role is briefed for (`review`, `deep-dive`, `perspective`, `synthesis`, `closing-pass`), or it is no longer in flight; `lens` — that perspective dispatch's label, a lens of the polarity pairs as `agent dispatch` holds it; `perspectives` — the report of each perspective in that synthesis's set, verbatim, in the order they were dispatched, refused for one with no report; and the plain search's: `knowledge-query` — the conversation's last `knowledge query` as it kept it, `Terms:` and `Filters:` each flag as given, or `none`, then `It returned:` and its output fenced, `It failed: {why}`, or `It never finished.`, refused where the conversation has run none. A decided-calls, linters, topic-log, other-records, topic-record or product-record record the project holds none of reads `None recorded.` **The brief** is stored at `{config}/conversations/{session-id}/briefs/{id}.md`, exactly what the agent is handed, its id a new one; beside it, `{id}.json` records whose it is, `{"role", "agent", "unit", "task", "topic"}` — the task (`{phase}.{n}`) and the topic each null for a role that takes none, the unit null for a role that takes neither. **The implementation-task bookkeeping** — `init`, the three-argument `start`, `fix-attempt`, `complete` and `analysis-cycle` — is format-blind and manifest-side — the one other write being the calling conversation's position, which `start` puts its task on and that task's `complete` takes it off (see `conversation`). The loop's brief, result header, and gate sections are served by their own `render` surfaces (`task-brief`, `task-result`, `task-gate`, `fix-gate`, `blocked-tasks`, `cycle-limit`, `cycle-gate`), fetched at the stage that displays them.

```bash
engine task init <work-unit> <topic>                       # create-or-resume the implementation item
engine task start <work-unit> <topic> <internal-id>        # record current_task; fresh task (mode started): reset fix_attempts, drop the fix-tracking file; restarting the in-flight task (mode resumed) preserves both
engine task fix-attempt <work-unit> <topic> <internal-id> --findings-file <path>
engine task complete <work-unit> <topic> (<internal-id> | --external <id>) [--skipped] [--next-task <id|~>] [--phase <N>] [--phase-complete]

```

`init` creates the item with `status: in-progress`, gated gate modes, zeroed counters, `current_phase: 1`, `current_task: null` — `linters`/`project_skills` left absent for the setup steps to record (absent is never asked; a stored `[]` is a confirmed empty set) — or, when it already exists, performs a session-only reset (four gate modes → `gated`; `analysis_cycle_total`, arrays, and progress fields untouched; `fix_attempts` → 0 unless `current_task` has a live fix-tracking file — a crash-resume mid-task keeps the in-flight pair). Response: `{"ok": true, "mode": "created"|"resumed", "gates": {…}, "counters": {…}}`. `start` records the internal id as `current_task`, resets `fix_attempts`, and drops the task's fix-tracking file (clean slate per task; the deletion rides the next commit) — unless the id is already `current_task` AND its tracking file exists (a true resume, or a post-compaction re-run), where both survive as that task's convergence history; re-running `start` for the in-flight task is idempotent. The id must carry its phase (`{topic}-{N}-{k}`) — one without is refused before anything is written. Both modes answer `do_banking` — `true` while the task's phase is still taking BANK deposits: the work unit's `work_type` is not `quick-fix` (its plan never takes a boundary, so nothing would drain a deposit), the phase is not in `consolidated_phases`, and `staging.p{N}` is absent; derived on every call from the manifest, never stored. `fix-attempt` increments `fix_attempts` and appends the findings file's content verbatim under a `## Attempt {N}` section in `.leeway/{wu}/implementation/{topic}/fix-tracking-{internal-id}.md` — committed history beside the analysis reports, the per-task record convergence diagnostics and post-hoc flow analysis read; response carries `attempts`, `threshold_reached` (≥ 3), and `fix_gate_mode`. `complete` pushes the internal id to `completed_tasks` (skips included — the plan carries the skip distinction; an id already recorded is a no-op push, same response), zeroes `fix_attempts` when the completed id is the in-flight `current_task` (the finished task's counter never leaks into the next; an out-of-band completion of another id leaves a live fix loop's counter untouched; the tracking file stays as history), resolves `--external` by mirroring manifest `key-of` over `{wu}.planning.{topic}.task_map`, sets `current_phase`/`current_task` (`~` = null) when flagged, and pushes to `completed_phases` on `--phase-complete` (`--phase`, or the phase embedded in the internal id) — the plan phase's close, which also returns the phase-bounded gates (`task_gate_mode`, `fix_gate_mode`) holding `bounded` to `gated`, named in `recorded.gates_reset`; `auto` is the session's and stands. `analysis-cycle` responds with `cycle_total`, `over_cycle_limit` (> 3 — the topic's lifetime count, so a loop spread across sessions still trips it), and `analysis_gate_mode`.

**Gate sections.** The loop's brief, result header, and gates render via the `render` catalogue's task surfaces (`task-brief` and `task-result` in `domain/render.cjs`; `task-gate`, `fix-gate`, `blocked-tasks`, `cycle-limit`, `cycle-gate` — builders in `domain/projections/tasks.cjs`), each fetched by the flow at the stage that displays it. `task-brief` is the pre-dispatch announcement — the shared task header plus the payload's summary and watch lines, rendered between `task start` and the executor dispatch each time the loop takes up a task. `task-result` is the one shape for every presentation moment — approved, needs-changes, blocked, failed — the same header with a markdown verdict line between its marker and its meta rows, deriving the verdict detail from `fix_attempts` against the threshold. Both headers are built by one definition, so the announcement and the result cannot drift: the `▪` marker naming the task (`title`, with the `current`/`total` ordinal when the format's listing yields it), then the id, phase, and position rows. Both payloads require an `id` naming the in-flight task — a stale per-topic file refuses rather than rendering under the wrong task; the task's name is the plan format's, so it rides in the payload rather than being read from the manifest. Gate-mode branching renders inside the gate surfaces: `task-gate` and `fix-gate` read the item's in-flight `current_task`, gate modes, and `fix_attempts` from the manifest and answer with the menu where the loop stops or the continuation line where it must not — every gate branch renders an artifact; an auto branch that rendered nothing would let the loop end a turn by silence. The result header names the task, so the gates never repeat the id. `blocked-tasks` renders the open tasks and what blocks each above its stop menu — plan-format state the engine never reads, so it rides the session's payload. Conversational content (reviewer findings, executor summaries) never renders here — it stays with the session.

**`land`** — a task's change landed through the project's landing driver (`domain/landing.cjs`): `open` the task's pull request, `chain` it into its phase's stack, merge a `phase` whole, and `finish`, which merges every phase still standing — the review phase's fix phases after every other. **The driver** is a folder the workflows ship, `scripts/drivers/landing/{name}/driver.cjs`, named by the project manifest's `drivers.landing`; where that is absent the first verb settles it — the driver serving the project's remote, else the local driver — and commits the setting on the state branch (`chore: the landing driver is {name}`), whatever the driver then does. A verb that fails where a tool the driver needs is missing or fails to run is refused for that. **The names** (`domain/landing-names.cjs`), one form for every driver: a task's branch is `{type}/{unit}-{phase}.{n}-{slug}` — the slug the title lowercased, its accents folded (`ß` as `ss`, `æ` as `ae` and the like), its runs of letters and digits joined by `-`, as many whole words as fit in 48 characters (a first word longer cut at 48), and `task` where no letter or digit is left — the name the task's branch must already carry, made by whoever makes the branch; a phase's branch `feat/{unit}-phase-{phase}`; a task's pull request title, and the subject of the commit it squashes to, `{type}({unit}): {title}`, the message closed by a `Task: {internal-id}` trailer — how a landed task is read back off git. **Where it lands**: the default branch of each repository of the project the task touches — its own, and each nested in its folder, a clone or a submodule — never the state branch, under the same names, children first and the project's own last, so a submodule's landing merges before the repository holding it records its pointer. `open` reads the task's type and title from the tracker as `task show` does — a task it lacks, or holds with no type, refused — and refuses, before it opens anything: no repository of the project holding a branch by that name; the branch changing nothing in the repositories holding it; its change carrying anything under `.leeway/` at the top of the project's repository; the branch not descending from its chain's tip; a branch pointing a submodule at a commit the submodule here does not hold; and, where no repository holds anything past its default branch or the chain's tip and none has the task opened already, nothing past the tip anywhere, naming the project's own where it holds the branch. Past those, a repository with nothing past its default branch or the chain's tip is passed over while another holds the task's work. A merge refuses, before anything merges, where a default branch points a submodule the walk lands in at a commit the submodule's own default branch does not descend from; a driver landing through a host refuses a repository whose remote it does not serve. Every verb first stops on a rebase stopped in a worktree a remedy made, until it is settled or ended there. A refusal in a nested repository names it, one after a repository moved names what moved where and carries the warnings those landings gave, and the verb run again picks up where it stopped; `open` and `phase` run again where their work is done answer `already: true`. `chain` refuses a task not open, `phase` a phase with no task opened; `finish` makes each repository's next merge until none is left, a refusal saying which phases merged before it. Nothing is recorded but the driver setting, the tracker's setting up that `open`'s read commits where the state branch lacks it, and what a driver keeps in a repository's own refs: the landing's state is read off git and the host each time. Response: `open` `{task, branch, already?, repos}`, `chain` `{phase, repos}`, `phase` `{phase, already?, repos}`, `finish` `{repos}` — `repos` children first, each repository where the landing did something, `repo` naming it (`.` the project's own) beside what the driver answered, `finish`'s `{into, phases}` — each with `driver`, and `committed` and `warnings` where it has them.

```bash
engine land open <work-unit> <phase>.<task>     # the task's pull request, in every repository its change touches
engine land chain <work-unit> <phase>.<task>    # the task chained into its phase's stack
engine land phase <work-unit> <phase>           # the phase merged whole
engine land finish <work-unit>                  # every phase still standing merged
```

**`inbox`** — archive / restore / delete one or more inbox items as a single transaction. Paths are validated strictly against the inbox layout (`.leeway/.inbox/{ideas|bugs|quickfixes}/…`, archived items under `.inbox/.archived/…`) before anything moves; one commit covers the whole set (`workflow(inbox): archive {slug}` for one item, `… archive {N} items` for several — same forms for restore/delete). Response: `{"ok": true, "archived": [paths…], "committed": "<short-sha>"}` (key matches the verb: `archived` / `restored` / `deleted`).

```bash
engine inbox archive <path> [<path> …]   # live → .archived/{folder}/
engine inbox restore <path> [<path> …]   # .archived/{folder}/ → live
engine inbox delete <path> [<path> …]    # git rm archived items
```

**`baseline`** — the project baseline's one verb: `record <native|skipped>` writes leeway's one-time verdict to the project manifest (`baseline.status`) and commits it confined to that file (`baseline: the project grew up on the workflows` / `baseline: decline the assessment offer`) in one transaction — a peer session's dirty files never ride. Refuses any other value, and refuses once any status is recorded: the judgment happens once. Response `{"ok": true, "status": "native"|"skipped", "committed": "<sha>"|null}` (`note: "nothing to commit"` when the manifest was already committed as written). The rest of the baseline lifecycle (`in-progress`, area statuses, `completed`) is written by the baseline skill through `manifest set project.baseline.…`.

**`walkthrough`** — the walkthrough's one verb: `record <walked|skipped>` writes the answer to leeway's one-time offer to the project manifest (`walkthrough.status`) and commits it confined to that file (`chore(help): walkthrough walked` / `chore(help): walkthrough skipped`) in one transaction — a peer session's dirty files never ride. Refuses any other value, and refuses once an answer is recorded: the offer is answered once and the answer is the record. Response `{"ok": true, "status": "walked"|"skipped", "committed": "<sha>"|null}` (`note: "nothing to commit"` when the manifest was already committed as written). Nothing else is stored — no seen-set, no screen position — and the recorded status drives the offer alone: the `h/help` row on both start menus is unconditional, and no render surface reads it.

**`roadmap`** — the product-roadmap layer: the project manifest's `roadmap` node — an ordered `horizons` list (user-named release labels; position carries the semantics) and an `items` record — ideas at capability grain, a bug or a quick-fix one fix each — every one `{horizon, summary, kind, origin[, sources][, pulled_to][, postponed_from]}`, never a status field. Item lifecycle is computed at read time by joining `pulled_to` against the named work unit (`waiting` = no join; `in-flight` = unit in-progress; `shipped` = completed; `orphaned` = the join names a missing or cancelled unit — the honest fallback for a revert that never ran). Every mutation is one transaction under the project-manifest lock **plus its own pathspec commit of `.leeway/manifest.json`** (engine-owned message, e.g. `roadmap: add {name} ({horizon})`) — no work-unit commit cadence covers the project manifest, and a park fired mid-session must be durable immediately; a git failure degrades to the standard commit-pending note. The node and any named horizon are created just-in-time by `add`/`add-batch`/`move` (`horizon_created: true` rides the response) — the roadmap has no genesis ceremony. `origin` is `harvest` | `park:{work_unit}` (the mid-flow valve — the suffix names the parking session's containing work unit, or the literal `park:discovery` from pre-commit shaping, where no unit exists yet) | `inbox:{file stem}` (moved off the inbox with its note) | `postpone:{work_unit}` (a topic that left an epic — see `topic postpone`); `kind` is `idea` | `bug` | `quick-fix`, required on every item — `add --kind` (default `idea`), an `add-batch` entry's `kind` (default `idea`), `idea` at the postpone's birth while a re-wait keeps the item's own, carried by `rename` — and an unknown kind is refused; `--source` entries are provenance pointers into session logs (relative paths under `.leeway/`, validated non-absolute, non-traversing, and never carrying a leading `.leeway/`), and every one must already exist on disk — `add` and `add-batch` refuse the whole call naming each missing path, so a session log's open comes before the op that records it. Item and horizon names follow the dot/slash-free rule, and `roadmap` is a reserved work-unit name (the layer's identity).

**Notes.** An item moved off the inbox keeps its note in the roadmap's own notes, `.leeway/.roadmap/notes/{ideas|bugs|quickfixes}/{file}` (the inbox's folder and filename kept), never KB-indexed while it waits. An `add-batch` entry's **`note`** names a live inbox path in the form `inbox archive` takes; with it the entry's kind is the note's folder's (`ideas` → `idea`, `bugs` → `bug`, `quickfixes` → `quick-fix` — a contradicting `kind` refused), its origin `inbox:{file stem}` (a note whose file name has a space is refused, naming the file), and its one source the note's new home, `.roadmap/notes/{folder}/{file}` — an `origin` or `sources` beside a note is refused. Every entry is validated first — legal names, no name twice or already on the roadmap, each note a live inbox file named once with its roadmap home free — so a refusal moves and persists nothing (`render inbox-roadmap-gate` runs the same validation over the same file); then every item lands and every note moves under one commit naming the inbox paths, the notes and the project manifest (`notes_moved: [{from, to}]` on the response, absolute). **`remove`** of a waiting item sends each roadmap note it names to `.leeway/.inbox/.archived/{folder}/` under the same commit (`notes_moved` again) — declined, restorable with `inbox restore` — except a note another item still names, which stays; an archive already holding the name refuses the remove, nothing moved. A note is never in neither place: one coming onto the roadmap moves after the manifest names it, one leaving moves before the manifest drops it, and a move that throws puts back what moved and leaves the manifest as it was. A pulled item's note stays where it is: the pull reads it as a source.

**`pull`** is the commitment point: it joins the named items (validated together — a failing name means nothing pulled) to an existing in-progress work unit by setting `pulled_to: {work_unit}`, and its response names the **remainder** per touched horizon (`"remainder": {"mvp": 3}` — a partial pull is never silent). The unit's seed set is derivable from these joins; nothing is mirrored onto the work unit (one home per fact). **`bind`** is the epic harvest's closing move for a pulled item: it records the topic the item crystallised as (`pulled_to.topic`), validated against the joined unit's discovery map; re-binding re-aims the join (a split or rename at the harvest). Only an idea binds: a pulled bug or quick-fix rides with the unit as material and is never a topic, so `bind` refuses one — and a postponed topic's re-waited item is always an idea. **`pull-forward`** is the mid-epic expansion move, one composed transaction: it creates the discovery-map item on the epic (topic = item name, source `roadmap`, summary carried; the discovery-map domain's own gates apply — `--force-dismissed` passes a user-confirmed re-add through), writes the join with the topic, and lands one commit staging both manifests; refused for a non-epic, a joined item, an occupied topic name, or an item whose kind is not `idea` — an epic grows by topics, so a bug or a quick-fix is started with the pull, as work of its own, and the refusal says so. **`flag`** records that a product session materially deepened a pulled item's ground (the judgment is the caller's): `reconcile_needed: "roadmap"` on the joined topic's live research/discussion items — `flagDownstream` semantics across the boundary (terminal items skipped, an existing flag never clobbered, a signal never a rewrite; self-commits the epic's manifest); a flag that reaches nothing — a join with no topic (a bug or a quick-fix riding with an epic, an idea not yet bound, a join into a feature, bugfix or quick-fix), or a topic whose live research and discussion are already flagged or gone — writes nothing and answers `committed: null` with a `note`, `nothing reached "{wu}" — {why}`. A postponed item — one carrying `postponed_from` — moves three ways the others do not. **`remove`** cancels the epic's row in the same transaction ("actually never" has one door): the map marker flips from `postponed` to `cancelled` and every stashed item with it, each stash and the stashed map order kept for a later reactivate, the item is deleted, and one commit stages both manifests (`roadmap: remove {name} — {topic} cancelled in {wu}`; `epic_row_cancelled: {work_unit, topic}` on the response). An item whose epic no longer exists refuses rather than orphaning the row, and so does one whose named topic holds no postpone (`the join is stale`) — the remove never reports a cancel it did not make. **`pull-forward` back into the epic that postponed it** takes the **return** branch instead of creating: `restored` names every item the marker returns, each restored `completed` artifact is re-indexed, the map order comes back unless a live row took the number, the join is re-recorded and `postponed_from` dropped (the item is in flight again; a later postpone re-sets it) — `--routing` names nothing there, the row keeping its own. The epic menu's own `f/forward` row is that branch's door, over a sub-view of every topic the epic postponed whose item still waits. **A pull that lands anywhere else** carries the prior record's address onto the receiving epic's map row as `prior: {work_unit, topic}` — `pull-forward` at creation, `bind` on the row it binds to, both staging the epic's manifest alongside the project's; the prior epic's files stay where they are and are never moved or drained. `move` re-buckets a postponed item freely — it is waiting. **The cancel-revert hop is the un-pull**: `topic cancel` whose cancellation leaves the topic's map lifecycle cancelled — and `workunit cancel`, whole-unit — delete the affected joins (`sources`/`origin` intact, items back to waiting), report `roadmap_reverted: [names]`, and stage the project manifest in their own commits; reactivation never silently re-joins (a re-pull re-binds deliberately).

**`session open`/`session close`** are the product-road session lifecycle — discovery-session's project-level sibling. `open` starts a session at the log's first write: allocate the next number from the on-disk logs (`.leeway/.roadmap/sessions/`), move the model-drafted log into place, set `roadmap.active_session` (the node created just-in-time — the genesis conversation predates any item) — no commit and no index; the session is live, and `engine commit --roadmap` is its cadence commit. `close` finalises as one transaction: clear the marker, index the log (identity `roadmap`, phase `roadmap` — graded like discovery logs), commit the roadmap dir + project manifest with the caller's `-m`. Both refuse loudly out of place (double open, close with no marker or a missing log), everything pristine. Responses: `open` `{"ok": true, "session": "NNN", "path": …}`; `close` `{"ok": true, "session": "NNN", "session_log": …, "committed": …}`. **`import`** lands reference files at the product altitude — the project-level imports home, the work unit's `workunit import` with no unit to belong to: the shared normalise/dedupe filename discipline (markdown-ish sources land `.md`, any other extension is kept and lowercased, each copy `0644`), `roadmap.imports[]` entries stamped `{path, imported_at, origin: "roadmap"}` — the layer is its own origin — a KB index per `.md` landing (phase `imports`, identity `roadmap`, warn-don't-block; a binary is tracked and never embedded), one commit staging the files and the manifest; a path that is missing or is not a regular file fails the whole call with `missing_imports` for the re-prompt, and a call whose every source is dropped by filename normalisation refuses loudly. Response: `{"ok": true, "op": "import", "imports": [{path, origin}…], "skipped_imports": […], "committed": …}` — relay `skipped_imports` when non-empty. `state` also reports the session material: `active_session`, `session_logs` (number + path, ascending), `next_session_number`, `imports` (each with its `origin`).

Authority splits at the pull: un-pulled items take every edit (`edit`, `rename`, `move`, `remove`); a **pulled** item refuses `move` and `remove` — re-bucketing or deleting in-flight delivery is the work unit's decision, and the refusal names the join and the item's way back to waiting: for a topic join, cancelling or postponing that topic; for any other join (a bug or a quick-fix riding with an epic, an idea not yet bound, a join into a feature, bugfix or quick-fix), only the work unit's cancel; a shipped item stays as its release's record, and an orphaned join is named as such — while `edit` (cosmetic; the row is a window) and `rename` (every field carried, the join included) stay open. Horizon ops run at any join state — relabeling a release never un-commits work: `rename` cascades to every member's `horizon` field, `reorder` demands a complete permutation of the current list, `merge` moves every member and drops the source label, `split` creates the new horizon (default: right after the source; `--position` overrides, 1-based) and moves the named members (each must belong to the source), `remove` refuses a horizon with members, naming them. `add-batch` validates every entry before applying any (a failing entry means nothing persisted) and lands under one commit; `added` names each item with its horizon and kind. `state` is the derived read every consumer shares: `{"ok": true, "exists": bool, "horizons": […], "items": [{name, horizon, summary, kind, origin, sources, state[, work_unit][, topic][, work_type]}…], "totals": {items, waiting, in_flight, shipped, orphaned}}` — items horizon-ordered, absent/malformed state reading `exists: false`. Mutation responses are decision-ready: `add`/`move` echo the placement plus `horizons` and `item_total` (`add` its `kind` too); `rename` carries `renamed_from`/`preserved_fields`; horizon ops echo the list after (`horizons`) plus op-specifics (`items_updated`, `items_moved`).

```bash
engine roadmap state
engine roadmap add <name> --horizon <h> --summary <text> [--kind <idea|bug|quick-fix>] [--origin <tag>] [--source <path> …]
engine roadmap add-batch --file <items.json>       # entries {name, horizon, summary, kind?, origin?, sources?, note?} — atomic, one commit; a note moves off the inbox to .roadmap/notes/
engine roadmap edit <name> --summary <text>        # any join state (cosmetic on a pulled item)
engine roadmap rename <old> <new>                  # any join state; every field carried, join included
engine roadmap move <name> --horizon <h>           # waiting items only; JIT-creates the horizon
engine roadmap remove <name>                       # waiting items only; no dismissed list — git history keeps the story; its roadmap note goes to the inbox archive; a postponed item cancels the epic's row with it
engine roadmap pull <name> [<name> …] --into <work-unit>   # the commitment point; remainder named per horizon
engine roadmap bind <name> --topic <topic>         # record the topic a pulled idea crystallised as — a bug or quick-fix never binds
engine roadmap pull-forward <name> --into <epic> --routing <research|discussion> [--force-dismissed]   # ideas only; map topic + join, one commit; back into the epic that postponed the item it restores that row instead, and --routing names nothing
engine roadmap flag <name>                         # reconcile_needed: "roadmap" on the joined topic's live phase items
engine roadmap session open --session-log-file <path>   # install the drafted log, set the marker — no commit
engine roadmap session close -m "<message>"             # clear the marker, index, commit roadmap dir + project manifest
engine roadmap import <path> [<path> …]                 # land reference files at the product altitude (origin "roadmap") — one commit
engine roadmap horizon add <name> [--position <n>]
engine roadmap horizon rename <old> <new>          # cascades to member items, joins included
engine roadmap horizon reorder <name> [<name> …]   # the complete order — a permutation of the current list
engine roadmap horizon merge <from> --into <to>    # moves every member, drops the source label
engine roadmap horizon split <name> --new <name> --items <a,b,…> [--position <n>]
engine roadmap horizon remove <name>               # empty horizons only
```

Errors when no qualifying inputs exist — the analysis's preconditions skip the stamp in that case. Response: `{"ok": true, "kind": "…", "checksum": "…", "files": N, "warnings": []}`. **`commit`** — the scoped commit helper. **Every engine commit is confined to a pathspec** — this helper and every transaction tail alike: each commits exactly its paths, from HEAD plus the working tree's content of them — in the code tree `git add -- <paths>` then `git commit -m … -- <paths>` (the code side of `--migrations` alone commits its paths as the index records them — below). Every path is taken literally: one holding `[`, `*` or `?`, or opening on `:`, names that file and never a pattern (`app/[id]/page.tsx` commits that file, never `app/i/page.tsx` beside it). Nothing outside the declared scope can ride but a state commit's logs (below), so a concurrent session's dirty or staged files (and the user's own staged code) are ignored and left exactly as they were. Pathspecs matching neither disk nor index are dropped before the add — a scope naming a path its action never created is normal. A clean scope is fine: `{"ok": true, "committed": null, "note": "nothing to commit"}`, exit 0 — `"committed": []` for `--paths`, whose commits are listed per repo (below).

**Two doors, one per side** (`domain/commit.cjs`). **The state commit** takes paths under `.leeway/`, named from the state root, and is made in the state worktree on `leeway-state` (`domain/state-worktree.cjs`) under the writer lock: built in a private index from HEAD and the working tree, never through the worktree's own index, so nothing a killed verb or a person left staged there can break it; a merge's landing a kill cut short is finished first, so the commit moves the branch on from where that landing put it. A commit whose ledger does not start, byte for byte, with its parent's is refused, but the one a migration's conversion lets through. Then the branch is pushed wherever the project has a remote, never forced: a push that fails, runs out of time, or finds no remote chosen among several is a warning in `warnings`, and the commit stands. Every form but `--paths` makes one, and so does every verb's own commit. **The code commit** — `--paths`, and the code side of `--plan` and `--migrations` — is made in the code root's own tree on the branch checked out, never on the state branch: no code commit lands in a tree that has `leeway-state` checked out.

The scope by form, named from the state root: `{wu}` bare, `.inbox` with `--inbox`, `.roadmap` plus the project manifest with `--roadmap` (the product session's cadence commit — the roadmap node lives on the project manifest), the whole state with `--workflows` (a flow writing across work units — the baseline, a quick-fix promotion), the whole state and the files the workflows own in the code tree with `--migrations`. No form stages the knowledge directory or the cache: the state's own `.gitignore` ignores them whole, beside the writer lock.

Every state commit — this helper's state forms and every verb's own, a transaction tail's among them — is held to the layout (`domain/layout.cjs`) before its tree is built, reading the state worktree's changes once (`git status`: untracked files among them, ignored ones not). A file on disk the layout has no place for — one a shell wrote past the layout hook — refuses the commit, naming each with the way on, and nothing is committed: `the state at {root} holds {unit}/tmp/x.md, outside the workflows' layout — nothing committed; remove it, or move it into the layout`. A transaction tail answers it as it answers any commit git refuses: the verb `ok`, the refusal in `warnings`, and the `commit pending` note. `--workflows` and `--migrations` refuse it too, `--migrations` committing nothing on the code side either. A file gone refuses nothing, whether deleted from the working tree or with its deletion staged. Every changed log of the layout's — a topic's `log.md`, discovery's `session-NNN.md`, the product's `sessions/session-NNN.md` and the build's `log.md` — rides along with the scope under the same message, and is pushed with it. The files the person's tools leave beside the state's are neither refused nor committed, wherever they are — matched by base name, `*` any run of characters: Finder's, Explorer's and AppleDouble's (`.DS_Store`, `Thumbs.db`, `desktop.ini`, `._*`), Vim's (`.*.swp`, `.*.swo`, `.*.swx`), Emacs's (`*~`, `#*#`, `.#*`) and JetBrains' (`*___jb_tmp___`, `*___jb_old___`). A merge's landing at the catch-up is no verb's commit, and is never held to the layout.

`--migrations` is the reviewed migration commit — leeway's, on the user's yes at the migration gate — one commit on each side that changed, under the one message. The state side is the whole state, a state commit like any other. The code side is the files the workflows own in the code tree, a list held once in the commit door (`OWNED_PATHS`, `domain/commit.cjs`): `.claude/settings.json`, `.worktreeinclude` and the code root's `.gitignore`. It stages every change under them — edits, new files, deletions — and commits them as the index then records them, from a scratch index holding HEAD with those paths' entries taken from the real one: a removal a migration staged (`git rm --cached`, the file left on disk) lands, where a partial commit would read the file straight back from the working tree, and whatever else is staged stays staged and out of the commit. An owned path git refuses to stage — one the project ignores, one beyond a symbolic link — is left as it is, never forced in, and one that neither exists nor is tracked is dropped. The code side refuses while a merge, cherry-pick, revert, rebase or bisect is in progress, staging nothing. The response carries the state commit as `committed` and the code commit as `code_committed` (null where that side had nothing), `nothing to commit` noted only where neither committed.

`--plan <topic>` is the planning session's form: the planning topic's directory and the work-unit manifest — the same action scope `--topic` takes — plus the plan's declared storage, which often lives outside the work unit: the project manifest (plan init writes project defaults), committed in the state; and every `storage_paths` entry recorded on the planning item at plan init (the format's authoring doc declares them; entries are validated relative-only, while deleted-but-tracked paths still commit their deletions), committed in the code tree, from the code root — two commits under one message, answered as `--migrations`' are (`committed`, `code_committed`). A sibling topic's files — a peer session's discussion, another plan — never ride. A planning item without `storage_paths` fails loudly with the one-line repair. Code never rides a `--plan` commit — code has its own form below.

`--topic <phase>/<topic>` is the session-cadence form: the topic's artifact (`{phase}/{topic}.md` for research/discussion/investigation, `topics/{topic}/experiments/` for experiment, `{phase}/{topic}/` for specification/planning/implementation/review) plus the topic's mailbox directory (the mailbox phases — research, discussion, investigation) plus the work-unit manifest. `--sweep` marks a commit made on a topic the session is not working — the conclude sweep's leavings, the retry a foreign-topic delivery's pending note prescribes, a resolution landed in another phase's document. Its presence semantics are in the beat table under `presence`, where `--sweep` outranks everything and the item's own status decides the rest. Mutually exclusive with `--plan`, `--discovery` and `--state`.

`--discovery` is the discovery session's cadence form: `discovery/sessions/`, `discovery/briefs/`, and the work-unit manifest (the map lives there). Discovery runs beside live research and discussion sessions on the same work unit, so it slices its own paths and never theirs.

`--imports` is the retry the import landing's pending note prescribes: the work unit's `imports/` home and its manifest — the landing's own tail scope, so the retry stages no more than the landing itself would have. It never beats: running an owed commit is not a session's work on a topic.

`--state` is the analysis form, and names two scopes by whether a work unit rides with it. `{wu} --state` is the work unit's analysis dir plus its manifest — the scope the epic-wide analyses write: the grouping and consolidation passes, the gap analysis, build-order sequencing. Every one of them runs beside live topic sessions whose half-written documents sit in the same work unit. Bare `--state` is the state's `.state` alone — the global bookkeeping dir (migrations, environment setup), written from inside whatever session happened to need it. Neither beats: an analysis is not a session sitting in a topic.

`--paths <file> …` is the code commit — the one scope no layout derives (code has none), so the session declares it and the engine checks it: every path must resolve inside the project and never in the state, `.leeway/`, whose artifacts have derived scopes of their own. Paths are the project's wherever the code lives. A project can keep code in repos of its own inside its folder — an untracked nested repo, a submodule, or an ignored folder holding `.git` itself, each searched for its own in turn, and never a linked worktree of the repository holding it, the state worktree among them — found on every call, never configured (`kernel/repos.cjs`); a path belongs to the deepest of them whose folder holds it, else to the root. In that repo the path must be on disk or in the index and stageable there (an ignore rule or a symbolic link refuses it), have its deletion staged, or have been deleted by the repo's HEAD commit (one an earlier run of the call landed, with nothing left to commit). Every repo the call would commit in, a reached submodule's parent among them, must have no merge, cherry-pick, revert, rebase or bisect in progress — the commit would take on its state — must be on a branch: a commit on a detached HEAD (a submodule after `git submodule update`) would be orphaned by the next checkout — and must not have the state branch checked out. Each refuses the call, naming the repo. Every path and repo is checked before any repo commits. Each repo then commits its own paths with the one message, deepest first so a nested repo commits before its parent, holding out the untracked repos and submodules inside it: a parent never commits a nested repo's folder, and commits a submodule's pointer only where the call reached into that submodule — its parent then takes the submodule's folder too, never holding it out of a folder the call also names, so the pointer lands whenever it differs from the parent's HEAD. The call names its target, one of two: `--task <work-unit> <N.M>`, the task in flight (below), or `--for <work-unit> <implementation|review>/<topic>`, the code topic, which the commit beats — so that target is checked before anything is staged: the work unit's directory and the named phase item must both exist, or the call refuses. (A mistyped `--for` would otherwise mint a hold no session owns and no session-end sweeps, and the checkout's code slot would read taken until the machine restarted.) `committed` lists the commits made in that order, `[{"repo": "api", "sha": "…"}, {"repo": ".", "sha": "…"}]` — `.` naming the root, a repo with nothing to commit left out — and is `[]` beside the `nothing to commit` note when no repo had anything. A repo whose commit fails fails the call, the error naming that repo and the commits already made; re-running the same call is the retry, since those repos have nothing left in the named paths and a moved pointer lands whatever moved it. The response adds `left_dirty` — every tracked modification and untracked file left in the code, in every repo, each untracked file on its own (never its folder, so a file the call left beside one it named is named itself), named from the project (a project inside a larger repository reads only its own folder of it); a parent's view of a nested repo (its untracked folder, a submodule's moved pointer) is never dirt — so the session can close the loop on a path it forgot to name. The state is never code dirt: document sessions run concurrently with the code session by design, and their dirt is theirs.

`--task <work-unit> <N.M>` commits for a task, which must be in flight in the calling conversation (`domain/commit-task.cjs`) — the one `CLAUDE_CODE_SESSION_ID` names, as its position records it once `task start` puts the task there (read through `conversation.cjs`'s `tasksInFlight`, as the hook before Bash reads it). Before any path is read it refuses, each with the way on: no conversation; a unit the project lacks; a task id that does not read `{phase}.{n}`; no task in flight — start it with `engine task start <unit> <N.M>`, again after a `/clear`, which begins another conversation; and another task in flight, named. The paths and repos are then checked as above, and the project's checks run: its tests, `environment.run.tests` on the project manifest, then each of `environment.linters`' commands (`domain/environment.cjs`) — a part the setup does not hold is no check, and one of another shape refuses. Each runs by `sh -c` in the code root of the calling checkout — a code worktree the call is made from is its own — before any lock is taken, its output and errors captured, with no timeout of the engine's own. The first that fails refuses the commit, nothing committed, naming the check, its exit code (a signal's as the shell gives it, 128 and its number) and its output's last 40 lines. The checks run inside the Bash tool's call, which stops at two minutes unless given a longer timeout, so a commit whose checks run long is called with one; the refusal says so. Then each repo commits as above, under the message given with the trailer `Leeway-Task: {id}`, the task's internal id (`domain/task-id.cjs`) — added to the trailers the message ends in, as `git interpret-trailers` adds one, where its last paragraph past the subject is all `Token: value` lines, else a paragraph of its own — never landing's `Task:` line, which the landing drivers read as the task landed. It beats no topic. The response is `{committed, left_dirty, task, checks}`, `note` beside them as above: `task` the id, `checks` each check run, `{name, exit}`, in order — the tests named `tests` — and `[]` where the project sets none. `--for` stays beside it until the implementation prose moves onto `--task`: a commit through it names no task and runs no check.

Every code commit runs under a process-wide commit lock in the git dir of the repo it commits in (`.git/leeway-commit.lock` — in the `.git` dir so it can never be staged; a holder stale only after five minutes, a contender waiting up to one), and every state commit under the writer lock; index-mutating git operations retry briefly through `index.lock` contention before surfacing git's error. Transaction-tail commits degrade rather than abort: the state write has landed, so a git failure leaves the verb `ok` with a `note` prescribing the retry and the git error appended to `warnings`, beside any push warning. A note is contract surface — a session runs the command it names verbatim — so a tail whose commit was narrower than the work unit spells its own scope (`retry with: engine commit {wu} --discovery -m "<message>"`); only a genuinely work-unit-wide tail keeps the bare `retry with engine commit`.

While the migration runs — `leeway-state` checked out with no commit yet — every state commit is held: a file outside the layout refuses it as ever, and otherwise nothing is committed or pushed, the writes staying on disk for the migration's commit to take, and a verb answers `"committed": null` with the note `held for the migration's commit`.

```bash
engine commit <work-unit> -m "<message>" [--plan <topic> | --discovery | --imports | --state | --topic <phase>/<topic> [--sweep]]
engine commit --paths <file> … -m "<message>" --task <work-unit> <N.M>    # the task in flight in this conversation; the project's checks first
engine commit --paths <file> … -m "<message>" --for <work-unit> <implementation|review>/<topic>
engine commit --state -m "<message>"                # the state's own .state dir
engine commit --inbox -m "<message>"
engine commit --roadmap -m "<message>"
engine commit --workflows -m "<message>"
engine commit --migrations -m "<message>"            # the whole state, and the owned code files as the index records them
```

**`code`** — the code change, read across every repo in the project (`domain/code.cjs`): the root and the repos the code commit finds inside it (see `--paths` under `commit`). Paths in and out are the project's, whichever repo holds the code; a project inside a larger repository reads only its own folder of it, a commit that touched nothing there none of its. In a project of one repo each form answers what git answers there. Nothing is written.

`log` and the selecting `diff` take commits by one of two selections, never both:

- `<work-unit> <topic> [--phase <N>]` — the topic's task commits: those whose subject opens `impl({work_unit}): T` and an internal id of the topic, `{topic}-{phase}-{task}`, ending the subject or followed by a character no id continues with — anything but a word character or `-`, so a space, a colon or an em dash ends it. A sibling topic whose name extends this one (`auth`, `auth-flow`, `auth-2`) is never caught, and neither is an id that runs on (`auth-1-1x`). `--phase` takes that phase's task commits alone.
- `--subject <prefix>` — the commits whose subject opens with the prefix, taken as a fixed string (`review({work_unit}): {topic} cycle {N} — apply do-now findings`). A mention in a body, or the prefix later in a subject, never matches.

The forms:

- `log` answers `{"ok": true, "commits": [{"repo", "sha", "subject"}], "files": […], "repos": [{"repo", "base"}]}` — the selected commits grouped in repo order (the root, `.`, first, then the nested repos in folder order), oldest first within each; the project paths they touched, sorted, each once; and one entry per repo holding any, its `base` the full sha of the parent of its earliest selected commit, or git's empty tree where that commit is the repo's first. A move names both its paths. A submodule's pointer is the submodule's change, never its parent's: the commit that records a moved pointer under the task's subject drops out, and one carrying more keeps the rest. A repo with no commits yet adds nothing; a selection nothing matches answers three empty lists.
- `diff` with a selection is the change those commits made: each repo's diff from its base to its `HEAD`, confined to the files its selected commits touched — a later commit on one of those files is part of it, a file only an unselected commit touched is not.
- `diff` alone is the change not yet committed: each repo's change against its `HEAD` (the empty tree before the repo's first commit), staged and unstaged, with its untracked files read as additions in the same patch — taken in as intent-to-add on a scratch copy of the index, so the real one never changes. `.leeway/` is held out, and so is a parent's view of a nested repo — its untracked folder, a submodule's moved pointer.
- `status` answers `{"ok": true, "files": [{"path", "status"}]}` — every uncommitted file across the repos with its two-letter porcelain status (`??` untracked, whatever the user's `status.showUntrackedFiles`; each untracked file named on its own, never its folder, so a new folder lists every file in it), the same dirt `commit --paths` answers as `left_dirty`, with the same hold-outs as `diff`.

The two `diff` forms answer the unified diff itself on stdout, never JSON — read as `git diff` output is — and nothing at all when there is no change. One patch per repo, in repo order, its paths named from the project: a nested repo's folder rides the `a/` and `b/` prefixes (`diff --git a/api/src/billing.ts b/api/src/billing.ts`), and a move reads as a deletion and an addition, so both its paths carry it. The patch is plain whatever the user's git config — no colour, no external diff driver. Bad usage refuses (`{"ok": false, "error": …}` on stderr, exit 1): the two selections mixed, a missing or empty prefix, a second one, a `--phase` that is not a phase number or names no topic, an unknown flag, a stray positional.

```bash
engine code log <work-unit> <topic> [--phase <N>]
engine code log --subject "<prefix>"
engine code diff [<work-unit> <topic> [--phase <N>] | --subject "<prefix>"]
engine code status
```

**Transaction receipts.** The lifecycle verbs answer with their one-line JSON only. The user-facing receipt — `DISPLAY: confirmation`, the `DISPLAY: kb warning` advisory, the absorption/promotion summaries, the `MENU: pivot continuation` — is fetched by the calling flow right after the verb via the `render` receipt surfaces (`workunit-receipt`, `topic-receipt`, `absorb-receipt`, `absorb-continuation`, `promote-receipt`, `pivot-continuation`, `session-receipt`). Each surface validates that the state it renders from matches the verb it receipts and refuses loudly out of place; `--warn` prepends the knowledge advisory, set by the caller when the transaction's JSON carried `warnings` (the failure detail itself stays in the JSON line). The calling flow emits each section verbatim per its marker, in the step that shows it, and never parses it for decisions.

**`handoff`** — every move into work, named by one call (`domain/handoff.cjs`), the skill bare or as its slash command — a menu's stored route passes as it stands. One table holds each skill a handoff lands on and the arguments it takes: `leeway-discovery <work-type|none> <none|epic> [<inbox-paths|none>]` (a work type or `none`; `none` or an epic the project holds, an epic only beside the work type `epic` or `none`; `none` or comma-joined live inbox items on disk, each named once, and only where no epic is named — absent reads `none`), `leeway-roadmap open`, `leeway-baseline`, which takes no arguments, `leeway-continue-epic <epic> [<completed-phase> <outcome>]` (the phase `discovery` or one the epic's pipeline holds, the outcome `completed`, `paused`, `cancelled` or `postponed`, the two given together, and `paused` only from a phase `render phase-paused` takes — `PAUSING_PHASES`, the one list both read), and each phase's own skill, `leeway-{phase}-process` — `<work-type> <work-unit> [<topic>]` (a work type whose pipeline holds the phase, a work unit the project holds of that type, and a legal topic name, which need not exist yet — an epic always names it). One more form names no skill: `topic <work-unit> <topic>`, the start skill's direct open (`/leeway {unit} {topic}`, the line a send report ends with), hands off into the phase the unit's topics are talked through — a bugfix's investigation, any other's discussion — its work type read from the unit and the rest checked as that skill's handoff is. It refuses, before anything travels, what that phase's `enter` would refuse, by its rule (`domain/topic-standing.cjs`) and in its words: a unit the project lacks or not in progress, one past its `spec.md`, a topic the unit does not hold, and one cancelled, postponed, promoted, closed as a dead end or, in discussion, decided — a bugfix's investigation once its menu leads past it (`computeNextPhase`); and a quick-fix, which has no topics to open by name. Anything else refuses (`{"ok": false, "error": …}` on stderr, exit 1): a skill outside the table, the wrong number of arguments (the error is the target's usage), an argument of the wrong shape or in a combination its target cannot take, a work unit no longer in progress (a handoff moves into work in progress), a manifest that does not parse (refused as such, never as a unit not found), and an argument the invocation could not carry — a backtick in any (it would end the continuation's code span), whitespace or a quote in any but the quoted seeds, a double quote in those. `none` is a reserved work-unit name, so the placeholder never names a unit. The engine composes the continuation, ``Invoke `/<skill> <args>`.`` — the inbox seeds quoted, as discovery reads them — and the line naming where the work goes, the place and then its most specific name (`→ Discussion · note-window`, `→ Discovery`, `→ Epic · fumi`); the session writes neither, and nothing travels but the skill and its arguments. The answer is sections, as a render surface's is, and nothing is written: a `DATA` section reading `handoff: mod` where the gate mod announced it carries handoffs (`LEEWAY_HANDOFF=1` in the environment, set at session start beside and independent of `LEEWAY_GATE_SURFACE`) and `handoff: inline` where it did not, then `skill:` and, where the skill takes any, `args:` as the skill is invoked with them; a `DISPLAY: handoff` section carrying the line; and, announced alone, a `=== HANDOFF … ===` section — one line of JSON, `{"skill", "args", "text", "line"}` with `text` the continuation — for the mod, which cuts it from the conversation's Bash result, clears the conversation as the turn ends and sends `text` into the new one. Under `inline` the session invokes the skill in place, as it does under `mod` where the section is still in the result — the mod did not take it.

```bash
engine handoff <skill|/skill> [args …]
engine handoff topic <work-unit> <topic>
```

**`render`** — the surface catalogue (`domain/render.cjs`): named runtime surfaces returning demarcated `=== DISPLAY: … ===` / `=== MENU: … ===` sections the calling flow emits verbatim per their markers, in the step that shows them. Address-backed values come from the manifest (JSON state only — the engine never parses markdown artifacts); judgment content arrives as a JSON payload file written to the phase cache with the Write tool and validated loudly per-field. Gate-mode branching happens inside the surface: the response carries the menu when the mode is `gated` and the auto-proceed line otherwise — a payload may force the gate over an `auto` mode (the `finding` surface's `choice` move), so the calling flow follows the response's sections, never a section re-derived from gate-mode state. No git commit; nothing is written, with one exception — `code-gate`'s empty path beats the addressed topic, because claiming the code slot and reading it are the same act. While `LEEWAY_GATE_SURFACE=1` is in the environment a `=== GATE … ===` section sits directly above the response's first `MENU` — one line of JSON stating the menu's question, its statement (every other line of prose it draws), its pressable rows (each part of a row's label a field of its own) and its typed rows, each row with its detail (the lines drawn directly beneath it, `null` when none), every value as text with its markup removed and its escapes honoured. The collector is taken once per response, so a later `MENU` in the same response carries none, and neither does a `MENU` that draws nothing; the section is for a surface that draws the gate, never displayed, and absent without the flag.

The pipeline continuation surfaces — the bridge's gates, the epic menu's banners and completion offer — take a bare `<work_unit>` address (work-unit-level, type read from the manifest).

The `finding` surface serves both review-findings loops (planning and specification) with per-consumer labels in the payload; `proposed-task` serves the synthesis loops (implementation analysis, review actions), the ad hoc plan-changes gate, and the consolidation-boundary walk the same way — two altitudes picked by the payload (a proposal carries title/problem/solution and optionally outcome; a full task adds criteria/steps), severity/sources ride the synthesis and consolidation payloads, placement/priority/depends_on the ad hoc and consolidation ones, all optional and rendered only when present; a `decision` payload — an irreducible product fork, its required `stakes` arguing the stop — slims the display to the header, carries its question as the menu's statement label, and renders its sides as the menu (recommended side first, a `t/technical` arm back to the staged record and the findings behind it), stopping at either gate mode; the record stays staged — the session composes the raise between the two emissions; its gate mode rides as a flag because the flows carry the mode in a cycle response or the manifest's staging subtree. `task-list` takes `--variant existing` for plan-construction's review-of-existing-tables gate (no auto-opt-in option; "confirmed" phrasing). The `finding` surface renders a diff as a single section in a diff code block (```diff fence) — space-prefixed context lines placing the change, `-`/`+` change lines — so the host's diff colouring applies; prose artefact content (`content`) renders as markdown (not a code block). Drawn borders never frame content, and nothing commits to a fixed width.

The `render` group also keeps its dev/debug primitives (`signpost`, `wrap`, `tree`) — authoring aids only, never called from skill flows.

**Static chrome stays literal in skill prose; everything parameterised or state-branching renders in code** — adapter-side via projections, shared runtime surfaces (gates, receipts, menus) via the `render` catalogue above. Transactions answer with one JSON line and render nothing. Only the `render` group's dev primitives (`signpost`, `wrap`, `tree`) are authoring aids never called from flows.
